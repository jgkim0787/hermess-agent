개념

M4에서 Hermes에 대화 메모리를 달며 우리는 못을 하나 박아 뒀다 — "이건 대화를 요약해 이어가는 working memory일 뿐, 임베딩으로 문서를 검색하는 RAG가 아니다 → M6". M5에서 자율 에이전트를 완성하며 또 한 번 미뤄 뒀다 — "Hermes는 가진 도구로만 자율적이다. 모르는 지식을 검색해 오는 건 M6". 이번 모듈이 그 두 예고를 한꺼번에 회수한다. (M4가 agent.py의 "여기가 Memory 자리" 주석을, M5가 run_bash의 "승인 게이트는 M5" 주석을 회수했던 것과 같은 구조다.)

지금의 Hermes를 냉정히 보면, 답을 짓는 재료가 딱 두 가지뿐이다 — 모델이 학습 때 익힌 지식과 지금 대화의 history. 그 둘 밖에 있는 것은 모른다. 이 모듈은 세 섹션이 하나의 소재를 공유한다 — "Nimbus"라는 (우리가 방금 지어낸) 사내 배포 도구다. "Nimbus에서 동시에 배포하는 서버 수 기본값이 몇이야?"라고 물으면 지금의 Hermes는 모른다고 하지 않고 그럴듯한 숫자를 지어낸다. 정답 4는 로컬 문서에만 있다. M6가 끝나면 Hermes는 그 문서를 스스로 찾아 "4"라고 답한다 — 이 여정이 이번 개념의 전부다.

왜 RAG인가 — 모델은 자기 밖을 모른다

정의 — RAG (Retrieval-Augmented Generation): 모델이 모르는 외부 지식을 검색해 프롬프트에 넣고(retrieval), 그 근거로 답을 생성(generation)하는 방식. 모델을 재학습하지 않고 지식을 질의 시점에 붙인다. 비유하면 캐시/DB를 조회해 그 결과로 응답을 조립하는 서버 핸들러 — 단, 최종 응답을 쓰는 주체가 우리 코드가 아니라 LLM이다.

왜 Hermes는 Nimbus를 모를까. M1의 두 사실 때문이다. LLM은 stateless 함수라 매 호출은 우리가 보낸 messages만 보고, 지식은 학습 cutoff 시점에 얼어붙어 있다. 그래서 학습 코퍼스에 없던 것 — 로컬 파일 내용, 사내 규칙, 어제 정한 값, cutoff 이후의 사실 — 은 애초에 알 수가 없다. Nimbus가 딱 그렇다. 우리가 방금 지어낸 도구라 세상 어떤 모델도 모른다.

더 나쁜 건, 모른다고 안 하고 그럴듯하게 지어낸다는 것이다(hallucination). "max_parallel 기본값?"에 모델은 "8입니다" 같은 답을 자신 있게 내놓는다 — 틀렸는데 틀린 티가 안 난다. 해법은 모델의 머리를 바꾸는 것(재학습)이 아니라, 답에 필요한 텍스트를 그때그때 찾아 입력에 끼워 넣는 것이다. 함수가 모든 데이터를 하드코딩하지 않고 런타임에 DB를 조회해 응답을 조립하듯, RAG는 LLM판 "외부 조회 후 응답"이다.

그 파이프라인은 다섯 조각이다 — 문서를 chunk로 쪼개고 → 각 chunk를 embedding(벡터)으로 만들고 → 질문도 같은 공간의 벡터로 만들어 vector search로 가장 가까운 top-k를 찾고(이 검색 행위가 retrieval) → 그 chunk를 프롬프트에 넣어 → 답을 생성(generation)한다. 하나씩 보자. (미리 못 박아 둘 사실 하나 — chunk화·embedding·검색에는 API 호출이 0이다. 전부 순수 파이썬이고, Claude는 오직 "검색이 필요하다"는 판단과 "chunk를 근거로 한" 생성에만 쓰인다.)

문서를 chunk로 쪼갠다

정의 — chunk(청크): 검색·임베딩의 단위로 문서를 쪼갠 작은 텍스트 조각(문단·고정 길이 등). 비유하면 큰 로그/문서를 인덱싱 단위(라인·블록·문단)로 나누는 것.

왜 문서를 통째로 안 넣고 쪼갤까. 이유가 둘이다. ① 정밀도 — 질문과 관련된 바로 그 부분만 골라 넣어야 정확하다. 문서 전체를 넣으면 노이즈가 섞이고 토큰 비용(M1)만 는다. ② context window(M4) — 큰 문서 여러 개를 애초에 통째로 못 넣는다. 그래서 문단/문장 단위로 색인하고, 관련된 chunk만 주입한다.

우리 소재로 보면, Nimbus 문서 몇 개를 chunk_text()가 문단(빈 줄) 기준으로 쪼갠다. 짧은 문서라 대개 한 문단 = 한 chunk다. "max_parallel … 동시에 배포할 서버 수 … 기본값은 4다" 한 문장이 하나의 chunk가 되고, "점심 메뉴: 화요일 김치찌개 …" 문장이 또 다른 chunk가 된다.

chunk 크기는 트레이드오프다: chunk가 너무 크면 관련 문장이 무관한 문장에 묻혀 유사도가 희석되고 토큰을 낭비한다. 너무 작으면 맥락이 끊겨(대명사·앞뒤 문장 참조가 사라져) 검색해도 쓸모가 준다. "어디서 끊느냐"가 검색 품질을 좌우하는 실무 RAG의 핵심 다이얼이지만, M6는 문단/고정 길이의 가장 단순한 방식 하나만 쓴다(겹침·메타데이터 청킹 등은 범위 밖).

텍스트를 벡터로 — embedding

정의 — embedding(임베딩): 텍스트를 숫자 벡터로 변환해 "비슷한 텍스트는 벡터가 가깝다"가 성립하게 만든 표현. 그러면 텍스트 유사도를 벡터 거리로 잴 수 있다. 비유하면 문서를 term 벡터로 보는 벡터 공간 모델(전통 IR).

텍스트끼리 "얼마나 비슷한가"를 컴퓨터가 재려면 숫자로 바꿔야 한다. embedding이 그 다리다 — 텍스트를 벡터로 사상하면 비슷한 텍스트 = 가까운 벡터가 되어, 벡터 거리로 검색할 수 있다. ★ 우리의 embedding은 순수 파이썬 TF-IDF다. 각 chunk를 {단어: TF-IDF 가중치} 스파스 벡터로 만든다. 예컨대 정답 chunk는 개념적으로 이런 모양이 된다 — {"nimbus": 0.31, "max_parallel": 0.74, "동시에": 0.52, "배포": 0.28, "서버": 0.41, "기본값": 0.52, "4": 0.60, ...}. 이 dict가 곧 이 chunk의 embedding이다.

def tokenize(text):
    return re.findall(r"[가-힣a-zA-Z0-9_]+", text.lower())   # 소문자화 + 단어 추출

def tfidf_vector(tokens, idf):          # ← 이 함수가 '우리의 embedding'이다
    tf = Counter(tokens)
    n = len(tokens) or 1
    return {t: tf[t] / n * idf.get(t, 0.0) for t in tf}
# idf 는 compute_idf() 가 코퍼스 전체에서 미리 구해 둔 {단어: IDF} 표.
# (TF-IDF 의 수식 자체는 아는 것으로 두고 넘어간다.)

여기서 이 모듈에서 가장 중요한 한 문장을 못 박는다. TF-IDF도 "진짜" embedding이다. "텍스트 → 벡터, 유사도 = 벡터 거리"라는 embedding의 정의를 그대로 만족한다. 다만 이 벡터의 차원이 단어 그 자체라, 어휘(lexical, 단어 겹침) 기반이지 의미(semantic) 기반이 아니다. 이 구분이 왜 중요한지는 잠시 뒤 "정직한 고백"에서 정면으로 다룬다.

가장 가까운 걸 고른다 — vector search

정의 — vector search(= similarity search, 유사도 검색): 질문을 같은 방식으로 벡터화한 뒤, 저장된 chunk 벡터들과 cosine 유사도를 재서 가장 가까운 top-k를 찾는 것. 비유하면 벡터 공간의 최근접 이웃(k-NN), 검색엔진의 스코어링·top-k.

질문도 chunk와 똑같이 tokenize → tfidf_vector로 벡터화한다. 결정적으로 질문도 코퍼스의 같은 idf로 벡터화한다 — 두 벡터가 같은 공간에 있어야 거리를 잴 수 있기 때문이다. 그다음 질문 벡터와 모든 chunk 벡터의 cosine을 재서 높은 순으로 TOP_K개를 반환한다.

def cosine(a, b):
    dot = sum(a[t] * b.get(t, 0.0) for t in a)
    na  = math.sqrt(sum(v * v for v in a.values()))
    nb  = math.sqrt(sum(v * v for v in b.values()))
    return dot / (na * nb) if na and nb else 0.0   # ← 0-norm 가드: 겹치는 단어가 0이면 0.0

대표 질문 "Nimbus에서 동시에 배포하는 서버 수 기본값이 몇이야?"를 벡터화하면 Nimbus·동시에·배포·서버·수·기본값이 살아 있다. 정답 chunk와는 이 단어들이 여럿 겹쳐 cosine이 높고 → top-1. 반면 "점심 메뉴" chunk는 겹치는 단어가 하나도 없어 cosine이 0 → top-k 밖으로 밀린다. (검색이 노이즈를 제대로 버리는지 보려고 일부러 무관한 문서를 섞어 뒀다.) cosine을 쓰는 이유는 문서 길이에 휘둘리지 않는 방향 유사도라서다. 0-norm 가드가 빠지면 질문이 어떤 chunk와도 안 겹칠 때 ZeroDivisionError가 난다 — 흔한 경우다.

비유의 한계(k-NN): 교과서적 k-NN은 보통 밀집(dense) 벡터·유클리드 거리지만, 우리 건 스파스 dict·cosine이다. 또 우리는 chunk가 몇 개뿐이라 전수 비교(정확한 top-k)를 하지만, 대규모에선 근사 최근접(ANN)·vector DB를 쓴다 — 그건 M6 범위 밖(포인터)이다.

묶으면 retrieval, 도구로 노출하면 RAG 에이전트

정의 — retrieval(검색/인출): 질의 시점에 embed(query) → vector search → 관련 chunk 반환까지를 묶은 검색 행위. 비유하면 요청을 받아 인덱스를 조회해 관련 레코드를 꺼내 오는 조회 계층.

지금까지의 세 조각(embedding·vector search·top-k)을 하나로 묶으면 retrieval이다. 코드에서는 search()가 그 실체다 — query를 벡터화하고, 각 chunk와 cosine을 재고, 내림차순 top-k chunk 텍스트를 돌려준다.

★ 여기가 M6의 방점이다: 이 retrieval을 "도구로" 노출한다. search()를 search_docs라는 도구로 감싸(M2의 tool use) TOOLS 스키마에 등록하면 — 모델이 스스로 "지금 검색이 필요하다"고 판단해 부른다. "매 질문마다 무조건 검색"이 아니라 필요할 때만. 이게 "RAG 파이프라인"과 "RAG 에이전트"의 차이다:

  • RAG 파이프라인 — 우리 코드가 항상 검색해서 프롬프트에 넣는다(실습에서 이렇게 손으로 해 본다).
  • RAG 에이전트 — 모델이 검색 여부와 검색어를 스스로 정한다(클론에서 search_docs로 이렇게 만든다).

이제 RAG = Retrieval-Augmented Generation이 완성된다 — 찾아온 chunk를 프롬프트에 주입(augment)하고, 모델이 그 근거로 답을 생성(generation)한다. 여기에 한 겹을 더한다: grounding(근거 두기) — SYSTEM에 "검색해 온 문서에 근거해 답하고, 문서에 없으면 모른다고 하라"는 정책을 넣어 hallucination을 줄이는 것이다. Nimbus 질문엔 검색한 chunk(정답 4)를 근거로 답하고, kb/에 없는 것(예: "Nimbus 로그는 어디 쌓여?")엔 지어내지 않고 "문서에 없다"고 답하게 된다. 전체 흐름을 한 장으로 보면:

you> Nimbus에서 동시에 배포하는 서버 수 기본값이 몇이야?
      │
      │   모델: "이건 학습으로 알 수 없다" → search_docs 호출을 스스로 결정   (M3 루프)
      ▼
  [embed]    질문 → tfidf_vector(tokenize(질문), idf)        질문도 '같은 idf'로 벡터화
      ▼
  [search]   질문 벡터 vs 각 chunk 벡터 → cosine → 내림차순    (vector search)
      ▼
  top-3   1. "…max_parallel…동시 배포 서버 수…기본값 4"   점수 높음   ← 정답 chunk
          2. "…nimbus ship / --stage…"                   점수 낮음
          3. "…nimbus.toml…"                             점수 낮음
          ✗ "화요일 김치찌개…" (점심 메뉴)   cosine 0 → top-k 밖
      ▼
  [augment]  top-3 chunk를 tool_result 문자열로 회신 → 프롬프트에 주입   (retrieval 끝)
      ▼
  [generate] 모델이 그 chunk를 근거로 답: "기본값은 4입니다"    (grounding)
비유의 한계(조회 계층): 보통 조회 계층은 호출자(코드)가 "언제 무엇을 조회할지"를 정한다. 도구화한 retrieval은 그 결정을 모델에게 넘긴다 — 그래서 SYSTEM의 검색 정책은 강제가 아니라 부탁이다. 모델이 검색을 건너뛰고 지어낼 수도 있다(그때는 M5의 교훈대로 — 강제가 필요하면 코드로 막지만, 검색은 위험하지 않아 강제하지 않는다).

★ 정직한 고백 — 왜 embedding이 TF-IDF인가

여기서 이 모듈에서 가장 정직해야 할 부분을 짚는다. 우리 embedding은 신경망이 아니라 순수 파이썬 TF-IDF다. 왜?

왜 신경망 embedding이 아니라 TF-IDF인가: Anthropic API에는 embeddings 엔드포인트가 없다 — Claude는 텍스트를 벡터로 만들어 주지 않는다. 따라서 client.embeddings.create(...) 같은 코드는 존재하지 않는다(있는 줄 알고 쓰면 에러다). 그래서 M6는 embedding을 표준 라이브러리(math·re·collections)만으로 직접 만든다 — 외부 vector DB·임베딩 API·numpy/sklearn 없이. 이건 버그가 아니라 설계다. 그리고 이 결정이 오히려 더 깊은 학습을 준다 — 아래 세 가지 때문이다.
  • TF-IDF도 진짜 embedding이다. "텍스트 → 벡터, 유사도 = 벡터 거리"라는 정의를 그대로 만족한다. 다만 벡터가 어휘(단어 겹침) 기반이지 의미 기반이 아닐 뿐.
  • 파이프라인이 프로덕션과 100% 동일하다. chunk → embed → cosine top-k → 프롬프트 주입 → 생성, 그리고 search_docs 도구화·agent loop 연결 — 전부 신경망 RAG와 똑같다.
  • 바뀌는 seam은 딱 하나: embed(text) -> vector. 프로덕션은 이 함수 하나(우리의 tfidf_vector)를 신경망 임베딩 모델로 갈아끼울 뿐, 나머지 코드는 그대로다.

그래서 세 섹션이 똑같이 못 박는 한 문장은 이것이다 — "TF-IDF는 프로덕션 신경망 embedding의 자리에 끼운 순수 파이썬 대체물이고, 교체 지점은 embed 한 곳이다." 임베딩을 못 배우는 게 아니라, 임베딩을 교체 가능한 한 함수로 이해하는 것이 오히려 더 본질이다.

어휘(lexical) vs 의미(semantic) — TF-IDF는 동의어를 못 잡는다: TF-IDF 벡터의 차원은 단어 그 자체다. 그래서 "동시에"와 "한꺼번에"는 서로 다른 차원이고, 겹치는 단어가 없으면 cosine이 0이 된다. 대표 질문을 동의어로 바꿔 "Nimbus에서 한꺼번에 올리는 머신 개수 한도?"(동시에→한꺼번에, 배포→올리는, 서버→머신)라고 물으면 TF-IDF는 max_parallel chunk를 놓친다 — 사람에겐 같은 질문인데도. 이건 버그가 아니라 어휘 유사도의 본질적 한계다. 신경망 embedding은 "동시에"와 "한꺼번에"를 가까운 벡터로 두어(의미) 이걸 잡는다 — 그래서 프로덕션은 신경망 embedding을 쓴다. 업그레이드 경로는 한 줄이다: embed()만 신경망 임베딩 모델(서드파티 임베딩 API 또는 로컬 sentence-transformers 같은)로 교체, 나머지는 그대로. (실습에서 이 "놓침"을 직접 재현해 본다.)

★ memory(M4)와 RAG(M6)는 다르다

M4에서 "이건 임베딩/검색이 아니다 → M6"라고 미뤄 둔 구분을 여기서 닫는다. 둘 다 "모델에게 뭔가를 더 준다"는 점이 같아 헷갈리기 쉽지만, 방향이 반대다.

memory(M4) ≠ RAG(M6): memory는 "방금까지 무슨 대화를 했나"를 이어가는 working memory다 — history를 쌓고, 길어지면 요약·압축(compaction)한다. 핵심은 저장·요약이고, 내용은 우리가 나눈 대화다. RAG는 "내가 모르는 외부 지식"을 검색해 끌어오는 것이다 — embedding·유사도로 문서를 찾아 주입한다. 핵심은 검색·주입이고, 내용은 대화 밖의 문서다. 둘은 대체재가 아니라 보완재다 — memory는 대화를 잇고, RAG는 사실을 끌어온다.

그리고 둘은 실제로 만난다 — 검색해 온 chunk는 tool_result로 history에 쌓여 context window를 먹고, 대화가 길어지면 M4의 compaction이 그 오래된 chunk를 접는다. 즉 RAG 결과는 영속 지식이 아니라 그때그때의 소모성 컨텍스트다. (kb 문서 자체는 파일로 남지만, 한 번 검색해 넣은 chunk는 대화가 흘러가면 사라진다 — 필요하면 또 검색한다.)

새 능력 = 새 도구 — 루프는 그대로

이제 이 모듈의 클라이맥스다. RAG라는 큰 능력을 붙였는데 — agent.py는 한 줄도 안 바뀐다. 왜냐하면 search_docs는 그냥 하나의 도구이기 때문이다. 모델이 부르면 M2의 tool_use↔tool_result 왕복과 M3의 while 루프가 이미 다 처리한다. 위험하지 않으니(읽기 전용) M5의 승인 게이트도 그냥 통과하고, update_plan이 아니니 else: run_tool 경로로 흐른다 — read_file과 똑같은 길이다.

# (M5 agent.py — 한 줄도 안 바뀐다) search_docs 호출은 이 '기존' 경로로 흐른다:
if block.name in DANGEROUS_TOOLS and not confirm(...):   # search_docs ∉ DANGEROUS_TOOLS → 게이트 건너뜀
    ...
if block.name == "update_plan":                          # search_docs ≠ update_plan → else 로

else:
    result = run_tool(block.name, block.input)           # ← search_docs 가 여기 (read_file 과 같은 길)

그럼 이 새 도구를 어디에 둘지, 실행 전에 물을지는 어떻게 정했나? M5의 두 질문이 그대로 답을 준다. ① 바깥이냐 자신이냐 → search_docs는 바깥 지식(kb/ 문서)을 조회한다(read_file과 같은 부류) → tools.py + run_tool에 둔다(self.plan을 건드리던 update_plan과는 정반대). ② 되돌릴 수 있느냐 → 읽기 전용이라 되돌릴 게 없다 → DANGEROUS_TOOLS에 넣지 않는다(승인 게이트 없음). M5에서 세운 기준이 새 도구에 그대로 적용된다.

왜 큰 능력을 붙였는데 루프는 그대로인가: M3에서 agent loop를 제대로 만든 뒤로, 새 능력을 붙이는 방법은 "루프를 고치는 것"이 아니라 "도구를 더하는 것"이었다. M2 read_file, M3 write_file/run_bash, M5 update_plan, 그리고 M6 search_docs — 루프는 고정, 도구만 쌓였다. 비유하면 잘 설계된 플러그인 아키텍처 — 코어(loop)는 그대로, 기능은 플러그인(도구)으로 얹는다. 이것이 M7(통합)의 전제다: 통합이란 "새 코드를 합치는 것"이 아니라 "이미 다 되는 루프에 도구들을 모아 두는 것"이다.
비유의 한계(플러그인) + 한 가지 미묘함: 플러그인은 코어가 명시적으로 등록·호출하지만, 도구는 모델이 확률적으로 고른다 — 그래서 "검색해라"가 강제가 아니라 부탁인 것이다. 그리고 미묘한 점 하나 — ReAct(M3)의 눈으로 보면 search_docs는 "관찰(observation)을 스스로 만들어 오는" 도구다: 모델이 추론("이건 모른다") → 행동(search_docs 호출) → 관찰(chunk를 tool_result로 받음) → 그 근거로 생성. RAG가 agent loop에 이토록 자연스럽게 맞아 드는 이유가 바로 이것이다.

한눈 정리

  • 왜 RAG인가. 모델은 stateless + 학습 cutoff(M1)라 자기 밖의 지식(로컬·사설·최신)을 모르고, 모르면 지어낸다(hallucination). 해법은 재학습이 아니라 관련 텍스트를 찾아 프롬프트에 넣어 주기 — LLM판 "외부 조회 후 응답".
  • 파이프라인은 다섯 조각. 문서를 chunk로 쪼개(chunk_text) → 각 chunk를 embedding(tfidf_vector)으로 → 질문도 같은 idf로 벡터화해 vector search(cosine top-k)로 검색 → 이 검색 행위가 retrieval(search) → chunk를 주입해 생성. chunk화·embedding·검색엔 API 호출이 0이다.
  • ★ TF-IDF도 진짜 embedding이다 — 다만 어휘(lexical)지 의미(semantic)가 아니다. Anthropic엔 임베딩 API가 없어 순수 파이썬 TF-IDF를 직접 만든다(설계, 버그 아님). 파이프라인은 프로덕션과 동일, 바뀌는 seam은 embed 한 곳뿐. 동의어를 못 잡는 게 어휘 유사도의 한계이자 프로덕션이 신경망 embedding을 쓰는 이유다.
  • retrieval을 도구로 노출하면 "RAG 에이전트"가 된다. search_docs로 감싸면 모델이 스스로 검색 시점을 정한다("항상"이 아니라 "필요하면"). grounding(SYSTEM 정책)으로 문서에 있으면 근거로 답하고, 없으면 "모른다"고 하게 한다 — 단 이건 부탁이다.
  • memory(M4) ≠ RAG(M6). memory는 대화를 잇고(저장·요약), RAG는 외부 사실을 끌어온다(검색·주입). 보완재다. 검색해 온 chunk는 tool_result로 history에 쌓여 길어지면 M4 compaction이 접는 소모성 컨텍스트다.
  • ★ 새 능력 = 새 도구 — agent.py는 무변경. search_docs는 M3 루프·M5 게이트 분기를 그대로 통과한다(read_file과 같은 길). 배치·게이트는 M5의 두 질문(바깥이냐 자신이냐 / 되돌릴 수 있느냐)이 답한다. 범위 = RAG 파이프라인 + 도구화까지 — 신경망 embedding·vector DB·재순위는 포인터, 세 flavor 통합·eval·trace 로깅은 M7.

def tokenize(text):
    """소문자화 + 한글/영문/숫자 단어만 추출. query와 chunk를 '같은 규칙'으로 쪼개야
    같은 벡터 공간에 놓인다 → 그래서 이 함수를 양쪽에서 공용한다."""
    return re.findall(r"[가-힣a-zA-Z0-9_]+", text.lower())


def chunk_text(text, max_chars=500):
    """문서를 검색·임베딩의 단위 chunk로 쪼갠다. 문단(빈 줄) 기준으로 나누고, 너무 길면 max_chars로 자른다.
    (여기 DOCS는 짧아 대개 1문서 = 1chunk. 클론에선 같은 함수로 .md 파일을 쪼갠다.)"""
    chunks = []
    for para in re.split(r"\n\s*\n", text):
        para = para.strip()
        if not para:
            continue
        if len(para) <= max_chars:
            chunks.append(para)
        else:                                    # 너무 길면 고정 길이로 더 자른다
            for i in range(0, len(para), max_chars):
                chunks.append(para[i:i + max_chars])
    return chunks


def compute_idf(chunk_token_lists):
    """코퍼스 전체의 IDF. ★ smoothed 공식: log((N+1)/(df+1)) + 1.
    평범한 log(N/df)는 '모든 chunk에 있는 단어'의 idf를 0으로 만들어(→ 벡터가 죽는다),
    문서 수가 적은 작은 코퍼스에서 특히 위험하다. +1 smoothing이 그걸 막는다."""
    N = len(chunk_token_lists)
    df = Counter()
    for tokens in chunk_token_lists:
        for t in set(tokens):                    # 한 chunk에서 같은 단어는 한 번만(document frequency)
            df[t] += 1
    return {t: math.log((N + 1) / (df_t + 1)) + 1 for t, df_t in df.items()}


def tfidf_vector(tokens, idf):
    """★ 우리의 embedding — 토큰을 {단어: TF-IDF 가중치} 스파스 벡터(dict)로 만든다.
    query도 반드시 '코퍼스에서 만든 같은 idf'로 벡터화해야 같은 공간에 놓인다."""
    tf = Counter(tokens)
    n = len(tokens) or 1                          # 빈 입력의 0으로 나누기 방지
    return {t: tf[t] / n * idf.get(t, 0.0) for t in tf}


def cosine(a, b):
    """두 스파스 벡터의 코사인 유사도. 방향(각도)만 보므로 문서 길이에 안 휘둘린다.
    ★ 0-norm 가드 필수 — 겹치는 단어가 하나도 없으면 norm=0 → ZeroDivisionError."""
    dot = sum(w * b.get(t, 0.0) for t, w in a.items())
    na = math.sqrt(sum(w * w for w in a.values()))
    nb = math.sqrt(sum(w * w for w in b.values()))
    return dot / (na * nb) if na and nb else 0.0


# ── 색인(index) 만들기: DOCS → chunk → idf → 각 chunk의 embedding 벡터 ──
chunks = []
for doc in DOCS:
    chunks.extend(chunk_text(doc))
token_lists = [tokenize(c) for c in chunks]
idf = compute_idf(token_lists)                    # 코퍼스 전체에서 idf를 '한 번만' 구한다
vectors = [tfidf_vector(toks, idf) for toks in token_lists]


def search(query, k=TOP_K):
    """retrieval의 실체 — query를 '같은 idf'로 벡터화해 각 chunk와 cosine을 재고,
    높은 순으로 (점수, chunk) 상위 k개를 돌려준다."""
    qv = tfidf_vector(tokenize(query), idf)
    scored = [(cosine(qv, v), c) for v, c in zip(vectors, chunks)]
    scored.sort(key=lambda pair: pair[0], reverse=True)
    return scored[:k]


# ── 데모: 대표 질문으로 검색 (★ step2·step3에서는 이 아래만 바꾼다) ────────────
question = "Nimbus에서 동시에 배포하는 서버 수 기본값이 몇이야?"
print(f"문서 {len(DOCS)}개 → chunk {len(chunks)}개, 어휘(고유 단어) {len(idf)}개")
print(f"질문: {question}\n")
for rank, (score, chunk) in enumerate(search(question, k=len(chunks)), 1):   # k=전체 → 전 문서 점수를 본다
    cut = " ← top-k 안" if rank <= TOP_K else " ← top-k 밖"
    print(f"[{rank}] score={score:.3f}  {chunk[:34]}...{cut}")

어휘 검색을 "성공"시키는 법: 겹치는 단어를 쓰면 된다 — synonym을 "Nimbus 동시에 배포하는 서버 수 한도?"처럼 정답 chunk의 단어(동시에·배포·서버)를 넣어 다시 실행해 보라. 점수가 0에서 살아나 max_parallel chunk가 다시 top-1으로 올라온다. 검색이 "뜻"이 아니라 "단어"에 반응한다는 걸 손으로 확인하는 순간이다.
더 실험해 보기(각 1분).
  • TOP_K = 1 또는 TOP_K = 5로 바꿔 step1을 돌려 보라 → search가 돌려주는 결과 수가 바뀐다(← top-k 경계가 이동). RAG에서 "몇 개를 근거로 넣을까"를 정하는 다이얼이다(너무 많으면 노이즈·토큰↑, 너무 적으면 정답을 놓칠 위험).
  • DOCS에 문서를 더 넣어 보라(예: "Nimbus 대시보드는 nimbus web 으로 연다."). 어휘가 늘면 idf·점수가 바뀐다 — 노이즈를 늘려도 정답이 여전히 top-1인지 확인.
  • chunk_text(text, max_chars=20)처럼 max_chars를 아주 작게 주면 한 문장이 여러 chunk로 쪼개진다 → chunk가 너무 작으면 맥락이 끊겨 검색이 나빠지는 걸 관찰(chunk 크기 트레이드오프).
  • cosine의 if na and nb else 0.0을 dot / (na * nb)로 바꾸고 동의어 질문(step3)을 돌리면? → 겹치는 단어 0이라 norm이 0 → ZeroDivisionError. 0-norm 가드가 왜 필요한지 몸으로 확인하고 되돌린다.
막히면:
  • ZeroDivisionError (cosine에서) → 질문이 어떤 chunk와도 겹치는 단어가 하나도 없어 norm이 0이 됐다. cosine의 0-norm 가드(return dot / (na * nb) if na and nb else 0.0)가 빠졌거나 잘못됐다. 겹침 0이면 유사도 0을 돌려줘야 한다.
  • 모든 점수가 이상하다 / 검색이 무의미하다 → compute_idf에 평범한 log(N/df)를 썼다. 문서 몇 개짜리 작은 코퍼스에선 모든 chunk에 있는 단어의 idf가 0이 되어 벡터가 죽는다. smoothed log((N+1)/(df+1))+1을 쓴다.
  • 동의어로 물으니 못 찾는다(step3) → 버그가 아니다. TF-IDF는 어휘 유사도라 "동시에"≠"한꺼번에"다(설계). 겹치는 단어로 묻거나, (프로덕션) 신경망 embedding으로 embed를 교체한다.
  • AttributeError: module 'anthropic' has no attribute 'embeddings' / client.embeddings…가 없다 → 그런 API는 존재하지 않는다. Anthropic은 임베딩 엔드포인트를 제공하지 않는다 — 임베딩은 tfidf_vector(순수 파이썬)가 전부다. Claude는 (b)의 생성에만 쓴다.
  • AuthenticationError (401) → step2에서 ANTHROPIC_API_KEY가 없다/오타. echo $ANTHROPIC_API_KEY로 확인. step1·step3은 API를 안 부르니 키 없이도 된다 — 검색만 확인하려면 이 둘부터.

# hermes/rag.py  (이어서)

def tokenize(text: str) -> list:
    """소문자화 + 한글/영문/숫자 단어만 추출. query와 chunk가 '같은 규칙'으로 쪼개져야
    같은 벡터 공간에 놓인다 — 그래서 이 함수 하나를 양쪽에서 공용한다."""
    return re.findall(r"[가-힣a-zA-Z0-9_]+", text.lower())


def chunk_text(text: str, max_chars: int = 500) -> list:
    """문서를 검색·임베딩의 단위인 chunk로 쪼갠다. 문단(빈 줄) 기준으로 나누고,
    한 문단이 너무 길면 max_chars로 잘라 여러 chunk로 만든다.
    (chunk가 너무 크면 유사도가 희석되고, 너무 작으면 맥락이 끊긴다 — 여기선 단순한 문단 방식.)"""
    chunks = []
    for para in re.split(r"\n\s*\n", text):     # 빈 줄로 문단 분리
        para = para.strip()
        if not para:
            continue
        if len(para) <= max_chars:
            chunks.append(para)
        else:                                    # 너무 길면 고정 길이로 더 자른다
            for i in range(0, len(para), max_chars):
                chunks.append(para[i:i + max_chars])
    return chunks

지금 무엇을/왜: 이 모듈의 개념 축이다. compute_idf(코퍼스 IDF) → tfidf_vector(우리 embedding) → cosine(vector search의 거리 함수). 세 함수가 텍스트 → 벡터 → 유사도를 완성한다.

# hermes/rag.py  (이어서)

def compute_idf(chunk_token_lists: list) -> dict:
    """코퍼스 전체의 IDF(역문서빈도)를 계산한다. ★ smoothed 공식:
        idf(t) = log((N+1) / (df(t)+1)) + 1
    ⚠ 평범한 log(N/df)는 '모든 chunk에 있는 단어'의 idf를 0으로 만들어(→ 벡터가 죽는다),
       문서 수가 적은 작은 코퍼스에서 특히 위험하다. +1 smoothing이 그걸 막는다."""
    N = len(chunk_token_lists)
    df = Counter()
    for tokens in chunk_token_lists:
        for t in set(tokens):                    # 한 chunk에서 같은 단어는 한 번만(document frequency)
            df[t] += 1
    return {t: math.log((N + 1) / (df_t + 1)) + 1 for t, df_t in df.items()}


def tfidf_vector(tokens: list, idf: dict) -> dict:
    """★ 우리의 embedding — 토큰 리스트를 {단어: TF-IDF 가중치} 스파스 벡터(dict)로 만든다.
    query도 반드시 '코퍼스에서 만든 같은 idf'로 벡터화해야 같은 공간에 놓인다."""
    tf = Counter(tokens)
    n = len(tokens) or 1                          # 빈 입력의 0으로 나누기 방지
    return {t: tf[t] / n * idf.get(t, 0.0) for t in tf}


def cosine(a: dict, b: dict) -> float:
    """두 스파스 벡터(dict)의 코사인 유사도. 방향(각도)만 보므로 문서 길이에 안 휘둘린다."""
    dot = sum(w * b.get(t, 0.0) for t, w in a.items())
    na = math.sqrt(sum(w * w for w in a.values()))
    nb = math.sqrt(sum(w * w for w in b.values()))
    return dot / (na * nb) if na and nb else 0.0  # ★ 0-norm 가드: 겹치는 단어 0이면 ZeroDivisionError
두 곳의 함정을 미리 막았다: ① smoothed idf — 평범한 log(N/df)는 모든 chunk에 있는 단어의 idf를 0으로 만든다. 문서 몇 개짜리 작은 코퍼스에선 흔한 단어가 많아 벡터가 통째로 죽을 수 있다. log((N+1)/(df+1))+1은 최소 1 이상을 보장한다. ② 0-norm 가드 — query가 어떤 chunk와도 겹치는 단어가 하나도 없으면 norm이 0이라 dot/(na*nb)가 ZeroDivisionError다. if na and nb else 0.0이 그때 유사도 0을 돌려준다(= 안 겹침).
개념↔코드: 개념 embedding = tfidf_vector()(우리 embedding의 실체). 개념 vector search의 거리 계산 = cosine(). 실습의 다섯 함수와 이름·수식이 100% 동일하다 — 실습에서 점수를 눈으로 본 그 cosine이 바로 이거다.

# hermes/rag.py  (이어서)

class DocIndex:
    """색인(상태)을 소유하는 클래스 — M4의 class Memory와 같은 계보다.
    build로 폴더를 읽어 chunk 벡터들과 idf를 들고 있고, search로 질의에 답한다."""

    def __init__(self):
        self.chunks = []      # chunk 원문(list[str]) — 검색 결과로 이걸 돌려준다
        self.vectors = []     # 각 chunk의 embedding(list[dict]) — chunks와 같은 순서
        self.idf = {}         # 코퍼스 idf — query 벡터화에도 '같은' 걸 쓴다

    def build(self, folder: str) -> "DocIndex":
        """folder의 .md 파일들을 읽어 chunk → idf → chunk 벡터로 색인한다."""
        self.chunks = []
        for path in sorted(glob.glob(os.path.join(folder, "*.md"))):
            with open(path, "r", encoding="utf-8") as f:
                self.chunks.extend(chunk_text(f.read()))
        token_lists = [tokenize(c) for c in self.chunks]
        self.idf = compute_idf(token_lists)
        self.vectors = [tfidf_vector(toks, self.idf) for toks in token_lists]
        return self           # build().search() 로 이어 쓸 수 있게 self 반환

    def search(self, query: str, k: int = TOP_K) -> list:
        """★ retrieval의 실체 — query를 '같은 idf'로 벡터화해 각 chunk와 cosine을 재고,
        높은 순으로 상위 k개 chunk 텍스트를 반환한다(점수 0=전혀 안 겹침은 버린다)."""
        qv = tfidf_vector(tokenize(query), self.idf)
        scored = [(cosine(qv, v), c) for v, c in zip(self.vectors, self.chunks)]
        scored.sort(key=lambda pair: pair[0], reverse=True)
        return [c for score, c in scored[:k] if score > 0]
핵심 한 줄 — query도 self.idf로 벡터화한다: chunk를 색인할 때 쓴 바로 그 idf로 query도 tfidf_vector한다. 그래야 둘이 같은 벡터 공간에 놓여 cosine이 의미를 갖는다. 그리고 점수 0인 chunk는 버린다 (if score > 0) — 전혀 안 겹치는 문서를 top-k 채우기용으로 물어오면 오히려 노이즈이고, 이게 grounding(없으면 모른다)의 토대가 된다.
