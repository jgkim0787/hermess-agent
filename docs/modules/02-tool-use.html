Tool Use (도구 사용)

개념

M1에서 우리는 LLM이 stateless하다는 것을 코드로 만들었다 — 모델은 이전 호출을 기억하지 못하고, "기억"은 우리가 messages(append-only 대화 로그)를 매 호출에 통째로 다시 보내기 때문에 생긴다. 그리고 응답이 왜 멈췄는지를 stop_reason(end_turn / max_tokens / refusal)으로 읽어 분기하는 습관도 들였다. 이번 모듈은 그 위에서 한 걸음 나아간다: 모델이 처음으로 "행동"을 요청한다. 단, 실행은 여전히 우리 코드의 몫이다.

running example은 한 줄이다 — 단일 도구 1-step 왕복: 도구 1개(get_weather)를 정의해 알려주고 → 모델이 "이 입력으로 불러 달라"고 tool_use로 요청하면 → 우리가 실행해 → 그 결과를 tool_result로 회신하고 → 모델이 그걸 보고 최종 답을 낸다. 개념·실습·클론 세 섹션이 같은 식별자(client, MODEL = "claude-sonnet-4-6", MAX_TOKENS, tools, get_weather, run_tool, messages, tool_results)를 쓴다. 개념·실습은 이 가짜 get_weather로 왕복을 눈으로 확인하고, 클론은 첫 진짜 도구 read_file로 같은 왕복을 Hermes에 얹는다.

tool use — 모델은 실행하지 못하고 "요청"만 한다

정의 — tool use: LLM이 직접 실행하지 못하는 작업을, 우리가 정의해 준 함수(도구)를 "이 입력으로 불러 달라"고 요청하게 하는 메커니즘. 요청은 모델이, 실행은 우리가 한다.

익숙한 그림으로 옮기면, tool use는 모델이 우리에게 내는 RPC 요청이다. 모델은 파일을 읽거나 날씨를 조회하는 부작용을 스스로 일으킬 수 없다. 대신 "get_weather를 location="Seoul"로 불러 줘"라는 호출 요청을 만들 뿐이고, 우리는 그 요청을 받아 서버처럼 실제로 실행한 뒤 응답을 돌려준다. 실행의 주체는 항상 우리 코드다.

비유의 한계: RPC와 달리 모델은 어떤 도구가 있는지 스스로 발견하지 못한다 — 우리가 매 호출에 tools=로 목록을 넣어 줘야만 그 도구를 부를 수 있다는 걸 안다. "요청/응답" 골격만 가져가면 된다.
표기 규약(혼동 주의): 메커니즘을 가리킬 때는 공백을 쓴 "tool use", API 응답의 블록 타입이나 stop_reason 값을 가리킬 때는 밑줄을 쓴 코드 표기 tool_use다. 마찬가지로 우리가 돌려보내는 블록 타입은 tool_result. 이 글에서 두 표기를 계속 구분한다.

도구를 알려주기 — tools 배열과 input_schema

정의 — input_schema: 도구가 받는 인자의 모양을 JSON Schema로 기술한 것 (type: "object" + properties + required). 모델은 이 스키마를 보고 인자를 어떤 타입으로 채울지 정한다.

도구의 함수 시그니처(또는 OpenAPI 파라미터 정의)라고 보면 된다. 우리가 넘기는 tools는 {name, description, input_schema} dict의 리스트이고, 모델은 이 세 가지 텍스트만 보고 "언제, 어떤 인자로" 부를지 결정한다. 그래서 description에 언제 쓰는 도구인지까지 적으면 호출 정확도가 올라간다.

# cheatsheet "Tool Use — 도구 정의" 그대로. 도구 1개(get_weather).
tools = [
    {
        "name": "get_weather",
        "description": "특정 도시의 현재 날씨를 반환한다.",
        "input_schema": {
            "type": "object",
            "properties": {
                "location": {"type": "string", "description": "도시 이름, 예: Seoul"}
            },
            "required": ["location"],
        },
    }
]
정의 — tool_use 블록: 모델 응답 resp.content 안에 담겨 오는 블록 (block.type == "tool_use"). .id · .name(도구 이름) · .input(인자 dict)을 가진 구조화된 도구 호출 요청이다. 역직렬화된 RPC 호출 객체(메서드명 + 인자)라고 보면 된다.

도구 왕복 4단계

도구를 알려준 뒤 한 번의 도구 사용은 아래 4단계로 흐른다. 핵심은 이 왕복이 messages.create를 두 번 부른다는 것(요청받기 → 결과 주고 최종답 받기), 그리고 그 사이 실행은 우리가 한다는 것이다.

[호스트 = 우리 코드]                          [Claude API = 무상태]

create 1 → messages = [질문] + tools 전송
     ← 응답: stop_reason == "tool_use",  resp.content 에 tool_use 블록
              뜻: "get_weather 를 이 입력으로 불러 달라" (모델은 요청만)

실행     → run_tool("get_weather", {"location": "서울"})  →  "서울: 맑음, 23도"
              (실행은 우리 코드. 모델은 직접 실행하지 못한다.)

회신     → messages 에 append:  assistant = resp.content (tool_use 블록 통째로)
                               user = [ tool_result ]  (같은 tool_use_id)

create 2 → 전체 messages 재전송  (원 질문 + tool_use + tool_result)
     ← 응답: stop_reason == "end_turn"  →  "서울은 지금 맑고 23도예요"
정의 — stop_reason == "tool_use"(M1 연결): M1의 stop_reason 값 집합 (end_turn/max_tokens/refusal)에 새로 추가되는 값. "도구를 부르고 싶어서 멈췄다"는 신호다 — 이 값을 보고 우리가 도구를 실행·회신한다.

① 멈춤: tools=를 넘겨 호출하면, 모델이 도구를 쓰고 싶을 때 stop_reason == "tool_use"로 멈추고 resp.content에 tool_use 블록을 담아 온다. 함수 반환의 exit code에 분기 하나가 새로 생긴 셈이다. ② 실행: 그 블록의 .name·.input을 꺼내 우리가 실제 함수를 부른다. 도구 이름으로 실제 함수를 부르는 디스패처 run_tool(name, tool_input)은 결과를 반드시 문자열로 돌려준다(그대로 회신에 실린다).

def get_weather(location: str) -> str:          # 가짜: 네트워크 없이 하드코딩 반환
    return f"{location}: 맑음, 23도"

def run_tool(name: str, tool_input: dict) -> str:   # 이름 → 실제 함수 (디스패처)
    if name == "get_weather":
        return get_weather(**tool_input)   # tool_input 예: {"location": "서울"}
    raise ValueError(f"unknown tool: {name}")
정의 — tool_result 블록: 우리가 도구를 실행한 뒤 모델에게 돌려주는 블록 — {"type": "tool_result", "tool_use_id": ..., "content": "결과 문자열"}. 이걸 user 메시지의 content로 담아 보낸다 (= messages에 append되는 user 턴). RPC 응답에 요청 id를 그대로 달아 "이 호출에 대한 답"임을 표시하는 것과 같다.

③ 회신: 모델의 tool_use 응답을 통째로 assistant 턴으로 append하고, 실행 결과를 tool_result(요청과 같은 tool_use_id)에 담아 user 턴으로 append한다. ④ 최종답: 이 messages를 다시 보내면 모델이 결과를 읽고 end_turn으로 최종 답을 낸다. 아래 코드는 이 왕복을 if 하나로 펼친 것이다(도구 스텝 하나).

messages = [{"role": "user", "content": "서울 날씨 어때?"}]

# ── create ① : 질문 + tools 를 보낸다 ───────────────────────────
resp = client.messages.create(
    model=MODEL, max_tokens=MAX_TOKENS,
    tools=tools, messages=messages,          # tools 를 넘겨야 모델이 도구 존재를 안다
)

if resp.stop_reason == "tool_use":           # 도구를 부르고 싶어서 멈췄다
    # ② assistant 응답(tool_use 블록 포함)을 통째로 history 에 append
    messages.append({"role": "assistant", "content": resp.content})

    # ③ tool_use 블록마다 우리가 실행 → tool_result 로 수집
    tool_results = []
    for block in resp.content:
        if block.type == "tool_use":                     # block.name / .input / .id
            result = run_tool(block.name, block.input)    # 실행은 우리 코드가
            tool_results.append({
                "type": "tool_result",
                "tool_use_id": block.id,   # tool_use 의 id 를 그대로 (매칭)
                "content": result,          # 반드시 문자열
            })
    messages.append({"role": "user", "content": tool_results})   # 결과는 user 턴

    # ④ create ② : 원 질문 + tool_use + tool_result 가 담긴 messages 를 다시 전송
    resp = client.messages.create(
        model=MODEL, max_tokens=MAX_TOKENS,
        tools=tools, messages=messages,
    )                                        # 이번엔 stop_reason == "end_turn"

final_text = next(b.text for b in resp.content if b.type == "text")
print(final_text)   # 예: "서울은 지금 맑고 기온은 23도예요."
★ 왜 create를 두 번 부르고, 두 번째에 전체 messages를 다시 보내나 — M1 stateless의 연장: 첫 호출로 받은 tool_use(assistant 턴)와 우리가 만든 tool_result(user 턴)는 결국 messages에 append되는 두 개의 턴일 뿐, 새 자료구조가 아니다. 그리고 API는 무상태이므로, 모델이 "원래 무엇을 물었고 / 무엇을 부르려 했고 / 그 결과가 무엇인지"를 알려면 이 세 가지가 모두 담긴 messages를 두 번째 호출에 통째로 다시 보내야 한다. M1에서 "내 이름?"을 기억시킨 원리와 정확히 같다.
1-step ≠ API 호출 1회: "1-step"은 도구 실행 스텝 하나를 뜻한다. 그 한 스텝을 완성하는 데 messages.create는 위처럼 두 번 필요하다(요청 받기 → 결과 주고 최종답 받기).

tool_use_id — 요청과 응답을 잇는 correlation id

정의 — tool_use_id: 각 tool_use 블록의 고유 id. 우리가 보내는 tool_result에 같은 값을 달아, 어느 요청에 대한 결과인지 매칭한다. 비동기 RPC의 correlation id와 같은 역할이다.

모델이 낸 각 tool_use에는 정확히 하나의 tool_result를 같은 id로 달아 답해야 한다. id가 빠지거나 어긋나면 다음 호출이 400이다.

여기서 400이 잘 난다: ① tool_result를 빠뜨리거나 tool_use_id가 안 맞음 → "요청에 답이 없다"며 400. ② assistant의 resp.content를 통째로 append하지 않고 텍스트만 넣으면 tool_use 블록이 유실돼 400. ③ 두 번째 호출에 tools=를 안 넘기면 모델이 도구를 모른다. (M1 교훈 재활용 — SDK 400은 값보다 필드 이름·id 매칭부터 확인한다.)
다른 provider(예: OpenAI)의 "function calling"도 같은 개념이다 — 블록 이름과 필드 표기만 다를 뿐, "모델은 요청, 실행은 우리, 결과를 history에 회신"이라는 골격은 동일하다.

한눈 정리

  • tool use = 모델은 도구를 직접 실행하지 못하고 "이 입력으로 불러 달라"고 요청만 한다(RPC 요청). 실행은 우리 코드.
  • 도구 알려주기 = tools 배열로 넘기고, 각 도구의 인자 모양은 input_schema(JSON Schema = 함수 시그니처)로 기술.
  • 왕복 4단계 = ① stop_reason == "tool_use"로 멈추고 resp.content에 tool_use 블록 → ② 우리가 run_tool 실행 → ③ tool_result(같은 tool_use_id)를 user 메시지로 회신 → ④ 최종 답(end_turn).
  • ★ 1-step 왕복 = create 두 번. tool_use(assistant 턴) · tool_result(user 턴) 모두 messages에 append → M1 stateless 그대로(두 번째 호출에 전체 history 재전송).
  • tool_use_id = 요청/응답 correlation id. 빠지거나 어긋나면 다음 호출 400.
  • 범위 = 여기까지는 단일 도구 1-step 하나. 여러 도구를 연쇄하거나 결과를 보고 또 부르려면 while 루프가 필요하다 → M3 "The Agent Loop"에서 위 if가 while이 된다.

1) 도구 정의 — 명세와 실제 함수를 나눠 만든다 (키 불필요)

도구는 두 조각이다. 모델이 읽는 명세(tools — 이름·설명·input_schema)와, 우리가 실제로 부르는 함수(get_weather). 모델은 명세만 보고 "불러 달라"고 요청할 뿐 실행은 못 한다. 여기선 get_weather를 가짜로(네트워크 없이 하드코딩) 만들어, API 없이 도구가 도는지 먼저 확인한다.

# step1.py — 도구 "명세"와 "실제 함수"를 나눠 만든다 (API 호출 없음 → 키 불필요)

# 1) 모델에게 알려줄 도구 "명세": 이름 + 설명 + 인자 모양(input_schema, JSON Schema)
tools = [
    {
        "name": "get_weather",
        "description": "특정 도시의 현재 날씨를 반환한다.",
        "input_schema": {
            "type": "object",
            "properties": {
                "location": {"type": "string", "description": "도시 이름, 예: Seoul"},
            },
            "required": ["location"],
        },
    }
]

# 2) 실제로 실행되는 우리 쪽 함수 (가짜 구현: 네트워크 없이 하드코딩 문자열 반환)
def get_weather(location: str) -> str:
    return f"{location}: 맑음, 23도"

# 3) 도구 이름으로 실제 함수를 찾아 부르는 디스패처. 반환은 반드시 문자열.
def run_tool(name: str, tool_input: dict) -> str:
    if name == "get_weather":
        return get_weather(**tool_input)
    return f"알 수 없는 도구: {name}"

# API 없이 로컬에서 도구가 도는지 먼저 확인한다
print(run_tool("get_weather", {"location": "Seoul"}))
uv run python practice/02-tool-use/step1.py
Seoul: 맑음, 23도
input_schema는 JSON Schema로 쓴 함수 시그니처다 — 최상위 "type": "object" + properties + required. 모델은 이걸 보고 인자를 어떤 타입으로 채울지 정한다. run_tool은 도구 이름을 실제 함수로 잇는 디스패처(RPC 메서드 라우팅 analogy). 도구가 하나뿐이라 지금은 과해 보이지만, tools·run_tool이라는 이 뼈대가 그대로 Hermes로 이어진다.

2) 1차 호출 — 모델의 tool_use 요청을 눈으로 확인

이제 질문과 tools를 함께 보낸다. 모델은 날씨를 직접 못 구하니, "get_weather를 이 입력으로 불러 달라"는 tool_use 블록을 응답에 담고 stop_reason을 "tool_use"로 멈춘다. 아직 실행하지 않고, 응답 구조만 print해 관찰한다.

# step2.py — 질문 + tools 를 보내고, 모델이 돌려준 tool_use "요청"을 눈으로 본다
import anthropic

client = anthropic.Anthropic()          # ANTHROPIC_API_KEY 환경변수 자동 사용
MODEL = "claude-sonnet-4-6"
MAX_TOKENS = 512

tools = [
    {
        "name": "get_weather",

왜 tool_use에서 멈췄나? M1에서 stop_reason은 end_turn/max_tokens/refusal이었다. 도구를 주자 새 값 tool_use가 추가됐다 — "답을 마친 게 아니라, 도구를 불러 달라고 요청하며 멈췄다"는 신호다. 아직 우리는 실행하지 않았다. 다음 step에서 실행해 결과를 돌려주면, 그제야 모델이 최종 답을 낸다.

3) 실행 + 회신 — tool_result를 돌려주고 최종 답 받기

step2에서 받은 tool_use 요청을 실제로 실행하고(run_tool), 결과를 tool_result 블록에 담아 user 메시지로 history에 append한다. 그리고 결과가 담긴 messages 전체를 다시 보낸다(2차 호출). 그러면 모델이 결과를 보고 최종 답(end_turn)을 낸다. 이게 도구 1-step 왕복 전체다.

# step3.py — 도구 1-step 왕복 전체: 요청 → 실행 → tool_result 회신 → 최종 답
import anthropic

client = anthropic.Anthropic()
MODEL = "claude-sonnet-4-6"
MAX_TOKENS = 512

tools = [
    {
        "name": "get_weather",
        "description": "특정 도시의 현재 날씨를 반환한다.",
        "input_schema": {
            "type": "object",
            "properties": {
                "location": {"type": "string", "description": "도시 이름, 예: Seoul"},
            },
            "required": ["location"],
        },
    }
]

def get_weather(location: str) -> str:
    return f"{location}: 맑음, 23도"         # 가짜 구현 (네트워크 없음)

def run_tool(name: str, tool_input: dict) -> str:
    if name == "get_weather":
        return get_weather(**tool_input)
    return f"알 수 없는 도구: {name}"

messages = [{"role": "user", "content": "서울 날씨 어때?"}]

# --- 1차 호출: 모델이 tool_use 를 요청한다 ---
resp = client.messages.create(
    model=MODEL, max_tokens=MAX_TOKENS, tools=tools, messages=messages,
)
print("1차 stop_reason:", resp.stop_reason)      # tool_use 기대

# 모델 응답(assistant 턴)을 통째로 history 에 append — tool_use 블록을 보존해야 한다
messages.append({"role": "assistant", "content": resp.content})

# tool_use 블록마다 실제로 실행하고, 같은 id 로 tool_result 를 만든다
tool_results = []
for block in resp.content:
    if block.type == "tool_use":
        result = run_tool(block.name, block.input)   # 우리가 실제로 실행
        print("도구 실행 결과:", result)              # 모델에게 돌려줄 값
        tool_results.append({
            "type": "tool_result",
            "tool_use_id": block.id,                 # ★ 요청 id 와 반드시 매칭
            "content": result,                       # 문자열
        })

# 도구 결과를 user 메시지로 회신 (history 에 append)
messages.append({"role": "user", "content": tool_results})

# --- 2차 호출: 결과가 담긴 history 전체를 다시 보낸다 (stateless) ---
resp2 = client.messages.create(
    model=MODEL, max_tokens=MAX_TOKENS, tools=tools, messages=messages,
)
print("2차 stop_reason:", resp2.stop_reason)     # 이번엔 end_turn 기대

final = "".join(b.text for b in resp2.content if b.type == "text")
print("최종 답변:", final)

2차 호출에 왜 messages를 통째로 또 보내나? M1의 stateless 그대로다. "원 질문 + 모델의 tool_use + 우리의 tool_result"가 모두 담긴 messages를 다시 보내야 모델이 결과를 보고 답한다. tool_use(assistant 턴)와 tool_result(user 턴)도 결국 messages에 append되는 두 개의 턴일 뿐 — 새 자료구조가 아니다. Hermes에서는 이 왕복을 tools.py + chat_with_tools로 감싼다(실습은 한 스크립트에 펼쳐 봤을 뿐). 여러 도구를 연쇄하려면 이 if를 while로 바꿔야 한다 → M3 agent loop 예고.
막히면:
  • BadRequestError(400) "tool_use ids … without tool_result" → tool_use에 답하는 tool_result가 빠졌거나 tool_use_id가 안 맞는다. tool_use 하나당 같은 id의 tool_result 하나. (M1 교훈: SDK 400은 값보다 필드 이름·id 매칭부터 본다.)
  • BadRequestError(400)인데 위 문구가 아님 → 1차 응답을 history에 넣을 때 resp.content를 통째로 append했는지 확인. block.text만 문자열로 넣으면 tool_use 블록이 유실돼 2차 호출이 깨진다. {"role":"assistant","content": resp.content} 그대로.
  • 모델이 도구를 안 부르고 그냥 말로 답함(stop_reason이 end_turn) → create(...)에 tools=tools를 안 넘겼다. 도구를 안 넘기면 모델은 도구의 존재를 모른다.
  • 최종 텍스트가 비거나 StopIteration → stop_reason을 확인하지 않고 1차 응답에서 바로 text를 뽑으려 했다. 1차엔 tool_use만 있고 text가 없을 수 있다. 최종 text는 2차(end_turn) 응답에서 뽑는다.
  • input_schema 관련 400 / 도구가 이상하게 불림 → input_schema는 JSON Schema여야 한다. 최상위 "type": "object" + properties + required. type 누락·오타가 흔하다.
  • TypeError: get_weather() got an unexpected keyword argument → 모델이 스키마에 없는 인자를 채웠거나, run_tool이 tool_input을 **로 풀 때 키가 안 맞는다. properties의 키(location)와 함수 인자 이름을 일치시킨다.
  • BadRequestError(400) "first message must use the 'user' role" → messages는 user로 시작한다. (M1과 동일.)
  • AuthenticationError(401) → ANTHROPIC_API_KEY 미설정/오타. echo $ANTHROPIC_API_KEY로 확인(step1은 API를 안 부르니 키 없이도 됨).

def read_file(path: str) -> str:
    """실제 디스크 파일을 읽어 문자열로 반환한다 (Hermes의 첫 '진짜' 도구)."""
    with open(path, "r", encoding="utf-8") as f:

지금 무엇을/왜: 모델이 우리에게 주는 건 도구 이름 문자열("read_file")과 인자 dict다. 그 이름으로 실제 함수를 찾아 부르는 디스패처가 필요하다. 반환은 반드시 문자열 — 그대로 tool_result의 content가 되기 때문. read_file 아래에 이어서 추가한다.

def run_tool(name: str, tool_input: dict) -> str:

지금 무엇을/왜: 이 함수가 이번 모듈의 핵심 — 도구 왕복 4단계를 코드로 옮긴다. 치트시트의 "수동 agent loop"에서 while을 뺀 1회분이다(도구 스텝 하나). 코드로 옮길 매핑을 먼저 보자:

  • ① 모델이 stop_reason == "tool_use"로 멈춘다 → if로 분기
  • ② 우리가 run_tool()로 실행
  • ③ 결과를 tool_result에 담아 user 메시지로 append
  • ④ messages를 통째로 다시 보내(2차 create) 최종 답변을 받는다

stream_chat 함수 아래에 추가한다. 주석의 ①~④가 위 4단계와 대응한다.

# hermes/llm.py  (stream_chat 함수 아래에 추가)
def chat_with_tools(messages: list) -> str:
    """도구를 쓸 수 있는 한 턴. 도구 1-step 왕복까지만 (while 아님 — M3의 씨앗).
    messages 에는 이미 이번 user 입력이 들어 있다고 가정하고, 이 안에서
    assistant/tool_result 턴을 append 한 뒤 최종 답변 텍스트를 반환한다."""
    # ── 1차 호출: M1과 달리 tools=TOOLS 를 함께 보낸다 (모델이 도구 존재를 알게) ──
    resp = client.messages.create(
        model=MODEL,
        max_tokens=MAX_TOKENS,
        system=SYSTEM,
        tools=TOOLS,
        messages=messages,
    )

    # ① 모델이 도구를 안 부르고 그냥 답했으면(end_turn 등) 여기서 끝 — M1의 chat 과 같은 경로.
    if resp.stop_reason != "tool_use":
        messages.append({"role": "assistant", "content": resp.content})
        return "".join(b.text for b in resp.content if b.type == "text")

    # ② 도구를 부르고 싶어 멈췄다. assistant 응답을 '통째로' history에 넣는다
    #    (tool_use 블록을 보존해야 다음 호출이 맥락을 안다).
    messages.append({"role": "assistant", "content": resp.content})

    # ③ tool_use 블록마다 실제 함수를 실행하고 결과를 tool_result 로 모은다.
    tool_results = []
    for block in resp.content:
        if block.type == "tool_use":
            result = run_tool(block.name, block.input)   # 우리가 실행
            tool_results.append({
                "type": "tool_result",
                "tool_use_id": block.id,   # 같은 id로 '이 요청에 대한 답'임을 매칭
                "content": result,          # 반드시 문자열
            })

    # ④ 도구 결과를 user 턴으로 회신한다 (history에 append — M1 stateless 그대로).
    messages.append({"role": "user", "content": tool_results})

    # ── 2차 호출: 결과가 담긴 messages를 통째로 다시 보낸다 → 이번엔 최종 답변(end_turn) ──
    resp2 = client.messages.create(
        model=MODEL,
        max_tokens=MAX_TOKENS,
        system=SYSTEM,
        tools=TOOLS,
        messages=messages,
    )
    messages.append({"role": "assistant", "content": resp2.content})
    return "".join(b.text for b in resp2.content if b.type == "text")
왜 if이고 while이 아닌가? M2는 도구 스텝 하나만 다룬다 — 도구를 한 번 부르고, 그 결과로 바로 최종 답을 받는다. 모델이 첫 도구 결과를 보고 또 도구를 부르고 싶어도 지금은 못 한다(2차 호출의 답을 그냥 반환). 이 if를 while로 바꿔 "stop_reason이 end_turn이 될 때까지 반복"하게 만드는 것이 M3의 agent loop다.
1-step ≠ API 호출 1회: 도구 1-step 왕복은 messages.create를 두 번 부른다 — ①질문+tools를 보내 tool_use를 받고(resp), ②tool_result를 붙여 다시 보내 최종 답을 받는다(resp2). 즉 도구를 한 번 쓸 때마다 과금 호출이 2회 + 파일 내용이 context에 얹힌다(그래서 read_file이 큰 파일을 잘랐다).

3) hermes/__main__.py 연결 — 도구를 쓰는 REPL

지금 무엇을/왜: M1 REPL의 stream_chat을 chat_with_tools로 갈아끼운다(도구 왕복은 비스트리밍으로 — 왕복을 또렷이 보기 위해). 중요한 차이: chat_with_tools는 assistant 응답을 함수 안에서 append한다 → 그래서 M1과 달리 REPL에서 assistant를 다시 append하지 않는다(두 번 넣으면 history가 깨진다). 파일을 아래로 통째 교체한다.

# hermes/__main__.py
from .llm import chat_with_tools

def main():
    print("Hermes REPL — 빈 입력 또는 'exit'로 종료 (이제 도구를 쓸 수 있다)\n")
    messages = []                          # append-only 대화 history (이게 곧 '기억')
    while True:
        user = input("you> ").strip()
        if user == "" or user == "exit":   # 종료 조건
            print("bye.")
            break
        messages.append({"role": "user", "content": user})   # user 턴만 여기서 append
        answer = chat_with_tools(messages)  # 도구 왕복 + assistant append 는 이 안에서 처리
        print("hermes>", answer)

if __name__ == "__main__":
    main()
