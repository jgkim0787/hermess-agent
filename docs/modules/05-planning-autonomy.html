Planning & Autonomy

개념

M3에서 우리는 class Hermes에 agent loop를 만들고, run_bash라는 도구를 쥐여 줬다. 그때 tools.py에 이런 주석을 달아 뒀다 — "⚠️ 위험 … 실행 전 사용자 승인(승인 게이트)은 M5에서 추가한다." 이번 모듈이 그 약속을 회수한다. (M4가 agent.py의 "여기가 Memory 자리" 주석을 회수했던 것과 같은 구조다.)

지금의 Hermes를 냉정하게 보면 결함이 두 개 있다.

  • 계획이 없다. 목표를 받으면 매 스텝 즉흥적으로 다음 도구를 고른다. 멀티스텝은 하지만, 그 계획은 모델의 머릿속에만 있고 우리는 무슨 일이 벌어질지 실행되기 전엔 모른다.
  • 묻지 않는다. M3의 루프는 run_tool(block.name, block.input)을 그냥 부른다. 모델이 run_bash("rm -rf …")를 한 번 내면 그대로 돈다. 손발은 다 쥐여 줬는데 브레이크가 없다.

M5는 이 둘에 각각 하나씩 붙인다 — ① update_plan(steps): 모델이 목표를 하위 단계로 쪼개 계획을 밖으로 꺼내 놓게 한다. ② 승인 게이트: 되돌리기 어려운 도구는 실행 직전에 사람에게 y/n을 묻는다. running example은 세 섹션이 공유한다 — "plan 먼저 세우고, 위험 도구는 승인 후 실행". 그리고 이 모듈의 진짜 클라이맥스는 따로 있다: 사람이 거부해도 루프가 깨지지 않는다. 왜 안 깨지는지가 M5의 핵심이다.

표기 규약(★ 세 섹션 공통): 개념·패턴은 원어/한글로 — planning/"계획", autonomy/"자율성", guardrail/"가드레일", approval gate/"승인 게이트", human-in-the-loop, "거부(deny)", "관찰(observation)". 코드·식별자·API 값은 코드 표기로 — update_plan, steps, self.plan, DANGEROUS_TOOLS, confirm(), DENIED_MSG, is_error, run_tool. 헷갈리기 쉬운 쌍을 미리 갈라 둔다 — 개념 "계획" vs 도구 update_plan vs 상태 self.plan / 개념 "승인 게이트" vs 함수 confirm() vs 집합 DANGEROUS_TOOLS / 개념 "거부" vs 필드 is_error: True.

planning — 목표를 단계로 쪼갠다

정의 — planning(계획): 에이전트가 목표를 실행 가능한 하위 단계 목록으로 분해하고, 그 계획을 명시적인 상태로 유지하는 것. 비유하면 함수 하나로 다 처리하지 않고 작업을 체크리스트/작업 큐로 쪼개 놓는 것 — 또는 코드를 짜기 전에 주석으로 단계를 먼저 적어 두는 습관.

M3~M4의 Hermes도 여러 스텝을 밟긴 했다. 차이는 계획이 어디에 있느냐다. 즉흥 실행에서는 계획이 모델의 머릿속(=그때그때의 추론)에만 있어서, 스텝이 길어질수록 방향이 흔들리고 우리는 실행 로그를 보고 사후에 무슨 일이 있었는지 짐작할 뿐이다. M5는 그 계획을 리스트 하나로 꺼내 들고 있는다.

you> 작업 폴더의 임시 로그 파일(.log)을 정리해줘
  [plan] 3단계
    1. 파일 목록 확인
    2. .log 파일 고르기
    3. 각각 삭제
  ↳ step 2: list_files({})                          ← 안전(읽기만) → 묻지 않고 자동 실행
  ↳ step 3: delete_file({'path': 'temp1.log'})
  [승인 요청] delete_file({'path': 'temp1.log'})     ← 위험(되돌릴 수 없다) → 여기서 멈춘다
  실행할까요? [y/N]

이게 M5의 running example이다. 개념·실습은 같은 소재를 쓴다 — list_files·delete_file은 부작용 0인 가짜 도구라 마음껏 y도 n도 눌러 볼 수 있다. 클론에서는 같은 골격을 진짜 run_bash·write_file로 돌려 본다.

update_plan은 마법이 아니다 (★)

여기서 대부분의 입문자가 헛짚는다. update_plan은 모델을 똑똑하게 만드는 도구가 아니다. 이 도구가 하는 일은 부작용이 하나도 없다 — 파일도 안 건드리고, 셸도 안 돌리고, 네트워크도 안 탄다. 전부 세 줄이면 끝난다.

def _update_plan(self, steps: list) -> str:
    self.plan = steps                       # ① 우리 쪽 변수에 저장한다 (에이전트 자신의 상태)
    print(f"  [plan] {len(steps)}단계")      # ② 화면에 찍는다 (우리가 본다)
    for i, s in enumerate(steps, 1):
        print(f"    {i}. {s}")
    return f"계획 저장됨: {len(steps)}단계"   # ③ 문자열을 돌려준다 (모델이 본다)
    # ⚠ 반환은 반드시 '문자열'. len(steps)(숫자)를 그대로 리턴하면 tool_result content 규칙 위반 → 400 (M2)

저장하고, 출력하고, 문자열 하나 돌려준다. 그게 전부다. 되돌릴 게 없으니 승인을 물을 이유도 없다 (그래서 DANGEROUS_TOOLS에 안 들어간다). 그런데도 효과가 있다.

왜 이 '아무것도 안 하는 도구'가 효과가 있나 — 두 가지뿐이다: ① 생각의 외부화(externalize). 모델이 계획을 말로 뱉는 행위 자체가 tool_use/tool_result로 history에 남고, 그 history는 M1의 stateless 원리대로 다음 스텝마다 다시 모델에게 전송된다. 적어 둔 계획이 계속 눈앞에 있으니 이후 스텝이 덜 흔들린다. ② 관찰 가능성. 우리가 에이전트가 뭘 하려는지 실행되기 전에 볼 수 있다. "도구가 똑똑해서"가 아니라 "생각을 밖에 적어 두면 안 흔들려서"다.
비유의 한계(체크리스트): 체크리스트는 보통 실행 엔진이 순서대로 소비하지만, self.plan은 아무도 강제로 실행하지 않는다. 그냥 파이썬 리스트다. 계획을 세웠다고 모델이 그대로 따른다는 보장은 없다 — 모델을 실제로 움직이는 건 history에 남은 update_plan 호출과 그 결과일 뿐이다. 계획 단계를 코드가 순차 실행하는 executor형 planner는 다른 설계이고 이 모듈의 범위 밖이다.

구현 위치에도 규칙이 있다. read_file·write_file·run_bash는 바깥 세상을 바꾸므로 tools.py에 산다. 반면 update_plan이 바꾸는 self.plan은 에이전트 자신의 상태다 — M4의 self.memory와 같은 부류다. 그래서 스키마(모델과의 계약)는 tools.py의 TOOLS에 두되, 핸들러는 agent.py가 직접 처리한다(run_tool 디스패처에 넣지 않는다). 이 원칙은 잠시 뒤 승인 게이트에서 다시 나온다.

autonomy — 엔진은 이미 M3에 있다

정의 — autonomy(자율성): 사람이 매 행동을 지시하지 않아도, 에이전트가 스스로 다음 행동을 정해 실행하는 정도. on/off가 아니라 다이얼이다. 비유하면 스스로 도는 데몬/크론 — 단, 이 프로세스는 다음에 무엇을 할지까지 스스로 고른다.

중요한 사실: 자율성의 엔진은 M5가 새로 만드는 게 아니다. 이미 M3의 agent loop가 그 엔진이다 — stop_reason이 tool_use인 동안 계속 돌면서 모델이 고른 도구를 실행하고 결과를 되먹인다. M5가 더하는 건 엔진이 아니라 방향(먼저 계획하라)과 한계(위험한 건 묻고 하라)다.

비유의 한계(데몬/크론): 크론은 정해진 명령을 정해진 시각에 돌린다 — 무엇을 할지 우리가 안다. agent loop는 다음 행동을 모델이 고른다 — 그래서 무엇을 할지 미리 알 수 없다. 자율성이 유용한 이유이자, 그 자율성에 가드레일이 필요한 이유다.

guardrail — 부탁이 아니라 강제

정의 — guardrail(가드레일): 에이전트가 넘지 말아야 할 경계를 코드로 강제하는 장치. 모델이 착하게 굴어 주기를 기대하는 게 아니라, 우리 코드가 막는다. 비유하면 서버 측 입력 검증 / 권한 체크 — 클라이언트를 믿지 않는 그 태도 그대로다. 여기서 클라이언트가 곧 모델이고, 우리는 서버다.

이 대비가 M5 전체를 관통한다. llm.py의 SYSTEM에 "되돌리기 어려운 도구는 사용자 승인이 필요하다"라고 적는 것은 부탁이다 — 모델은 확률적이라 안 지킬 수 있다. 반면 agent.py의 if block.name in DANGEROUS_TOOLS:는 강제다 — 모델이 무슨 생각을 하든 그 줄을 통과하지 않고는 도구가 실행되지 않는다. 경계는 프롬프트가 아니라 코드에 있어야 한다.

그럼 SYSTEM의 그 문장은 왜 쓰나: 강제가 아니라 협조를 유도하려고 쓴다 — 미리 계획을 세우게 하고, 거부당했을 때 같은 도구를 억지로 재시도하지 않게 한다. M4에서 배운 대로 system은 history 밖 슬롯이라 compaction에도 안 사라지는 항구 규칙이다. M5는 그 슬롯이 '말투'를 넘어 '행동 정책'이 되는 첫 모듈이다. 다만 정책은 부탁이고, 강제는 게이트(코드)가 한다. 둘은 역할이 다르고, 둘 다 있어야 한다.
비유의 한계(서버 검증): 서버 검증은 보통 입력의 형식을 본다. 가드레일이 보는 건 형식이 아니라 행동 — "어떤 도구를 어떤 인자로 부르려 하는가"다. 그리고 악의적인 클라이언트를 막는 게 아니라, 선의지만 확률적으로 틀리는 클라이언트를 막는다.

승인 게이트는 '루프'에 둔다

정의 — approval gate(승인 게이트) = human-in-the-loop: 되돌리기 어려운 행동을 실행하기 직전에 사람의 승인을 받는 지점. agent loop의 '행동' 단계 바로 앞에 끼운다. 비유하면 프로덕션 배포 승인 단계, rm -i, PR 머지 게이트 — 자동화 파이프라인 한가운데에 사람을 한 명 세워 두는 것.

M3의 ReAct는 추론 → 행동 → 관찰이었다. 그 '행동' 단계가 코드에서 물리적으로 존재하는 곳은 agent.py의 run_tool(block.name, block.input) 호출 바로 그 줄이다. 승인 게이트는 정확히 그 앞에 들어간다 — 개념(human-in-the-loop)과 코드(루프의 실행 직전)가 1:1로 맞는다.

DANGEROUS_TOOLS = {"delete_file"}     # 개념·실습 소재. 클론에선 {"write_file", "run_bash"}

def confirm(name: str, tool_input: dict) -> bool:
    """위험 도구 실행 '직전'에 사람에게 y/n을 묻는다."""
    print(f"  [승인 요청] {name}({tool_input})")
    try:
        answer = input("  실행할까요? [y/N] ").strip().lower()
    except EOFError:      # 파이프·CI 등 비대화형이라 물어볼 수가 없다
        return False      # → 거부. 못 물으면 안 한다 (fail-closed)
    return answer == "y"  # 기본값은 거부 — 그냥 Enter를 치면 False


# --- agent loop 안, run_tool 호출 '직전' ---
for block in resp.content:
    if block.type == "tool_use":
        if block.name in DANGEROUS_TOOLS and not confirm(block.name, block.input):
            ...           # 거부 처리 (바로 다음 절)
            continue      # 도구는 실행하지 않는다
        result = run_tool(block.name, block.input)   # 승인됐거나, 애초에 안전한 도구만 여기 온다

게이트는 도구 함수 안(tools.py)이 아니라 루프(agent.py)에 둔다. 이유가 넷이다.

  • tools.py는 "무엇을 할 수 있는가"(능력), agent.py는 "무엇을 할 것인가"(정책). 승인은 정책이다. write_file이라는 함수 자체는 승인의 존재를 알 필요가 없다.
  • 재사용·테스트 가능성. 도구 함수 안에 input()이 박히면 그 함수는 단위 테스트도 못 하고 다른 데서 못 쓴다.
  • 한 곳에서 전부 커버한다. 도구가 10개로 늘어도 게이트는 여전히 루프의 세 줄이다. run_tool 안에 넣으면 승인 코드가 도구마다 흩어진다.
  • 순서. 게이트 검사를 update_plan 분기보다 먼저 둔다. 정책 판단이 실행 분기보다 앞에 와야 나중에 도구가 늘어도 게이트를 지나쳐 실행될 일이 없다.
왜 길목 한 곳만 잠그면 에이전트 전체가 잠기나: M2에서 확인한 사실 — LLM은 직접 행동하지 못한다. 모델이 할 수 있는 건 tool_use 블록을 내는 것뿐이고, 그 블록은 예외 없이 agent loop의 저 for문을 통과해야 실제 효과가 된다. 모델에게는 우리 코드를 우회할 손발이 없다. 그래서 모든 행동이 반드시 지나가는 길목인 루프에 게이트를 걸면 전체가 걸린다. 일반화하면: "에이전트에 규칙을 걸고 싶으면 도구가 아니라 루프를 봐라." 그리고 이것이 _update_plan(상태)과 게이트(정책)가 둘 다 agent.py에 있는 이유다 — 정책·상태는 루프(agent)가 소유하고, 효과는 도구(tools)가 소유한다.

★ 거부해도 루프는 깨지지 않는다 — 거부는 '관찰'이다

사람이 n을 눌렀다. 도구는 실행하지 않는다. 그럼 모델에게는 뭐라고 말하나? "거부했으니 아무것도 안 보내면 되지" — 이게 이 모듈의 대표 함정이고, 400을 부른다.

★ 거부해도 tool_result는 반드시 회신한다: M2의 규칙 — tool_use 하나당 tool_result 하나, tool_use_id가 일치해야 하고, 짝이 빠지면 다음 messages.create가 400이다. 이 규칙은 사용자가 거부해도 그대로 유효하다. 왜냐하면 모델은 이미 tool_use 블록을 냈고, 그 assistant 응답은 이미 history에 들어갔기 때문이다. 사람이 거부한 건 도구 실행이지 모델의 요청 자체가 없던 일이 되는 게 아니다. 그러므로 거부의 올바른 처리는 "아무것도 안 하기"가 아니라 "안 하고 나서, 안 했다고 말하기"다. 
DENIED_MSG = "사용자가 이 도구 실행을 거부했습니다. 다른 방법을 찾거나 사용자에게 물어보세요."

if block.name in DANGEROUS_TOOLS and not confirm(block.name, block.input):
    print("  [거부됨] 실행하지 않고, 거부 사실을 모델에게 알립니다.")
    tool_results.append({
        "type": "tool_result",
        "tool_use_id": block.id,   # tool_use 와 반드시 매칭 (M2)
        "content": DENIED_MSG,     # 문자열! (M2 — content는 문자열)
        "is_error": True,          # 이 tool_result 가 '실패/거부'임을 알리는 필드
    })
    continue                       # 도구는 실행하지 않는다. 루프는 계속 돈다.

도구는 안 돌고, 회신은 간다. 그러면 ReAct의 관찰 자리에 "거부됨"이 들어가고, 모델은 그걸 읽고 스스로 적응한다 — 다른 방법을 시도하거나, "그럼 어떻게 할까요?"라고 되묻거나, 그 단계를 건너뛴다. 거부가 크래시가 아니라 하나의 관찰(observation)이 되는 것 — 이 한 조각이 M5의 전부다. 에이전트를 안전하게 만드는 것과 에이전트를 망가뜨리는 것은 다르다.

목표 한 줄
   ↓
[추론]   모델이 tool_use 블록을 낸다             ← M3 그대로
   ↓
[게이트]  block.name in DANGEROUS_TOOLS ?        ← M5 신규. run_tool() 호출 '직전'
   ├─ 아니오(안전) ───────────────────────────→ 묻지 않고 실행
   └─ 예(위험) → confirm() → 사람에게 [y/N]
         ├─ y       ───────────────────────→ 실행
         └─ Enter/n ───────────────────────→ 실행하지 않음
   ↓
[행동]   run_tool(...)                          ← 승인됐거나 애초에 안전한 도구만 여기 온다
   ↓
[관찰]   tool_result 를 history 에 넣는다        ← M3 그대로
         · 실행됨: 결과 문자열
         · 거부됨: DENIED_MSG + is_error: True   ← 어느 쪽이든 짝은 '반드시' 회신된다
   ↓
다음 스텝 (루프는 거부당해도 계속 돈다)
흔한 오답 3종 — 전부 틀렸다: ① 거부했으니 tool_results에 아무것도 안 넣는다 → 짝 없는 tool_use가 남아 다음 호출이 400. ② 거부했으니 루프를 break하거나 예외를 던진다 → 에이전트가 죽는다. 거부는 "이 행동만 하지 마"이지 "일 그만둬"가 아니다. ③ 거부 사실을 안 알리고 빈 문자열을 회신한다 → 모델이 성공한 줄 알고 다음 단계로 간다(더 나쁘다). 게다가 빈 content는 그 자체로 400을 낼 수 있다.
왜 DENIED_MSG가 하필 저 문구인가: 그냥 "거부됨"이라고만 보내면 모델이 같은 도구를 다시 부르며 무한 재시도할 수 있다. 그래서 관찰 안에 다음 행동 지침("다른 방법을 찾거나 사용자에게 물어보세요")까지 넣는다. 비유의 한계(에러 코드를 리턴하는 syscall): 실패한 syscall이 예외를 던지는 대신 에러 코드를 돌려주고 호출자가 그걸 보고 분기하는 것과 구조는 같다. 다만 syscall의 에러 코드는 정해진 상수지만, 여기서 돌아가는 건 모델이 읽고 해석하는 자연어 문장이다 — 그래서 문구 자체가 설계의 일부다.

자율성 ↔ 안전 — 무엇을 '위험'으로 볼 것인가

게이트를 어디에 몇 개 걸지는 트레이드오프다. 공짜 점심이 없다.

  • 승인이 너무 많으면: 사람이 매 스텝 앉아 y를 눌러야 한다 → 자율성이 죽는다 (그럴 거면 에이전트를 쓸 이유가 없다). 더 나쁜 건 승인 피로(approval fatigue) — 습관적으로 y만 누르게 되어 게이트가 유명무실해진다. 게이트가 있는데도 사고가 난다.
  • 승인이 없으면: 모델이 run_bash("rm -rf …")를 한 번 내면 그걸로 끝이다.
기준 = 되돌릴 수 있는가(irreversibility). read_file은 읽기만 하니 잘못 돌아도 되돌릴 게 없다 → 자동 실행(그래서 DANGEROUS_TOOLS에 안 들어간다). write_file은 덮어쓰고, run_bash는 뭐든 할 수 있다(삭제 포함) → 게이트. 일반화하면 파일 덮어쓰기 · 셸 실행 · 삭제 · 외부 전송(네트워크·메일·결제) = 되돌리기 어려운 행동이다. 보조 축은 영향 범위(blast radius) — 로컬 tmp 폴더냐 프로덕션 DB냐.
fail-closed — 게이트는 '거부' 쪽으로 넘어져야 한다: 그래서 프롬프트 기본값이 [y/N](대문자 N)이다 — 그냥 Enter를 치면 거부다. 비대화형 실행(파이프·CI·백그라운드)에서 input()이 EOFError를 내면 그것도 거부로 처리한다. 못 물어보면 안 하는 것이 안전한 기본값이다. (거꾸로 만들면 — 기본값 y, 에러 시 실행 — CI에서 조용히 rm이 도는 시스템이 된다.)

실무에서 자율성을 되찾는 다이얼은 더 있다 — allowlist(ls·cat처럼 안전한 명령만 자동 허용), 샌드박스(격리 환경에선 게이트 없이 자율 최대), dry-run, 작업 전 git commit(되돌릴 수 있게 만들기). 핵심은 방향이다 — 게이트를 줄이는 방법은 "덜 묻기"가 아니라 "덜 위험하게 만들기"다. M5는 그중 가장 단순한 다이얼 하나(y/n)만 구현한다.

한눈 정리

  • planning = 목표를 하위 단계로 쪼개 명시적 상태로 들고 있는 것. update_plan(steps)은 부작용 없는 '상태 기록' 도구일 뿐이다 — 저장 + 출력 + 문자열 반환이 전부. 효과는 생각의 외부화(모델이 덜 흔들린다)와 관찰 가능성(우리가 미리 본다)에서 온다. 계획을 세웠다고 실행이 보장되진 않는다.
  • autonomy의 엔진은 이미 M3의 agent loop다. M5가 더하는 건 방향(먼저 계획하라)과 한계(위험한 건 묻고 하라)뿐. 자율성은 on/off가 아니라 다이얼이다.
  • guardrail은 프롬프트가 아니라 코드다 — SYSTEM의 정책 문장은 부탁, if block.name in DANGEROUS_TOOLS는 강제. 게이트는 tools.py가 아니라 모든 행동이 반드시 지나는 길목인 agent loop에 둔다. 원칙 한 줄: 정책·상태는 루프가, 효과는 도구가 소유한다.
  • ★ 거부는 크래시가 아니라 '관찰'이다. 거부해도 tool_use 하나당 tool_result 하나는 반드시 회신한다(안 보내면 400 — M2). 도구는 안 돌리고 is_error: True + DENIED_MSG를 돌려주면 모델이 그 관찰을 읽고 우회하거나 되묻는다. 그래서 거부해도 루프가 안 깨진다.
  • 트레이드오프의 기준 = 되돌릴 수 있는가. 읽기는 자동, 덮어쓰기·셸 실행·삭제·외부 전송은 게이트. 게이트는 fail-closed([y/N] 기본 거부, EOFError → 거부). 승인이 잦으면 승인 피로로 게이트가 무력해진다 — 해법은 "덜 묻기"가 아니라 "덜 위험하게 만들기"(allowlist·샌드박스·dry-run).
  • 범위 = 계획 + 자율 실행 + 승인 게이트까지. Hermes는 가진 도구로만 자율적이다 — 모르는 지식을 검색해 오는 것(RAG)은 M6, 통합·eval·trace는 M7. (지금의 print 로그는 눈으로 보는 임시 출력일 뿐 구조화된 trace가 아니다.)

# 2) 에이전트 자신의 상태 — 현재 계획 (클론에선 self.plan)
plan = []


def update_plan(steps):
    """계획 기록 핸들러 — 부작용이 '없다'. 파일도 셸도 건드리지 않는다.
    모델이 준 steps를 우리 쪽 상태(plan)에 저장하고, 화면에 찍고, 문자열을 돌려주는 게 전부다."""
    global plan
    plan = steps
    print(f"  [plan] {len(steps)}단계")
    for i, s in enumerate(steps, 1):
        print(f"    {i}. {s}")
    return f"계획 저장됨: {len(steps)}단계"   # ★ 반드시 '문자열' — tool_result content 규칙(M2)


# 3) 바깥 세상을 다루는 도구 2개 — 둘 다 '가짜'다(부작용 0).
def list_files():
    """(가짜) 실제 폴더를 읽지 않는다. 하드코딩된 목록을 문자열로 돌려준다. → 안전(자동 실행)"""
    return "app.py\nmain.py\nREADME.md\ntemp1.log\ntemp2.log\nnotes.txt"


def delete_file(path):
    """★ 가짜다 — 실제로 아무것도 지우지 않는다. '지운 척'하는 문자열만 돌려준다.
    그런데도 '위험 도구'로 취급한다(삭제 = 되돌리기 어려운 행동의 교과서적 예).
    진짜로 안 지우니 y도 n도 마음껏 눌러 볼 수 있다 — 진짜 삭제/셸은 클론에서 만난다."""
    return f"(가짜) {path} 삭제됨"


def run_tool(name, tool_input):
    """도구 이름으로 실제 함수를 부르는 디스패처. 반환은 반드시 문자열.
    ※ update_plan은 여기 없다 — 바깥 세상이 아니라 '에이전트 자신의 상태(plan)'를 바꾸는
       도구라서 agent loop(step2)가 직접 처리한다. 클론의 tools.py / agent.py 분리와 같은 이유."""
    if name == "list_files":
        return list_files()
    if name == "delete_file":
        return delete_file(tool_input["path"])
    return f"[unknown tool: {name}]"

#    list_files는 읽기만 하니 잘못 돌아도 되돌릴 게 없다 → 자동 실행.
#    delete_file은 되돌릴 수 없다 → 실행 직전에 사람에게 묻는다.
DANGEROUS_TOOLS = {"delete_file"}     # ← set이다(문자열로 쓰면 in 검사가 부분 문자열 검사가 된다)


# 5) ★ 승인 게이트(human-in-the-loop) — 위험 도구 실행 '직전'에 y/n을 묻는다.
def confirm(name, tool_input):
    """기본값은 거부([y/N]) — 되돌리기 어려운 행동의 안전한 기본값은 '안 함'이다(fail-closed).
    비대화형 실행(파이프/CI)에선 input()이 EOFError를 내므로 그것도 거부로 처리한다."""
    print(f"  [승인 요청] {name}({tool_input})")
    try:
        answer = input("  실행할까요? [y/N] ").strip().lower()
    except EOFError:
        return False          # 못 물어보면 안 한다
    return answer == "y"      # y가 아니면(Enter·n·그 무엇이든) 전부 거부


# --- API 없이 부품이 도는지 로컬에서 먼저 확인한다 (과금 0) ---
print(run_tool("list_files", {}))
print(run_tool("delete_file", {"path": "temp1.log"}))    # 진짜로 지우지 않는다
print(update_plan(["파일 목록 확인", ".log 파일 고르기", "각각 삭제"]))
print(f"plan 상태: {plan}")

왜 기본값이 거부([y/N])인가 — fail-closed. 대문자 N이 기본값이라는 관례 표기다(rm -i와 같다). 되돌리기 어려운 행동의 안전한 기본값은 "안 함"이다 — 사용자가 무심코 Enter를 쳐도, 스크립트가 비대화형으로 돌아 EOFError가 나도, 넘어지는 방향은 언제나 "실행 안 함"이어야 한다. return answer == "y" 한 줄이 그걸 보장한다(!= "n"이었다면 정반대가 된다).
세 가지를 미리 짚어 둔다(클론에서 그대로 다시 만난다).
  • update_plan은 마법이 아니다. 하는 일은 plan에 저장하고 화면에 출력하고 문자열을 반환하는 것이 전부다 — 파일도 셸도 없다. 그래서 DANGEROUS_TOOLS에 안 들어간다(되돌릴 게 없으니 물을 이유도 없다).
  • run_tool에 update_plan이 없다. list_files·delete_file은 바깥 세상을 바꾸지만 update_plan은 에이전트 자신의 상태(plan)를 바꾼다 → 도구 디스패처가 아니라 루프가 직접 처리한다(step2에서 확인).
  • update_plan의 반환은 문자열이어야 한다. f"계획 저장됨: {len(steps)}단계" — 여기서 len(steps)(숫자)를 그대로 리턴하면 tool_result의 content가 숫자가 되어 400이 난다(M2 규칙 · M3 실습에서 이미 겪은 그 에러).

2) 미니 agent loop에 게이트 끼우기 — 계획 → 자동 실행 → 승인(y)

이제 M3의 그 while 루프를 그대로 가져와 딱 두 곳을 더한다 — ① run_tool을 부르기 직전의 게이트 3줄(ReAct의 '행동' 단계 바로 앞)과 ② update_plan 분기. 목표는 한 줄만 준다: "작업 폴더의 임시 로그 파일(.log)을 정리해줘". 루프·stop_reason 분기·max_steps는 M3에서 하나도 안 바뀌었다. (step1의 부품을 그대로 포함해 이 파일 하나로 실행된다.)

# step2.py — 미니 agent loop에 '승인 게이트'를 끼운다
#            (step1의 부품을 그대로 포함해 이 파일 하나로 실행된다)
#            ⚠ input()으로 승인을 받는다 → 반드시 대화형 터미널에서 실행할 것.
import anthropic

client = anthropic.Anthropic()          # ANTHROPIC_API_KEY 환경변수 자동 사용
MODEL = "claude-sonnet-4-6"
MAX_TOKENS = 512
max_steps = 8                           # 무한 루프 가드 (M3)

# ★ 가드레일 — 되돌리기 어려운 도구 '집합'. delete_file만 게이트를 건다.
DANGEROUS_TOOLS = {"delete_file"}

# ★ 거부 시 모델에게 돌려줄 '관찰' 문구. 그냥 "거부됨"이 아니라 '다음에 뭘 하라'까지 넣는다 —
#   안 그러면 모델이 같은 도구를 무한 재시도한다.
DENIED_MSG = "사용자가 이 도구 실행을 거부했습니다. 다른 방법을 찾거나 사용자에게 물어보세요."

# 행동 정책을 system에 적는다. 단 이건 '부탁'이다 — 강제는 아래 게이트 코드가 한다.
SYSTEM = (
    "너는 파일 정리를 돕는 도우미다. "
    "여러 단계가 필요한 목표를 받으면, 가장 먼저 update_plan 도구로 계획(단계 목록)을 세운 뒤 실행을 시작한다. "
    "delete_file처럼 되돌리기 어려운 도구는 사용자 승인이 필요하다. 거부당하면 같은 도구를 억지로 다시 부르지 말고, "
    "다른 방법을 찾거나 사용자에게 무엇을 원하는지 물어본다."
)

tools = [
    {
        "name": "update_plan",
        "description": "현재 작업 계획(단계 목록)을 기록/갱신한다. 여러 단계가 필요한 목표를 받으면 "
                       "가장 먼저 이 도구로 계획을 세우고 시작한다. 계획이 바뀌면 다시 호출한다.",
        "input_schema": {
            "type": "object",
            "properties": {
                "steps": {
                    "type": "array",
                    "items": {"type": "string"},
                    "description": "실행할 단계들. 각 항목은 한 줄짜리 행동, 예: '파일 목록을 확인한다'",
                },
            },
            "required": ["steps"],
        },
    },
    {
        "name": "list_files",
        "description": "작업 폴더의 파일 목록을 반환한다. 읽기만 하므로 안전하다.",
        "input_schema": {"type": "object", "properties": {}},
    },
    {
        "name": "delete_file",
        "description": "지정한 경로의 파일을 삭제한다. 되돌릴 수 없다.",
        "input_schema": {
            "type": "object",
            "properties": {
                "path": {"type": "string", "description": "삭제할 파일의 경로"},
            },
            "required": ["path"],
        },
    },
]

plan = []


def update_plan(steps):
    global plan
    plan = steps
    print(f"  [plan] {len(steps)}단계")
    for i, s in enumerate(steps, 1):
        print(f"    {i}. {s}")
    return f"계획 저장됨: {len(steps)}단계"   # ★ 반드시 문자열


def list_files():
    return "app.py\nmain.py\nREADME.md\ntemp1.log\ntemp2.log\nnotes.txt"


def delete_file(path):
    return f"(가짜) {path} 삭제됨"           # ★ 진짜로는 아무것도 안 지운다


def run_tool(name, tool_input):
    # ※ update_plan은 여기 없다 — agent loop가 직접 처리한다(에이전트 자신의 상태를 바꾸는 도구).
    if name == "list_files":
        return list_files()
    if name == "delete_file":
        return delete_file(tool_input["path"])
    return f"[unknown tool: {name}]"


def confirm(name, tool_input):
    """위험 도구 실행 '직전'에 사람에게 y/n을 묻는다. 기본값은 거부([y/N], 그냥 Enter = 거부).
    비대화형 실행에선 EOFError → 거부(fail-closed)."""
    print(f"  [승인 요청] {name}({tool_input})")
    try:
        answer = input("  실행할까요? [y/N] ").strip().lower()
    except EOFError:
        return False
    return answer == "y"


# --- 목표 한 줄을 주고 루프를 돌린다 ---
messages = [{"role": "user", "content": "작업 폴더의 임시 로그 파일(.log)을 정리해줘"}]

step = 0
while step < max_steps:
    step += 1
    resp = client.messages.create(
        model=MODEL, max_tokens=MAX_TOKENS,
        system=SYSTEM, tools=tools, messages=messages,
    )
    messages.append({"role": "assistant", "content": resp.content})   # 통째로 보존(M3)

    if resp.stop_reason != "tool_use":                                # 종료 분기(M3)
        final = "".join(b.text for b in resp.content if b.type == "text")
        print(f"[step {step}] end_turn -> {final}")
        break

    tool_results = []
    for block in resp.content:
        if block.type == "tool_use":
            print(f"  ↳ step {step}: {block.name}({block.input})")

            # ★★ 승인 게이트 — run_tool을 부르기 '직전'(= ReAct의 '행동' 단계 바로 앞).
            #     정책 판단이 실행 분기보다 먼저 온다 → 도구가 늘어도 게이트를 지나쳐 실행될 일이 없다.
            if block.name in DANGEROUS_TOOLS and not confirm(block.name, block.input):
                print("  [거부됨] 실행하지 않고, 거부 사실을 모델에게 알립니다.")
                # ★★ 거부해도 tool_use 하나당 tool_result 하나! (M2 규칙 — 빠지면 400)
                tool_results.append({
                    "type": "tool_result",
                    "tool_use_id": block.id,   # tool_use와 반드시 매칭
                    "content": DENIED_MSG,     # 문자열
                    "is_error": True,          # 실패/거부임을 알리는 필드
                })
                continue                       # 도구는 실행하지 않는다. 루프는 계속 돈다.

            # update_plan은 '에이전트 자신의 상태(plan)'를 바꾼다 → run_tool이 아니라 여기서 처리
            if block.name == "update_plan":
                result = update_plan(block.input["steps"])
            else:
                result = run_tool(block.name, block.input)   # 바깥 세상을 바꾸는 도구

            tool_results.append({
                "type": "tool_result",
                "tool_use_id": block.id,
                "content": result,
            })
    messages.append({"role": "user", "content": tool_results})
else:
    print(f"[max_steps={max_steps} 도달 — 루프를 강제 종료했어요]")

  • 승인(y)했을 때 — {'type': 'tool_result', 'tool_use_id': 'toolu_…', 'content': '(가짜) temp1.log 삭제됨'} → 도구가 실행됐고, 그 결과가 관찰로 간다. is_error는 없다.
  • 거부(Enter)했을 때 — {'type': 'tool_result', 'tool_use_id': 'toolu_…', 'content': '사용자가 이 도구 실행을 거부했습니다…', 'is_error': True} → 도구는 실행되지 않았고((가짜) … 삭제됨 문자열이 안 보인다), 대신 "거부됨"이라는 관찰이 같은 tool_use_id로 간다.
둘 다 tool_result 하나를 회신한다 — 달라지는 건 내용(content + is_error)뿐이다. 그래서 400도, 크래시도 없이 루프가 end_turn까지 정상적으로 굴러간다. 에이전트를 안전하게 만드는 것과 에이전트를 망가뜨리는 것은 다르다. (tool_use_id는 실제로는 toolu_01A… 같은 긴 문자열이고, 매 실행마다 다르다.)

같은 step3.py를 다시 실행해 이번엔 y를 눌러 보라 — 회신 dict가 'content': '(가짜) temp1.log 삭제됨'으로 바뀌고 is_error가 사라진다. 승인 1회 + 거부 1회를 둘 다 보고 나면 이 모듈의 절반이 아니라 전부를 본 것이다.

거부 후 모델의 반응은 매번 다를 수 있다. 위 예처럼 되묻거나(가장 흔함), temp2.log를 대신 시도하거나(→ [승인 요청]이 한 번 더 뜬다), "삭제하지 않았습니다"라고 정리하고 끝낸다. 어느 쪽이든 상관없다 — 확인할 것은 딱 하나, 루프가 400이나 예외로 죽지 않고 [step N] end_turn까지 도달했다는 사실이다.

막히면:
  • ★ 거부했더니 BadRequestError(400) "tool_use ids were found without tool_result blocks" → 거부 분기에서 tool_results에 아무것도 안 넣고 continue했다. 거부해도 tool_result 하나는 반드시 회신한다 (content=DENIED_MSG + is_error: True). M2의 1:1 규칙은 거부해도 유효하다.
  • 거부하면 프로그램이 그냥 끝난다 / 최종 답이 없다 → 거부를 break·return·raise로 처리했다. 거부는 "이 행동만 하지 마"이지 "일 그만둬"가 아니다. continue로 그 블록만 건너뛰고 루프는 계속 돈다.
  • BadRequestError(400) "tool_result.content: Found a number, but tool_result content must either be a string …" → update_plan이 len(steps)(숫자)를 리턴했다. 반환은 문자열이어야 한다 — f"계획 저장됨: {len(steps)}단계". (M3 실습에서 run_tool 반환을 숫자로 둬 이미 한 번 겪은 그 에러다. tool_result의 content는 언제나 문자열.)
  • EOFError가 나거나, 승인 프롬프트가 뜨자마자 전부 거부된다 → 비대화형 실행이다(파이프·< /dev/null·CI·백그라운드). confirm()의 except EOFError: return False가 안전하게 거부로 처리한 것이다(fail-closed — 의도된 동작). 대화형 터미널에서 직접 실행한다.
  • 승인 프롬프트가 안 뜨고 위험 도구가 그냥 실행된다 → ① DANGEROUS_TOOLS를 집합이 아니라 문자열로 선언했다 (= "delete_file"이면 in이 부분 문자열 검사가 되어 "file"·"delete"에도 True가 된다) → {...} 집합으로. ② 도구 이름 오타(delete-file) → block.name과 정확히 같은 문자열이어야 한다. ③ 게이트를 run_tool 호출 뒤에 뒀다 → 이미 실행된 다음이라 아무 의미가 없다. 반드시 호출 '직전'.
  • [unknown tool: update_plan]이 회신된다 → 루프의 if block.name == "update_plan": 분기가 없어서 run_tool로 새어 나갔다(run_tool엔 update_plan이 일부러 없다). 핸들러는 루프에 둔다.
  • BadRequestError(400) "tool_use_id …" → tool_use_id를 block.id가 아닌 다른 값으로 넣었거나, 승인/거부 분기 중 한쪽에서만 회신했다. 두 분기 모두 같은 block.id로 tool_result를 만든다.
  • 모델이 계획을 안 세우고 바로 도구를 부른다 → SYSTEM에 계획 지시가 빠졌거나, 목표가 너무 단순해 모델이 계획이 필요 없다고 판단한 것이다 (정상 동작 — 여러 단계가 필요한 목표를 준다). SYSTEM은 '부탁'이라 100% 강제되지 않는다. 강제는 코드(게이트)가 한다 — 이 대비가 guardrail의 핵심이다.
  • [max_steps=8 도달 …] → 계획 단계가 많으면 update_plan이 1스텝, 각 도구가 1스텝씩 먹어 8을 넘길 수 있다. 목표를 작게 하거나 max_steps를 늘린다(M3의 그 가드).
  • AuthenticationError(401) → ANTHROPIC_API_KEY 미설정/오타. echo $ANTHROPIC_API_KEY로 확인(step1은 API를 안 부르니 키 없이도 됨).
클론으로 이어진다. 방금 만든 DANGEROUS_TOOLS · confirm() · DENIED_MSG · 게이트 3줄 · 거부 회신(is_error: True) · update_plan 분기는 이름도 문구도 그대로 Hermes에 들어간다 — DANGEROUS_TOOLS는 config.py로, confirm()과 게이트는 agent.py의 agent loop로, plan은 self.plan이 된다. 달라지는 건 도구가 가짜가 아니라는 것뿐이다 — 거기선 run_bash가 진짜 셸을 돌리고 write_file이 진짜로 덮어쓴다. 그래서 y를 누르는 손가락이 무거워진다.

교체 포인트는 다섯이다:

  1. config.py에 DANGEROUS_TOOLS + agent.py에 모듈 상수 DENIED_MSG·모듈 함수 confirm() 신설.
  2. self.plan = [](__init__) + _update_plan(steps) 메서드 — self.memory(M4) 옆에 나란히 놓인 또 하나의 에이전트 상태.

    """위험 도구 실행 '직전'에 사람에게 y/n을 묻는다 (human-in-the-loop).

M2에서 배운 tool_use 하나당 tool_result 하나 규칙은 거부해도 그대로 유효하다 — 짝을 빠뜨리면 다음 create가 400 (tool_use ids … without tool_result blocks)이다. 그래서 거부의 올바른 처리는 아무것도 안 보내기가 아니라 안 하고 나서, 안 했다고 말하기다: 도구는 실행하지 않고(continue) is_error: True인 tool_result만 회신한다. 흔한 오답 3종: ① 거부했으니 tool_results에 아무것도 안 넣는다 → 400. ② 거부했으니 루프를 break/예외로 탈출한다 → 에이전트가 죽는다. 거부는 이 행동만 하지 마이지 일 그만둬가 아니다. ③ 거부 사실을 안 알리고 빈 문자열을 회신한다 → 모델이 성공한 줄 알고 다음 단계로 간다(더 나쁘다).
거부는 에러가 아니라 하나의 관찰(observation)이다: ReAct(M3)의 추론 → 행동 → 관찰에서, 거부는 관찰 자리에 실패/거부가 들어가는 것일 뿐이다. 모델은 그걸 읽고 스스로 적응한다 — 다른 방법을 시도하거나, 사용자에게 그럼 어떻게 할까요?라고 되묻거나, 그 단계를 건너뛴다. 그래서 거부해도 루프가 안 깨진다. analogy: 실패한 syscall이 예외를 던지지 않고 에러 코드를 리턴하는 것 — 호출자(모델)가 그걸 보고 분기한다. 에이전트를 안전하게 만드는 것과 에이전트를 망가뜨리는 것은 다르다.
순서 규칙 — 게이트가 update_plan 분기보다 먼저: 정책 판단(if … in DANGEROUS_TOOLS)이 실행 분기(if block.name == "update_plan")보다 위에 온다. 그래야 나중에 도구가 늘어도 게이트를 지나쳐 실행될 일이 없다(fail-closed 읽기). run_tool로 가든 _update_plan으로 가든, 모든 행동은 게이트를 먼저 통과한다.

Memory(M4)는 그대로 돌고 — 계획도 승인 요청도 결국 history에 쌓이고, 길어지면 compaction된다 — REPL의 hermes = Hermes(); hermes.run(user)도 그대로다. 승인 프롬프트는 hermes.run() 안에서 뜨는 중첩된 입력이다: __main__.py의 input("you> ")와 confirm()의 input(" 실행할까요? 방금 무슨 일이 있었나: write_file은 실행되지 않았다(파일이 안 생겼다 — ls files.txt로 확인해 보라). 그런데 Hermes는 죽지 않았다. 게이트가 continue로 도구를 건너뛰고 {"type": "tool_result", "tool_use_id": …, "content": DENIED_MSG, "is_error": True}를 회신했고 → 그 거부됨이 ReAct의 관찰 자리에 들어가 → 다음 스텝에서 모델이 그걸 읽고 스스로 적응했다 (저장을 포기하고, 목록을 화면에 보여 주며 되물었다). 거부는 크래시가 아니라 관찰이다 — 이 한 조각이 안전한 에이전트와 망가진 에이전트를 가른다. (모델이 고르는 명령·계획 단계 수·적응 방식은 매번 조금씩 다르다 — 위 숫자와 문구는 예시다.)
개념↔코드 매핑(한눈에):
  • planning = TOOLS의 update_plan 스키마 + 상태 self.plan.
  • 계획의 외부화 = _update_plan의 print(우리가 본다) + history에 남는 tool_use/tool_result(모델이 본다).
  • autonomy = M3의 while 루프(엔진은 이미 있었다) + SYSTEM의 방향(먼저 계획하라) + 게이트라는 한계.
  • guardrail = config.py의 DANGEROUS_TOOLS + 루프의 if block.name in DANGEROUS_TOOLS (프롬프트가 아니라 코드).
  • approval gate / human-in-the-loop = confirm()의 input()이 run_tool 호출 직전에 있다는 사실 그 자체.
  • 거부는 관찰이다 = is_error: True tool_result + continue (도구는 안 돌고, 회신은 간다).
  • fail-closed = [y/N] 기본 거부 + except EOFError: return False.
  • 정책·상태는 루프가, 효과는 도구가 = 게이트와 _update_plan이 둘 다 agent.py에 있고, read_file/write_file/run_bash는 tools.py에 있는 것.
막히면: ★ 거부했더니 400(tool_use ids … without tool_result blocks) — 거부 시 tool_results에 아무것도 안 넣고 continue했다. 거부해도 tool_result 하나는 반드시 회신한다(is_error: True). M2의 1:1 규칙. [unknown tool: update_plan]이 회신된다 — agent.py에 if block.name == "update_plan": 분기가 없어 run_tool로 새어 나갔다. 핸들러는 agent.py(tools.py엔 스키마만). tool_result.content: Found a number … 400 — _update_plan이 len(steps)(숫자)를 리턴했다. 반환은 문자열 — f"계획 저장됨: {len(steps)}단계". M3 실습에서 이미 겪은 그 에러다. 승인 프롬프트가 안 뜨고 그냥 실행된다 — DANGEROUS_TOOLS가 집합(set)이 아니라 문자열(DANGEROUS_TOOLS = "write_file")이거나 도구 이름에 오타. 문자열이면 in이 부분문자열 검사가 돼 run_bash는 영영 안 걸린다. {…} 중괄호를 확인. 계획을 안 세우고 바로 도구를 부른다 — SYSTEM에 계획 지시가 안 들어갔거나, 목표가 너무 단순해서 모델이 계획이 필요 없다고 판단한 것(정상 동작이다 — 여러 단계가 필요한 목표를 줘 본다). 프롬프트는 부탁이지 강제가 아님을 다시 확인하는 기회. EOFError / 입력이 안 먹는다 — 비대화형 실행(파이프·리다이렉트·백그라운드·IDE 콘솔). 대화형 터미널에서 실행한다. except EOFError: return False가 안전망(fail-closed)이라 거부로 처리되고 죽지는 않는다. [max_steps 도달] — update_plan이 1스텝을 먹고 각 단계가 1스텝씩 → MAX_STEPS = 8을 넘길 수 있다. 목표를 작게 하거나 MAX_STEPS를 늘린다(M3의 그 가드). 모델이 거부당한 도구를 계속 다시 부른다 — DENIED_MSG에 다음 행동 지침 (다른 방법을 찾거나 사용자에게 물어보세요)이 들어갔는지 + SYSTEM의 거부 관련 문장 확인. 그래도 막히면 diff hermes/agent.py _solution/05-planning-autonomy/hermes/agent.py로 정답과 대조한다.
트레이드오프를 몸으로: 이 작은 태스크 하나에 게이트가 2번 떴다(run_bash + write_file). 겨우 ls까지 물어야 하나? 하는 짜증 — 그게 바로 자율성↔안전 트레이드오프의 실체다. 승인이 너무 많으면 자율성이 죽고, 더 나쁘게는 승인 피로(습관적으로 y만 눌러 게이트가 유명무실해짐)가 온다. 승인이 없으면 run_bash("rm -rf …") 한 번이면 끝이다. 실무의 해법은 덜 묻기가 아니라 덜 위험하게 만들기다 — allowlist(ls·cat처럼 안전한 명령만 자동 허용), 샌드박스(격리 환경이면 게이트 없이 자율 최대), dry-run, 되돌릴 수 있게 만들기(작업 전 git commit). M5는 가장 단순한 다이얼 하나(y/n)만 구현했다. 실험해 보라: DANGEROUS_TOOLS에 read_file까지 넣으면 모든 스텝에서 물어본다 — 자율성이 사라지는 걸 즉시 체감한다.
지금 Hermes의 한계 = 다음 모듈의 동기: ① 계획은 self.plan(파이썬 변수)에 있을 뿐이고, 모델을 움직이는 건 history에 남은 호출 기록이다 — compaction(M4)이 history를 접으면 모델 쪽 계획 기억은 흐려질 수 있다(계획 재주입은 M7 통합에서). ② Hermes는 가진 도구로만 자율적이다 — 모르는 지식은 여전히 못 가져온다. 로컬 문서를 검색해 답의 근거로 넣는 RAG는 M6다. ③ 무슨 일이 있었는지는 아직 print로 흘려볼 뿐 남지 않는다 — 구조화된 trace 로깅·eval은 M7.

자율 에이전트 요소 완성. Hermes는 이제 목표 한 줄을 받으면 스스로 계획을 세우고(update_plan), 안전한 도구는 자동으로 실행하되 되돌리기 어려운 도구는 실행 직전 사람에게 묻고(DANGEROUS_TOOLS + confirm()), 거부당해도 죽지 않고 적응한다(is_error tool_result) — 다음 M6 · RAG & Knowledge에서는 rag.py와 search_docs 도구를 붙여, 모르는 지식을 문서에서 검색해 오는 RAG 에이전트 성격을 흡수한다.
