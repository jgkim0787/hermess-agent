The Agent Loop

개념

M2에서 우리는 모델에게 첫 도구를 쥐여줬다 — 모델이 tool_use로 도구를 요청하면 우리가 실행해 tool_result로 돌려주고, 모델이 그 결과를 보고 최종 답을 냈다. 하지만 그 왕복은 딱 한 번이었다. M2의 chat_with_tools는 도구를 한 번 부르고(if) 끝났다 — 이것이 1-step이다. 실제 일은 그렇게 단순하지 않다. 도구 하나의 결과를 봐야 다음 도구를 정할 수 있고, 여러 도구를 순서대로 엮어야 하며, 몇 번이 걸릴지 미리 알 수 없다. if는 "한 번"만 표현한다. "끝날 때까지 반복"하려면 while이 필요하다.

이번 모듈은 그 왕복을 stop_reason이 end_turn이 될 때까지 반복하는 while 루프로 승격한다. 이 반복 구조가 바로 agent loop이고, 그 이론적 이름이 ReAct다. M0에서 "LLM은 한 번 답하면 끝이지만, Agent는 그 LLM을 loop로 감싸 목표에 도달할 때까지 반복한다"고 배운 바로 그 loop를 이제 코드로 만든다. 그리고 놀랄 만큼 적게 바뀐다 — 도구 왕복 4단계·tool_use_id 매칭·history append 규칙은 전부 M2 그대로다. 새 API 개념은 없고, 제어 흐름(control flow)만 if에서 while로 바뀐다.

running example은 순수 파이썬 계산기 도구 2개 add(a, b)·mul(a, b)로 (12+8)*3을 계산하는 것이다. 도구가 둘로 나뉘어 있어, 모델은 add(12, 8)로 20을 얻은 뒤에야 mul(20, 3)을 부를 수 있다 — 즉 도구를 2번 이어서 불러야 풀린다. 개념·실습이 이 계산기를 공유하고(클론은 같은 루프를 write_file·run_bash로 돌린다), 세 섹션이 같은 식별자(while step < max_steps, step, stop_reason != "tool_use", run_tool, tool_results, messages)를 쓴다.

왜 반복인가 — 1-step(if)의 한계

M2의 1-step이 부족해지는 상황은 셋으로 정리된다. 셋 다 (12+8)*3 한 줄에 들어 있다.

  • 의존(dependency): 도구 A의 결과가 있어야 도구 B의 인자를 정할 수 있다. mul의 첫 인자 20은 add(12, 8)를 실행하기 전에는 존재하지 않는다.
  • 연쇄(chaining): 하나의 목표를 위해 도구 여러 개를 순서대로 엮어야 한다(먼저 add, 그다음 mul).
  • 열린 종료(open-ended): 몇 스텝이 필요한지 미리 알 수 없다 — "다 될 때까지" 계속해야 한다.

if는 도구를 한 번 부르고 끝난다. "반복"을 표현하는 제어 구조는 while이다. 그래서 M3의 핵심은 사실상 한 줄로 요약된다 — M2의 if를 while로 감싼다.

ReAct — 사고 → 행동 → 관찰의 반복

정의 — ReAct: Reasoning + Acting. 모델이 다음 행동을 추론하고(사고) → 도구를 호출하고(행동) → 그 tool_result를 관찰해(관찰) 다시 추론하는 반복 패턴. agent loop의 이론적 이름이다.

익숙한 그림으로 옮기면 디버깅과 똑같다: 가설을 세우고(생각) → 한 줄 고쳐 실행하고(행동) → 결과를 보고(관찰) → 다시 가설을 세운다. 또는 REPL의 read-eval-print 순환 — 단 여기서 eval은 부작용을 일으키는 "도구 실행"이고, 다음 read의 입력은 그 실행 결과에 대한 "관찰"이다. 모델은 매 스텝 tool_result를 관찰해 다음 행동을 스스로 정한다.

정의 — agent loop: LLM 호출을 반복문으로 감싸, stop_reason이 tool_use면 도구를 실행해 결과를 되먹이고 end_turn이면 멈추는 제어 루프. ReAct를 코드로 구현한 것이며, Agent를 Agent이게 하는 심장이다. (개념/패턴을 가리킬 때는 공백을 쓴 "agent loop"로 표기한다.)

비유로는 함수 호출을 감싼 이벤트 루프 / REPL이 정확하다 — 매 바퀴 부작용(도구)을 일으키고, 그 피드백(관찰)을 다음 바퀴의 입력으로 되먹인다. M2의 도구 왕복(함수 호출 한 번)을 while로 감싼 것이 곧 이 루프다.

비유의 한계: REPL은 사람이 결과를 읽고 다음 줄을 입력하지만, agent loop는 모델이 스스로 tool_result를 관찰해 다음 행동을 정한다 — 사람이 매 줄 개입하지 않는 자율 루프다. 그래서 언제 멈출지도 사람의 Ctrl-D가 아니라 모델이 보내는 end_turn이 결정한다.

루프의 해부 — if를 while로

표기 규약(M2에서 이어감): 개념·패턴은 원어/공백으로 — agent loop, ReAct(대문자 R·A = Reasoning+Acting, react 아님), multi-step. 코드·식별자·API 값은 코드 표기로 — while, max_steps, 그리고 stop_reason 값 tool_use·end_turn. M2의 구분도 유지: 메커니즘 "tool use"(공백) vs 블록 타입 tool_use(밑줄).

도구 정의(tools 배열, 각 input_schema)와 도구 왕복 4단계는 M2에서 배운 그대로다 — 여기선 재정의하지 않고 루프에만 집중한다. 계산기 도구 본체와 디스패처는 이렇게 짧다(tools 배열 정의는 M2와 동일하므로 생략).

# 계산기 도구 2개 — 순수 함수, 부작용·네트워크 없음. 반환은 반드시 문자열.
def add(a, b): return str(a + b)
def mul(a, b): return str(a * b)

def run_tool(name, tool_input):        # 이름 -> 실제 함수 (M2의 디스패처 그대로, 분기만 추가)
    if name == "add": return add(**tool_input)
    if name == "mul": return mul(**tool_input)
    raise ValueError(f"unknown tool: {name}")

이제 핵심 — agent loop다. 아래는 cheatsheet의 "수동 agent loop"를 계산기 소재로 옮긴 골격이다. M2의 1-step 왕복과 비교하며 읽어 보라. 바뀐 곳은 if가 while이 된 것뿐이다.

max_steps = 8                       # 무한 루프 가드 (아래에서 설명)

def run(user_msg: str) -> str:
    messages = [{"role": "user", "content": user_msg}]
    step = 0
    while step < max_steps:                        # ← M2의 if 를 감싼 while + 가드
        step += 1
        resp = client.messages.create(             # 매 스텝 1회 (M2와 똑같은 호출)
            model=MODEL, max_tokens=MAX_TOKENS,
            tools=tools, messages=messages,
        )
        messages.append({"role": "assistant", "content": resp.content})   # 매 스텝 통째로 append

        if resp.stop_reason != "tool_use":         # ← 종료 조건: 도구를 안 부르면 끝
            return "".join(b.text for b in resp.content if b.type == "text")

        # ↓ 여기부터는 M2의 도구 왕복과 '완전히 동일' — 루프로 감쌌을 뿐이다
        tool_results = []
        for block in resp.content:
            if block.type == "tool_use":
                print(f"  [step {step}] {block.name}({block.input})")   # 연쇄를 눈으로
                result = run_tool(block.name, block.input)   # 실행은 우리 코드가
                tool_results.append({
                    "type": "tool_result",
                    "tool_use_id": block.id,       # tool_use 의 id 와 매칭 (M2 그대로)
                    "content": result,             # 반드시 문자열
                })
        messages.append({"role": "user", "content": tool_results})   # 결과는 user 턴으로 회신
        # → 루프 top 으로 돌아가 다시 create (M2가 손으로 하던 '2차 호출'을 루프가 대신한다)

    return "[max_steps 도달 — 루프를 강제 종료했어요]"        # 가드 탈출
왜 종료 판정이 != "tool_use"인가: stop_reason이 tool_use라는 건 "아직 부를 도구가 있다"는 신호다 → 실행하고 계속. 그 밖의 값은 모두 "더 이상 도구 호출이 없다"는 뜻이다 — end_turn(자연 종료)뿐 아니라 max_tokens(상한 도달)·refusal(안전상 거부)까지 — 그래서 단 하나의 테스트 != "tool_use"로 이 세 경우를 모두 "종료"로 처리한다. cheatsheet의 == "end_turn" 검사보다 안전하다(상한·거부로 멈춘 경우에도 루프를 확실히 빠져나온다).
M2 → M3: 무엇이 바뀌었나(그리고 안 바뀌었나):
  • if → while + 가드: 종료 테스트 자체(!= "tool_use")는 그대로다. 한 번 검사하고 끝내던 것을 매 바퀴 검사해 end_turn이 나올 때까지 반복할 뿐. 상한은 while step < max_steps.
  • 하드코딩 "2차 호출" 제거: M2가 도구 실행 뒤 손으로 한 번 더 부르던 create가 사라진다 — 루프의 다음 바퀴가 자연스럽게 그 역할을 한다.
  • 도구 실행·tool_result 수집 블록은 M2와 100% 동일 — 코드가 한 글자도 안 바뀐다. "루프로 감쌌을 뿐"의 실체가 이 부분이다.
  • assistant 응답 append를 루프 상단 한 곳으로: M2에서 분기마다 흩어져 있던 것을 create 직후 한 번으로 모았다.
(클론에서는 이 run()이 Hermes.run 메서드가 되고, messages는 self.messages, max_steps는 config 상수 MAX_STEPS가 된다. 골격은 똑같다.)

multi-step — 한 run()에 create가 여러 번

정의 — multi-step: 한 번의 요청 처리(한 run()) 안에서 모델이 도구를 두 번 이상 연쇄 호출하는 것. 앞 도구의 tool_result를 관찰해 다음 도구를 정한다. (멀티스텝이라고도 쓴다.)

익숙한 비유는 셸 파이프라인, 또는 뒤 단계가 앞 단계 출력에 의존하는 태스크 그래프의 순차 실행이다. (12+8)*3을 계산기 도구로 풀면 루프가 이렇게 돈다 — run() 하나가 messages.create를 세 번 부른다.

질문:  "(12+8)*3 을 한 번에 한 연산씩, 제공된 도구만 써서 계산해줘"

[step 1]  create #1 → stop_reason == "tool_use" :  add(12, 8)
          우리가 실행 → tool_result "20"  회신
          (모델이 20 을 '관찰'하고 다음에 mul 을 부르기로 추론)

[step 2]  create #2 → stop_reason == "tool_use" :  mul(20, 3)
          우리가 실행 → tool_result "60"  회신
          (모델이 60 을 '관찰' — 더 부를 도구가 없다)

[step 3]  create #3 → stop_reason == "end_turn" :  "60"   → 루프 종료(최종 답)

여기서 2번의 도구 연쇄(add → mul)가 눈에 보인다. mul은 add의 결과 20이 messages에 들어온 뒤에야 부를 수 있으므로, 1-step(if)으로는 애초에 표현이 불가능하다. 참고로 M2의 1-step은 이 루프가 딱 1바퀴 돌고 end_turn인 특수 케이스일 뿐이다.

(예고) history가 자란다: 매 스텝의 create는 M1의 stateless 원리 그대로 커진 messages 전체를 다시 보낸다. 루프가 돌수록 history가 계속 자라 context window·비용을 압박한다 — 이 문제는 M4 "Memory & Context"에서 요약 압축으로 다룬다. 여기서는 "자란다"는 사실만 짚고 넘어간다.

max_steps — 무한 루프 가드

정의 — max_steps: agent loop가 종료되지 않고 도구를 무한히 부르는 것을 막는 반복 상한. 스텝 수가 이 값에 도달하면 강제로 루프를 빠져나온다. watchdog 타이머, 재시도 max_retries, for _ in range(N)의 N과 같은 안전장치다.
왜 max_steps가 필요한가: 종료 판정은 모델의 판단(stop_reason)에 달려 있다. 그런데 모델이 종료하지 않고 도구를 계속 부르거나, 두 도구를 오가며 진동(oscillation)할 수 있다 — 그러면 루프가 무한히 돌며 토큰·시간·비용이 폭주한다. 사람이 개입하지 않는 자율 루프이므로, 스스로 멈추지 못할 때를 대비한 바깥의 상한이 반드시 필요하다. 그래서 while step < max_steps로 헤더에 가드를 명시한다.

실습에서 max_steps를 1로 낮춰 보면, 계산이 끝나기 전에 상한에 걸려 강제 종료되는 것을 직접 관찰할 수 있다 — 가드가 실제로 동작함을 눈으로 확인하는 셈이다.

한눈 정리

  • agent loop = LLM 호출을 while로 감싼 제어 루프 — stop_reason이 tool_use면 도구를 실행해 되먹이고, 아니면 종료. 이것이 ReAct(사고 → 행동 → 관찰의 반복)의 구현체다.
  • 왜 반복인가 = 1-step(if)은 의존·연쇄·"다 될 때까지"를 표현 못 한다. (12+8)*3은 add 결과가 있어야 mul을 부를 수 있어 도구 2번 연쇄가 강제된다.
  • 종료 조건 = if resp.stop_reason != "tool_use": return. tool_use면 계속, end_turn/max_tokens/refusal이면 종료. 이 테스트는 M2 그대로다.
  • multi-step = 한 run()에 create가 여러 번. 앞 도구의 tool_result를 관찰해 다음 도구를 정한다. 도구 왕복 4단계·tool_use_id 매칭·history append는 전부 M2 그대로 — 제어 흐름만 if→while.
  • max_steps = 무한 루프·진동을 막는 반복 상한(watchdog). 없으면 비용 폭주. while step < max_steps로 가드.
  • 범위 = 여기까지가 agent loop 완성(코딩 에이전트 Hermes가 이 모듈에서 완성된다). 루프가 돌수록 커지는 history 압축은 M4(Memory), 목표 분해(planning)와 위험 도구 실행 전 승인 게이트(예: run_bash)는 M5에서 다룬다.

M2에서는 도구 왕복을 딱 한 번 했다(if 1-step): 도구를 부르고 → 결과를 돌려주고 → 최종 답. 하지만 (12+8)*3을 도구로 풀려면 add(12, 8)로 20을 얻어야 그 20으로 mul(20, 3)을 부를 수 있다 — 도구를 2번 연쇄해야 한다. "한 번"으로는 부족하고 "될 때까지 반복"해야 한다. 그 if를 while로 키운 것이 agent loop다. 이번 실습은 순수 파이썬 계산기 도구 2개(add·mul)로 그 while 루프를 직접 돌려, 모델이 stop_reason을 tool_use로 낼 때마다 도구를 실행해 이어가고 end_turn이면 멈추는 흐름을 눈으로 확인한다.

0) 준비

M1~M2와 동일 환경이다(uv, Python 3.12). 키는 console.anthropic.com에서 발급한다. 루프는 매 스텝 messages.create를 부른다 — 이번 예제는 3번쯤 불리고 스텝마다 과금된다. 그래서 작은 max_tokens와 max_steps 가드로 비용을 억제한다. 아래 step1은 API를 부르지 않으니 키가 없어도 실행된다(도구를 로컬에서 먼저 검증).

1) 계산기 도구 2개 정의 — add·mul (키 불필요)

M2와 똑같이 도구는 두 조각이다 — 모델이 읽는 명세(tools)와 우리가 실제로 부르는 함수. 다만 소재가 순수 파이썬 산술이라 가짜가 아니라 진짜 계산이다(결과 검증이 명확). 그리고 도구를 add·mul 둘로 나눈 것이 이번의 핵심이다.

# step1.py — 계산기 도구 2개(add/mul)의 "명세"와 "실제 함수"를 나눠 만든다
#            (API 호출 없음, 키 불필요 — 도구가 로컬에서 도는지 먼저 검증)

# 1) 모델에게 알려줄 도구 "명세" 2개. 각각 숫자 a, b 를 받는다 (number).
tools = [
    {
        "name": "add",
        "description": "두 수 a, b 를 더한 값을 반환한다.",
        "input_schema": {
            "type": "object",
            "properties": {
                "a": {"type": "number", "description": "첫 번째 수"},
                "b": {"type": "number", "description": "두 번째 수"},
            },
            "required": ["a", "b"],
        },
    },
    {
        "name": "mul",
        "description": "두 수 a, b 를 곱한 값을 반환한다.",
        "input_schema": {
            "type": "object",
            "properties": {
                "a": {"type": "number", "description": "첫 번째 수"},
                "b": {"type": "number", "description": "두 번째 수"},
            },
            "required": ["a", "b"],
        },
    },
]

# 2) 실제로 실행되는 우리 쪽 함수 — 순수 파이썬 산술(외부 의존 없음). 반환은 반드시 문자열.
def add(a, b):
    return str(a + b)

def mul(a, b):
    return str(a * b)

# 3) 도구 이름으로 실제 함수를 찾아 부르는 디스패처. 반환은 반드시 문자열.
def run_tool(name, tool_input):
    if name == "add":
        return add(**tool_input)
    if name == "mul":
        return mul(**tool_input)
    return f"알 수 없는 도구: {name}"

# API 없이 로컬에서 도구가 도는지 먼저 확인한다
print(run_tool("add", {"a": 12, "b": 8}))   # 20
print(run_tool("mul", {"a": 20, "b": 3}))   # 60

왜 도구를 add·mul 둘로 나눴나? calc("(12+8)*3") 같은 단일 도구였다면 모델이 한 스텝에 끝내버려 루프가 안 보인다. add와 mul을 분리하면 "mul은 add의 결과(20)가 있어야 인자를 채울 수 있다"는 의존이 생긴다 → 도구를 두 번 연쇄(multi-step)해야만 풀린다. 이 의존이 바로 while 루프가 필요한 이유를 실증한다.
input_schema의 "type": "number"는 M2의 string과 달리 숫자를 받는다(모델이 12, 8 같은 수를 채운다). add/mul이 str(...)로 문자열을 반환하는 건 필수다 — tool_result의 content는 문자열이어야 하기 때문(다음 step에서 사용). 막히면: TypeError: add() got an unexpected keyword argument → properties의 키(a, b)와 함수 인자 이름을 일치시킨다(run_tool이 **tool_input으로 푼다).

2) 미니 agent loop — while로 end_turn까지 반복

이제 M2의 if 1-step을 while 루프로 키운다. 매 스텝 messages.create를 부르고, stop_reason이 tool_use면 도구를 실행해 tool_result를 회신하고 루프 top으로 계속, end_turn(등)이면 최종 답을 내고 break. 무한 루프는 max_steps로 막는다. 매 스텝을 print해 도구 연쇄가 눈에 보이게 한다. (step1의 도구 정의를 그대로 포함해 이 파일 하나로 실행된다.)

# step2.py — 미니 agent loop: while 로 도구 왕복을 end_turn 까지 "반복"한다
#            (step1 의 도구 정의를 그대로 포함해 단독 실행되게 했다)
import anthropic

client = anthropic.Anthropic()          # ANTHROPIC_API_KEY 환경변수 자동 사용
MODEL = "claude-sonnet-4-6"
MAX_TOKENS = 512
max_steps = 8                           # ★ 무한 루프 가드: 최대 8스텝 (없으면 폭주)

# 암산 방지: 이게 없으면 모델이 도구를 안 쓰고 60을 그냥 말해버려 루프가 안 보인다
SYSTEM = (
    "너는 계산을 반드시 제공된 도구(add, mul)로만 수행한다. "
    "암산·직접 계산 금지. 한 번에 한 연산씩 도구를 호출하고, "
    "모든 연산이 끝난 뒤에만 최종 숫자를 답한다."
)

tools = [
    {
        "name": "add",
        "description": "두 수 a, b 를 더한 값을 반환한다.",
        "input_schema": {
            "type": "object",
            "properties": {"a": {"type": "number"}, "b": {"type": "number"}},
            "required": ["a", "b"],
        },
    },
    {
        "name": "mul",
        "description": "두 수 a, b 를 곱한 값을 반환한다.",
        "input_schema": {
            "type": "object",
            "properties": {"a": {"type": "number"}, "b": {"type": "number"}},
            "required": ["a", "b"],
        },
    },
]

def add(a, b):
    return str(a + b)

def mul(a, b):
    return str(a * b)

def run_tool(name, tool_input):
    if name == "add":
        return add(**tool_input)
    if name == "mul":
        return mul(**tool_input)
    return f"알 수 없는 도구: {name}"

messages = [{"role": "user",
             "content": "(12+8)*3 을 한 번에 한 연산씩, 제공된 도구만 써서 계산해줘."}]

step = 0
while step < max_steps:                 # ← M2의 if 를 while 로 승격 + 가드
    step += 1
    resp = client.messages.create(
        model=MODEL, max_tokens=MAX_TOKENS,
        system=SYSTEM, tools=tools, messages=messages,
    )
    # 매 스텝: assistant 응답을 통째로 history 에 append (tool_use 블록 보존)
    messages.append({"role": "assistant", "content": resp.content})

    # 종료 조건: 도구를 더 안 부르면(end_turn 등) 최종 답을 내고 멈춘다
    if resp.stop_reason != "tool_use":
        final = "".join(b.text for b in resp.content if b.type == "text")
        print(f"[step {step}] end_turn -> 최종 답변: {final}")
        break

    # tool_use 블록마다 실행하고, 같은 id 로 tool_result 를 모은다
    tool_results = []
    for block in resp.content:
        if block.type == "tool_use":
            result = run_tool(block.name, block.input)          # 우리가 실제로 계산
            print(f"[step {step}] {block.name}({block.input}) -> {result}")
            tool_results.append({
                "type": "tool_result",
                "tool_use_id": block.id,        # ★ 요청 id 와 반드시 매칭
                "content": result,              # 문자열
            })
    # 도구 결과들을 user 턴으로 회신하고 루프 top 으로 (다음 스텝에서 다시 create)
    messages.append({"role": "user", "content": tool_results})
else:
    # while...else: 루프가 break 없이(=max_steps 소진으로) 끝나면 실행된다
    print(f"[max_steps={max_steps} 도달 — 루프를 강제 종료했어요]")
루프의 심장 = stop_reason 분기. 매 바퀴 stop_reason을 본다 — tool_use면 도구를 실행해 tool_result를 회신하고 루프 top으로(계속), 그 외(end_turn/max_tokens/refusal)면 break(종료). 이 if resp.stop_reason != "tool_use": 테스트는 M2의 chat_with_tools에서 쓰던 바로 그 검사다. M2는 이걸 딱 한 번 했고(if, 1-step), M3은 매 스텝 반복한다(while). 새 API는 없고 제어 흐름만 if→while로 바뀐다.
while...else가 낯설다면: while의 else는 루프가 break 없이 정상 종료됐을 때(=여기선 max_steps를 다 소진했을 때)만 실행된다. 즉 "도구를 계속 부르다 상한에 걸려 강제 종료"된 경우다. (클론 Hermes.run에서는 이 자리가 함수 맨 끝의 return "[max_steps 도달 …]"이 된다 — 같은 역할.)

3) 돌려보기 — (12+8)*3이 2스텝으로 풀리는 걸 관찰

이제 실행해서 도구가 두 번 연쇄되는 것을 눈으로 본다. step 1은 add, step 2는 mul, step 3은 최종 답(end_turn)이다.

uv run python practice/03-agent-loop/step2.py
[step 1] add({'a': 12, 'b': 8}) -> 20
[step 2] mul({'a': 20, 'b': 3}) -> 60
[step 3] end_turn -> 최종 답변: (12+8)*3 = 60 입니다.
모델 출력이라 스텝 수·문구·인자 표기는 달라질 수 있다. 예: 인자가 {'a': 12.0, 'b': 8.0}로 와 결과가 20.0으로 보이거나, 도구 호출 전 짧은 설명 text가 붙거나, 드물게 스텝이 한둘 더 늘 수 있다. 변하지 않는 핵심 3가지 — (1) add가 먼저 실행돼 20을 얻고, (2) 그 20으로 mul(20, 3)→60을 얻은 뒤, (3) end_turn으로 최종 답 60이 나온다. mul이 add보다 먼저 올 수 없다(의존) — 그래서 if 한 번이 아니라 while 반복이 필요했다.
history가 매 스텝 자란다. messages에는 스텝마다 assistant 턴(도구 요청)과 tool_result를 담은 user 턴이 쌓인다. create가 3번 불릴 때 매번 커진 messages 전체를 재전송한다(M1 stateless 그대로). 루프가 길수록 history가 커진다 → M4 메모리 압축의 동기(여기선 짚기만).
가드 체감 실험 — max_steps를 1로. step2.py의 max_steps = 8을 max_steps = 1로 바꿔 다시 실행해 보라. add(step 1)만 실행되고 루프 조건 1 < 1이 거짓이 되어 mul·최종 답 전에 잘리며 아래가 찍힌다: 
[step 1] add({'a': 12, 'b': 8}) -> 20
[max_steps=1 도달 — 루프를 강제 종료했어요]
가드가 없으면 모델이 종료하지 않고 도구를 계속 부를 때 루프가 무한히 돌아 토큰·비용이 폭주한다. max_steps는 watchdog / 재시도 상한 같은 안전장치다. 확인 후 8로 되돌려 둔다.
막히면:
  • 루프가 안 끝난다 / 토큰·비용 폭주 → 종료 분기 if resp.stop_reason != "tool_use":가 틀렸거나 max_steps 가드가 없다. 종료 조건과 while step < max_steps 상한부터 확인한다.
  • [max_steps 도달 …]가 찍히며 최종 답 없이 끝남 → 두 경우다. (a) 정답 경로인데 상한이 너무 낮음 → max_steps를 늘린다. (b) 모델이 계속 도구만 부름 → SYSTEM/도구 description이 애매하거나 종료 분기가 안 걸리는지 본다.
  • BadRequestError(400) "tool_use ids … without tool_result" → tool_use에 답하는 tool_result가 빠졌거나 tool_use_id가 안 맞는다. 매 스텝 tool_use 하나당 같은 id의 tool_result 하나를 만들어 user 턴으로 append했는지 확인. (M2 교훈: SDK 400은 값보다 필드 이름·id 매칭부터.)
  • BadRequestError(400)인데 위 문구가 아님 → 루프 안에서 resp.content를 통째로 append했는지 확인({"role":"assistant","content": resp.content}). block.text만 문자열로 넣으면 tool_use 블록이 유실돼 다음 create가 깨진다.
  • 모델이 도구를 안 쓰고 그냥 "60"이라 답함(step 없이 바로 end_turn) → 암산해 버린 것이다. SYSTEM의 암산 금지를 강화하고(반드시 도구만, 한 번에 한 연산), create(...)에 tools=tools를 넘겼는지 확인한다.
  • 최종 텍스트가 비거나 StopIteration → stop_reason을 확인하지 않고 도구 스텝의 응답에서 text를 뽑으려 했다. 최종 text는 end_turn(종료 분기)의 resp에서 뽑는다.
  • tool_result가 이상하게 들어감 / content 타입 오류 → run_tool 반환이 문자열이어야 한다. add/mul이 str(...)로 반환하는 이유다(숫자를 그대로 넣지 말 것).
  • AuthenticationError(401) → ANTHROPIC_API_KEY 미설정/오타. echo $ANTHROPIC_API_KEY로 확인(step1은 API를 안 부르니 키 없이도 됨).

Hermes 만들기

이번 단계: M2의 chat_with_tools(도구 1-step 왕복, if) 위에 while 승격과 새 도구 write_file·run_bash를 얹어 코딩 에이전트를 완성한다. 개념↔코드 매핑: 개념의 ReAct(사고→행동→관찰) 반복 = 아래 agent.py의 while 한 바퀴(추론 담긴 resp → run_tool 실행 → tool_result 관찰), "다 될 때까지" = stop_reason != "tool_use"가 될 때까지 반복, multi-step(도구 연쇄) = 그 루프가 2바퀴 이상 도는 것. M2의 1-step은 이 루프가 딱 1바퀴 돌고 end_turn인 특수 케이스다.

전제: M2까지 만든 clone-project/hermes/(config.py, llm.py의 ask/chat/stream_chat/chat_with_tools, tools.py의 read_file, REPL __main__.py) 위에 더한다. 이번엔 새 파일 agent.py를 만들고, tools.py에 도구 둘을 추가, config.py에 한 줄 추가, 그리고 llm.py·__main__.py를 정리한다. M0~M1 함수(ask/chat/stream_chat)는 그대로 둔다. 참조 해답: clone-project/_solution/03-agent-loop/hermes/ (막히면 diff로 대조).
실습과의 관계: "직접 사용해보기"에서 add·mul(가짜 계산기 도구)로 눈으로 본 while 루프·종료 조건·max_steps가 여기서도 똑같다. 차이는 둘뿐: ① 소재가 실제 파일을 만드는 도구(write_file·run_bash), ② 실습은 한 스크립트에 루프를 절차적으로 펼쳤지만, Hermes는 같은 루프를 agent.py의 class Hermes.run으로 캡슐화하고 도구는 tools.py로 분리한다.

M2 → M3: if를 while로 (before / after)

지금 무엇을/왜: 이번 모듈의 전부는 M2의 if 1-step을 while 루프로 승격하는 것이다. 새 API 개념은 없다 — 제어 흐름(control flow)만 바뀐다. 먼저 두 그림을 나란히 보자(개념용 축약 — 실제 타이핑은 아래 3)에서 한다).

# BEFORE — M2 llm.py::chat_with_tools  (if · 도구 1-step, 개념용 축약)
def chat_with_tools(messages):
    resp = client.messages.create(..., tools=TOOLS, messages=messages)   # 1차 호출
    if resp.stop_reason != "tool_use":            # 도구 안 부르면 여기서 끝
        messages.append({"role": "assistant", "content": resp.content})
        return text(resp)
    messages.append({"role": "assistant", "content": resp.content})       # 도구 1회분 append
    tool_results = [ ... run_tool(...) ... ]
    messages.append({"role": "user", "content": tool_results})
    resp2 = client.messages.create(..., tools=TOOLS, messages=messages)  # 2차 호출 (하드코딩·1회뿐)
    messages.append({"role": "assistant", "content": resp2.content})
    return text(resp2)
# AFTER — M3 agent.py::Hermes.run  (while · multi-step, 개념용 축약)
def run(self, user_msg):
    self.messages.append({"role": "user", "content": user_msg})
    step = 0
    while step < MAX_STEPS:                                # ← if 를 감싼 while + 가드
        step += 1
        resp = client.messages.create(..., tools=TOOLS, messages=self.messages)  # 매 스텝 1회
        self.messages.append({"role": "assistant", "content": resp.content})     # 매 스텝 append
        if resp.stop_reason != "tool_use":     # ← M2의 그 테스트 = 이제 '종료' 분기
            return text(resp)
        tool_results = [ ... run_tool(...) ... ]           # ← M2와 '완전히 동일'
        self.messages.append({"role": "user", "content": tool_results})  # ← 루프 top 으로
    return "[max_steps 도달 — 루프 강제 종료]"               # ← 새 가드 탈출

바뀐 것은 딱 다섯 곳이다:

  1. if → while + 가드: 종료 조건 테스트(!= "tool_use")는 그대로다. 한 번 검사하고 return하던 것을, 매 반복 검사해 end_turn이 나올 때까지 돈다. 상한은 while step < MAX_STEPS.
  2. 하드코딩 "2차 호출" 제거: M2의 별도 resp2 2차 호출이 사라진다 — 루프가 다음 바퀴에서 자연히 그 역할을 한다.
  3. 도구 실행·tool_result 수집 블록은 M2와 100% 동일: 코드가 한 글자도 안 바뀐다. "루프로 감쌌을 뿐"의 실체가 이 부분.
  4. assistant append를 루프 상단 1회로: M2에서 두 분기에 각각 있던 append를 create 직후 한 번으로 합친다.
  5. (위치) llm.py의 함수 → agent.py의 class Hermes.run 메서드. history를 인자 messages로 받던 것을 self.messages로 소유한다.
핵심 한 줄: 도구 왕복 4단계·tool_use_id 매칭·assistant 통째 append·tool_result를 user 턴으로 회신 — 전부 M2 그대로다. M3은 이 왕복을 while로 감싸 반복하는 것뿐이다.

1) hermes/config.py — MAX_STEPS 추가

지금 무엇을/왜: 이제 실제로 실행되는 함수 둘. read_file 함수 아래에 이어서 추가한다. 반환은 반드시 문자열(그대로 tool_result의 content가 된다)이라는 규칙은 M2와 같다.

# hermes/tools.py  (read_file 함수 아래에 두 함수 추가)
def write_file(path: str, content: str) -> str:
    """content를 path에 쓰고, 짧은 확인 문자열을 반환한다."""
    with open(path, "w", encoding="utf-8") as f:
        f.write(content)
    return f"{len(content)} bytes를 {path}에 저장했다."


def run_bash(cmd: str) -> str:
    """셸 명령을 실행하고 stdout(+stderr)을 문자열로 반환한다.

    ⚠️ 위험 — 학습용. 모델이 요청한 임의의 셸 명령을 '검증 없이 그대로' 실행한다.
    rm 같은 파괴적 명령도 그대로 돌아가므로 실제 서비스에선 절대 금물이다.
    실행 전 사용자 승인(승인 게이트)은 M5에서 추가한다. 지금은 신뢰할 수 있는
    로컬 학습 환경에서만 쓴다.
    """
    result = subprocess.run(cmd, shell=True, capture_output=True, text=True)
    return (result.stdout + result.stderr) or "(출력 없음)"   # 빈 문자열이면 400 → 대체 문구
⚠ run_bash는 위험하다 — 학습용: 모델이 요청한 임의의 셸 명령을 검증 없이 그대로 실행한다. rm -rf 같은 파괴적 명령도 그대로 돌아간다. 그래서 함수 위에 경고 주석을 반드시 달았다. 지금은 신뢰할 수 있는 로컬 학습 환경에서만 쓰고, 신뢰 못 할 명령은 절대 넣지 말 것. 실행 전 사용자에게 confirm을 받는 "승인 게이트"는 M5에서 붙인다 — M3의 run_bash는 경고만 달고 무조건 실행한다.

지금 무엇을/왜: 디스패처에 분기 둘을 더한다. 기존 read_file 분기는 그대로 두고 run_tool 전체를 아래로 교체한다.

# hermes/tools.py  (기존 run_tool 을 아래 내용으로 교체 — write_file·run_bash 분기 추가)
def run_tool(name: str, tool_input: dict) -> str:
    """도구 이름으로 실제 함수를 부르는 디스패처.
    반환은 반드시 문자열 — 그대로 tool_result 의 content 로 들어간다."""
    if name == "read_file":
        return read_file(tool_input["path"])
    if name == "write_file":
        return write_file(tool_input["path"], tool_input["content"])
    if name == "run_bash":
        return run_bash(tool_input["cmd"])
    return f"[unknown tool: {name}]"

3) hermes/agent.py 신설 — class Hermes.run (★ agent loop)

지금 무엇을/왜: 이 파일이 이번 모듈의 심장이다. M2에서 llm.py에 있던 도구 왕복을 새 파일 agent.py의 class Hermes로 옮기고 while로 승격한다. 먼저 껍데기 — import와 __init__. 여기서 history 소유권이 __main__에서 Hermes로 이동한다(M2에선 REPL의 지역변수 messages였다).

# hermes/agent.py
"""Hermes 본체 — agent loop(ReAct)를 담은 class Hermes.

M2 llm.chat_with_tools 의 도구 1-step 왕복(if)을 while 루프로 '승격'한 것.
도구 왕복 4단계·tool_use_id 매칭은 M2와 완전히 동일하고, 그 왕복을
'stop_reason 이 tool_use 가 아닐 때까지 반복'으로 감쌌을 뿐이다."""
from .llm import client, SYSTEM
from .config import MODEL, MAX_TOKENS, MAX_STEPS
from .tools import TOOLS, run_tool


class Hermes:
    def __init__(self):
        # 대화 history를 Hermes가 소유한다 (M2에선 __main__의 지역변수 messages였다).
        # 이 self.messages 가 M4에서 Memory 객체로 교체될 자리다.
        self.messages = []
정의 — self.messages(history 소유권 이동): M2까지 대화 history는 __main__의 지역변수였다. 이제 Hermes가 인스턴스 상태로 소유한다 — run()을 여러 번 불러도 같은 self.messages에 누적돼 멀티턴이 유지된다. 이 self.messages가 M4에서 Memory 객체로 교체될 자리다.

지금 무엇을/왜: 핵심 메서드 run. before/after의 AFTER를 그대로 코드로 옮긴다. while 한 바퀴 = ReAct 한 사이클(추론→행동→관찰). 주석의 ← 표시가 M2 대비 바뀐 지점이다. class Hermes 안에, __init__ 아래에 이어서 작성한다.

# hermes/agent.py  (class Hermes 안에 run 메서드를 이어서 작성)

    def run(self, user_msg: str) -> str:
        """user_msg를 받아, stop_reason이 tool_use가 아닐 때까지 도구를 반복 실행한다.
        while 한 바퀴 = ReAct 한 사이클(추론→행동→관찰). MAX_STEPS로 무한 루프를 막는다."""
        self.messages.append({"role": "user", "content": user_msg})

        step = 0
        while step < MAX_STEPS:                 # ← M2의 if를 감싼 while + 무한 루프 가드
            step += 1
            # 매 스텝: 커진 history 전체를 통째로 재전송(M1 stateless 그대로).
            resp = client.messages.create(
                model=MODEL,
                max_tokens=MAX_TOKENS,
                system=SYSTEM,
                tools=TOOLS,
                messages=self.messages,
            )
            # assistant 응답을 '통째로' append (tool_use 블록 보존).
            # M2에선 두 분기에 각각 있던 걸, 여기선 루프 상단 1회로 합쳤다.
            self.messages.append({"role": "assistant", "content": resp.content})

            # 종료 분기 — M2 chat_with_tools의 '그 테스트' 그대로.
            # tool_use가 아니면(end_turn/max_tokens/refusal) 최종 답으로 종료.
            if resp.stop_reason != "tool_use":
                return "".join(b.text for b in resp.content if b.type == "text")

            # 여기부터는 M2와 '완전히 동일' — tool_use 블록마다 실행해 tool_result 수집.
            tool_results = []
            for block in resp.content:
                if block.type == "tool_use":
                    print(f"  ↳ step {step}: {block.name}({block.input})")  # 루프가 도는 걸 눈으로
                    result = run_tool(block.name, block.input)   # 우리가 실행
                    tool_results.append({
                        "type": "tool_result",
                        "tool_use_id": block.id,   # tool_use 의 id와 반드시 매칭
                        "content": result,          # 반드시 문자열
                    })
            # 결과를 user 턴으로 회신하고 루프 top으로 → M2의 '2차 호출'을 루프가 대체.
            self.messages.append({"role": "user", "content": tool_results})

        # MAX_STEPS까지 돌아도 안 끝났다 → 강제 종료(가드 탈출).
        return "[max_steps 도달 — 루프를 강제 종료했어요]"
개념↔코드 매핑(한눈에):
  • ReAct 사고→행동→관찰 = while 한 바퀴 (resp에 추론 → run_tool로 행동 → tool_result로 관찰).
  • "다 될 때까지" = if resp.stop_reason != "tool_use": return ... 가 나올 때까지 반복. (tool_use=계속 / end_turn·max_tokens·refusal=종료.)
  • multi-step = 이 루프가 2바퀴 이상 도는 것(도구 A 결과를 보고 도구 B).
  • 무한 루프 가드 = while step < MAX_STEPS + 탈출 시 [max_steps 도달 …].
print(f" ↳ step ...") 한 줄은 루프가 도는 걸 눈으로 보려는 것 — M7의 실행 trace 로깅의 씨앗이다.

# hermes/__main__.py
from .agent import Hermes

def main():
    print("Hermes REPL — 빈 입력 또는 'exit'로 종료 (이제 도구를 여러 스텝 이어 쓴다)\n")
    hermes = Hermes()                      # history 소유권이 Hermes로 이동 (self.messages)
    while True:
        user = input("you> ").strip()
        if user == "" or user == "exit":   # 종료 조건
            print("bye.")
            break
        answer = hermes.run(user)          # agent loop(while)는 이 안에서. user append 도 run이 처리
        print("hermes>", answer)

if __name__ == "__main__":
    main()
M2와의 diff 주의: ① import가 from .llm import chat_with_tools → from .agent import Hermes로 바뀐다. ② messages = []와 messages.append({"role": "user", ...}) 두 줄이 사라진다(이제 Hermes가 담당). ③ 호출이 chat_with_tools(messages) → hermes.run(user)로 바뀐다.
