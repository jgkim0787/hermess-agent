Hermes 완성 (Capstone)

개념

M6를 닫으며 우리는 못을 세 개 박아 뒀다 — ② "검색이 맞는 chunk를 물어왔는지 측정하지 못한다 → M7 eval", ③ "무슨 도구를 언제·왜 불렀는지 print로 흘려볼 뿐 남지 않는다 → M7 trace", ④ "이제 Hermes는 코딩(M2~M4)·자율(M5)·RAG(M6) 세 성격을 다 가졌다 → M7에서 한 데모로 통합". 이 마지막 모듈이 그 셋을 한꺼번에 회수하며 과정을 닫는다. M2 첫 도구부터 여기까지 왔다.

★ 그런데 첫 못부터 박고 시작하자 — "통합"은 새 코드가 아니다. _solution/06-rag-knowledge/hermes/를 열어 보면 read_file·write_file·run_bash·update_plan·search_docs 다섯 도구가 이미 한 agent.py 루프 안에 다 통합돼 있고 memory.py의 compaction도 살아 있다. 그래서 M7이 정말로 새로 만드는 건 딱 둘이다 — 관찰(trace)과 측정(eval). 즉 M6까지의 Hermes는 "할 수는 있으나 무슨 일을 했는지 남지 않고, 잘했는지 측정도 안 되는" 실행기였고, M7은 여기에 능력이 아니라 신뢰성·운영 가능성을 더한다. 비유하면 기능이 다 돌아가는 서비스에 로깅·트레이싱·테스트를 붙여 "운영 가능"하게 만드는 마지막 한 걸음이다.

표기 규약(★ 세 섹션 공통): 개념·패턴은 원어/한글로 — observability/"관찰", trace/"실행 trace", eval/"평가·채점", "통합", "복합 데모", "기대 동작", grounding/"근거". 코드·식별자·값·파일은 코드 표기로 — trace.py, log_event, logs/trace.jsonl, LOG_DIR, LOG_FILE, eval.py, EVAL_CASES, check, agent.py, run_tool, confirm, DANGEROUS_TOOLS, search_docs, kb/, DEPLOY_NOTES.md, event 6키(ts·step·tool·input·result_preview·approved). 헷갈리기 쉬운 쌍을 미리 갈라 둔다 — 개념 "observability" vs 함수 log_event()(관찰의 실체) / 개념 "trace" vs 파일 logs/trace.jsonl(trace의 실체) / 개념 "eval" vs 스크립트 eval.py + 함수 check()(채점의 실체).

통합은 이미 끝났다 — 증명은 복합 데모로

M3에서 agent loop를 제대로 만든 뒤로, 새 능력을 붙이는 방법은 "루프를 고치는 것"이 아니라 "도구를 더하는 것"이었다 — M2 read_file, M3 write_file/run_bash, M5 update_plan, M6 search_docs. 루프는 고정, 도구만 쌓였다. 그러니 "세 flavor 통합"은 우리가 따로 할 일이 아니라 이미 자동으로 끝나 있다 — 다섯 도구가 한 루프에 다 꽂혀 있으니까. 비유하면 잘 설계된 플러그인 아키텍처다: 코어(loop)는 그대로 두고 기능은 플러그인(도구)으로 얹는다. 통합을 "증명"하는 방법도 코드 합치기가 아니라, 여러 플러그인을 한 시나리오로 관통시키는 통합 테스트 — 즉 다섯 도구를 다 요구하는 복합 태스크 한 번이다.

그 한 문장짜리 복합 태스크가 이것이다(kb/의 Nimbus 문서는 M6에서 검색하던 그 문서 그대로다):

you> 우리 팀 배포 도구 Nimbus 설정을 Hermes 프로젝트에 정리해두려고 해.
     hermes/ 폴더 코드에서 Hermes가 가진 도구 목록을 확인하고, Nimbus의 프로덕션
     배포 명령과 max_parallel 기본값을 문서에서 찾아서, 이 둘을 정리한
     DEPLOY_NOTES.md 문서를 만들어줘.

  step 1  update_plan([...])             계획      (M5 자율)     게이트 없음(자기 상태)
  step 2  run_bash("ls hermes/")         코드 읽기  (M2~M3)       승인 요청 → y
  step 3  search_docs("Nimbus 배포 …")   문서 검색  (M6 RAG)      읽기 전용(게이트 없음)
  step 4  write_file("DEPLOY_NOTES.md")  결과 작성  (M5 자율)     승인 요청 → y
  ──      end_turn                        최종 요약 답변          (도구 아님)

이 한 번의 run()이 관통하는 것 — 다섯 도구(계획·읽기·검색·쓰기, run_bash까지면 다섯), 양쪽 게이트 경로(자동 실행 + 승인 요청), RAG(kb/ 검색), 계획(update_plan), 메모리(길어지면 M4 compaction이 접는다), grounding(검색한 근거로 문서 작성). M2~M6이 한 실행에 다 들어 있다. 새 코드는 없다 — 실행이자 시연이다. (도구 호출 순서·횟수는 모델 재량이라 정확히 이대로는 아니고 "대략 이렇게 흐른다"이다.) 남은 문제는 하나 — 이 실행이 실제로 무슨 경로를 밟았는지, 그리고 잘했는지를 어떻게 확인하나? 그게 M7의 두 새 개념이다.

무슨 일이 있었나 — observability

정의 — observability(관찰가능성): 에이전트가 무슨 일을 왜 했는지(어떤 도구를 언제·어떤 입력으로 불렀고, 결과·승인 여부는 무엇이었는지)를 나중에 볼 수 있게 구조화해 기록해 두는 성질. 비유하면 서버의 구조적 로깅 + 분산 트레이싱 — print 디버깅을 영속 로그로 승격한 것.

M6까지 Hermes는 도구를 부를 때마다 print(f" ↳ step {step}: {block.name}(...)")로 화면에 흘려보내기만 했다 — 프로그램이 끝나면 사라진다. 다시 보고 싶어도 없다. observability는 그걸 디스크에 구조화해 남기는 것이다: 각 도구 호출의 시각·도구 이름·입력·결과 요약·승인 여부를 logs/trace.jsonl에 한 줄씩 append한다.

왜 필요한가 — 에이전트는 비결정적이다: LLM은 stateless(M1)라 같은 질문에도 매번 다른 경로를 밟을 수 있다 — 이번엔 run_bash로, 다음번엔 read_file로 도구 목록을 볼 수도 있다. 그래서 "왜 이렇게 답했지?", "검색을 했나 안 했나?"를 답하려면 그 실행이 남긴 기록(trace)이 반드시 있어야 한다. 코드는 결정적이라 다시 돌리면 되지만, 에이전트는 "그때 그 실행"이 유일하다 — 기록해 두지 않으면 사라진다.

관찰의 실체는 hermes/trace.py의 함수 하나다. 부작용 없이 한 도구 호출을 JSON 한 줄로 파일에 붙이기만 한다:

# hermes/trace.py — print(흘려보내고 사라짐)를 '구조화된 영속 로그'로 승격한 것.
import json, os, datetime
from .config import LOG_DIR, LOG_FILE          # LOG_FILE = "logs/trace.jsonl"

def log_event(step, tool, tool_input, result, approved=True):
    os.makedirs(LOG_DIR, exist_ok=True)         # logs/ 없으면 생성
    event = {
        "ts": datetime.datetime.now().isoformat(timespec="seconds"),
        "step": step, "tool": tool, "input": tool_input,
        "result_preview": str(result)[:200],    # 결과는 '요약'만 (전체 덤프 금지)
        "approved": approved,                   # 거부(게이트)도 기록 — '무엇을 막았나'도 관찰
    }
    with open(LOG_FILE, "a", encoding="utf-8") as f:
        f.write(json.dumps(event, ensure_ascii=False) + "\n")   # jsonl 한 줄 = event 하나

형식이 jsonl(줄 하나 = event 하나)인 이유는 pro 독자에겐 설명이 필요 없다 — append-only라 실행 중 안전하고, 사후에 한 줄씩 파싱해 집계·필터하기 쉽다(곧 eval이 이걸 기계로 읽는다). result_preview가 str(result)[:200]인 건 search_docs/read_file의 결과가 길기 때문 — trace는 "무슨 일이 있었나"의 요약이지 전체 덤프가 아니다.

한 번의 실행이 남긴 경로 — trace

정의 — trace(실행 trace): 한 번의 실행에서 일어난 도구 호출들의 시간순 기록 (각 event = 도구·입력·결과·시각). observability의 구체적 산출물이자, 곧 볼 eval의 증거다. 비유하면 요청 하나가 남긴 trace/span 로그, 함수 호출 스택의 시계열판.

위 log_event가 한 줄씩 쌓은 logs/trace.jsonl을, 복합 데모를 한 번 돌린 뒤 열어 보면 이런 모양이다 — 여러 줄을 시간순으로 읽으면 그 run() 한 번이 밟은 경로 전체가 재구성된다:

{"ts": "2026-07-27T14:03:11", "step": 1, "tool": "update_plan", "input": {"steps": ["도구 목록 파악", "Nimbus 배포 명령·기본값 검색", "DEPLOY_NOTES.md 작성"]}, "result_preview": "계획 저장됨: 3단계", "approved": true}
{"ts": "2026-07-27T14:03:14", "step": 2, "tool": "run_bash", "input": {"cmd": "ls hermes/"}, "result_preview": "__init__.py\nagent.py\nconfig.py\nllm.py\nmemory.py\nrag.py\ntools.py\ntrace.py", "approved": true}
{"ts": "2026-07-27T14:03:20", "step": 3, "tool": "search_docs", "input": {"query": "Nimbus 프로덕션 배포 명령 max_parallel 기본값"}, "result_preview": "max_parallel 키는 동시에 배포할 서버 수… 기본값은 4다.\n\n---\n\n프로덕션 배포는 nimbus ship …", "approved": true}
{"ts": "2026-07-27T14:03:31", "step": 4, "tool": "write_file", "input": {"path": "DEPLOY_NOTES.md", "content": "# Nimbus 배포 메모\n- 프로덕션 배포: nimbus ship\n- max_parallel 기본값: 4"}, "result_preview": "파일을 저장했습니다: DEPLOY_NOTES.md", "approved": true}

계획 → 코드 읽기 → 검색 → 파일 쓰기가 네 줄로 그대로 보인다. 각 event의 6키 — ts(시각)·step(루프 스텝)·tool(도구명)·input(입력)·result_preview(결과 앞 200자)·approved. 특히 approved는 거부(게이트에서 막힌 것)도 false로 기록한다 — observability는 "무엇을 했나"뿐 아니라 "무엇을 막았나"까지다.

훅은 어디에 거나 — M5가 게이트를 건 바로 그 길목(설계①): log_event는 agent.py::Hermes.run의 for block in resp.content 루프에 건다 — 도구가 실행되는 지점과 거부되는 지점, 두 곳에 한 줄씩. 왜 run_tool(tools.py) 안이 아닌가? update_plan은 run_tool을 안 거치고(에이전트 자신의 상태라 agent.py가 직접 처리 — M5 설계), 거부(denied)도 agent.py에서만 일어난다. 모든 도구 결정이 빠짐없이 지나가는 단 하나의 길목이 이 for-loop다 — 그래서 M5도 승인 게이트를 여기 뒀다. "에이전트의 모든 행동이 지나가는 곳 하나를 잠그면(게이트) / 들여다보면(로깅) 전체가 잠기고 / 전체가 보인다." run_tool에 걸면 update_plan과 거부가 trace에서 누락된다.

잘했나 — eval

정의 — eval(evaluation): 에이전트가 정해둔 입력에 기대한 대로 동작하는지(옳은 도구를 불렀나 · 답에 정답이 들어갔나)를 자동으로 채점해 통과/실패로 판정하는 것. 비유하면 코드의 단위 테스트 / CI 어서션 — 단, 대상이 LLM 에이전트의 비결정적 행동이다.

"Hermes가 잘 하나?"를 눈대중이 아니라 재현 가능한 체크로 바꾼다. 정해둔 질문(둘 다 M6 kb/의 Nimbus 사실 근거)에 대해 기대 동작 두 가지를 검사한다:

  • ① 옳은 도구를 불렀나 — 사실 질문이니 search_docs를 불렀어야 한다. 어떻게 아나? 방금 만든 logs/trace.jsonl을 읽어 tool 값에 "search_docs"가 있는지 본다.
  • ② 답에 정답 문자열 — 최종 답에 "4"(동시 배포 서버 수 기본값) / "nimbus ship"(프로덕션 배포 명령)이 들어갔는지 본다.

두 체크가 모두 참이면 그 케이스 PASS. 케이스별로 trace를 비워 그 실행만 격리한 뒤 돌리고, trace를 읽어 판정한다:

# eval.py (clone-project 루트) — 정해둔 질문에 Hermes가 '기대대로' 동작하는지 자동 채점.
EVAL_CASES = [
    ("Nimbus에서 동시에 배포하는 서버 수 기본값이 몇이야?", "search_docs", "4"),
    ("Nimbus로 프로덕션 배포하는 명령이 뭐야?",              "search_docs", "nimbus ship"),
]

def check(question, want_tool, want_substring):
    open(LOG_FILE, "w").close()                       # 이 케이스의 trace만 남게 비운다
    answer = Hermes().run(question)                   # fresh 메모리로 실행
    events = [json.loads(line) for line in open(LOG_FILE, encoding="utf-8")]
    tool_ok = want_tool in {e["tool"] for e in events}   # ← trace가 '도구 불렀나'의 증거
    ans_ok  = want_substring in answer
    return tool_ok and ans_ok
# main(): 전부 통과면 sys.exit(0), 아니면 sys.exit(1) — CI처럼 exit code로 성패

1/2 통과

이 케이스 1의 FAIL은 만든 게 아니라 실제로 재현된다 — 아래 "정직한 한계"에서 바로 그 원인을 연다.

★ trace와 eval은 한 이야기다(설계②): check가 "search_docs를 불렀나"를 확인하는 유일한 근거가 바로 우리가 방금 만든 logs/trace.jsonl이다. 두 새 코드를 따로 소개하지 않는 이유가 이것이다 — 기록(observability)이 없으면 "무슨 도구를 불렀나"를 알 수 없고 → 채점(eval)도 못 한다. 관찰이 먼저고, 측정은 그 위에 선다. (그래서 eval 질문은 전부 읽기 전용으로 골랐다 — write_file/run_bash가 끼면 비대화형 실행에서 M5 confirm()의 input()이 EOFError로 fail-closed 거부돼 결과가 뒤틀리기 때문. search_docs만으로 답할 사실 질문이라 게이트를 안 건드린다.)

★ 정직한 한계 — 문자열 eval은 취약하다

이 채점은 문자열 매칭이라 취약하다 — 그리고 방금 그 실물을 봤다. 위 케이스 1이 FAIL인 이유는 eval.py가 고장나서가 아니다: 모델이 검색어를 "동시에 배포하는 서버 수"에서 "동시 배포"처럼 줄여 보내면, kb의 정답 문단("동시에 배포하는 … max_parallel 기본값은 4다")과 TF-IDF 어휘가 안 겹쳐 검색이 빗나간다(M6에서 손으로 확인한 그 한계가 그대로 재발한 것). search_docs는 불렀지만(True) 엉뚱한 문단을 물어와 답에 "4"가 없다 — eval이 이 "근거 없는 답"을 정확히 잡아냈다. 일반화하면: "답에 '4'가 들어갔나"는 엉뚱한 문맥의 '4'도 통과시킬 수 있고(정밀도 문제), 정답을 다르게 표현하면(예: "넷") 실패할 수 있다(재현율 문제 — 방금 본 그 경우). 이건 버그가 아니라 입문용 골격이다. 진짜 eval은 정답셋 규모를 키우고 + LLM-as-judge(다른 모델이 답의 정확성을 채점)로 check의 판정부 한 곳만 갈아끼운다 — 격리·실행·trace 읽기 구조는 그대로다. 이는 M6의 정직성과 똑같은 모양이다: "TF-IDF는 진짜 embedding이지만 어휘 유사도" ↔ "문자열 eval은 진짜 eval이지만 취약". 골격은 프로덕션과 같고, judge(채점기) 한 곳만 교체하면 실무 eval이 된다.

루프는 이번에도 그대로

이 모듈의 조용한 클라이맥스다. 관찰(trace)이라는 큰 걸 붙였는데 — agent.py의 while 루프는 한 줄도 재구성하지 않았다. while·stop_reason 종료 분기·tool_use↔tool_result 왕복·tool_use_id 매칭·confirm() 게이트·self.memory — M3/M5와 byte 단위로 동일하다. 우리가 한 건 기존 줄을 옮기지 않고, for-loop 안 두 결과 지점에 log_event(...)를 삽입한 것뿐이다(+ import 1줄):

from .trace import log_event   # [+] 파일 상단 import 한 줄

# ... Hermes.run 의 for block in resp.content 루프 안 (기존 구조 그대로) ...
        if block.name in DANGEROUS_TOOLS and not confirm(block.name, block.input):
            print("  [거부됨] ...")                                        # (M5 기존)
            log_event(step, block.name, block.input, DENIED_MSG, approved=False)  # [+] 거부도 관찰
            tool_results.append({... "content": DENIED_MSG, "is_error": True})    # (M5 기존)
            continue                                                       # (M5 기존)

        if block.name == "update_plan":
            result = self._update_plan(block.input["steps"])              # (M5 기존)
        else:
            result = run_tool(block.name, block.input)                    # (M6 기존)
        log_event(step, block.name, block.input, result, approved=True)   # [+] 실행됨을 관찰
        tool_results.append({"type": "tool_result", "tool_use_id": block.id, "content": result})  # (기존)
왜 붙여도 안 흔들리나: 관찰은 로직을 바꾸지 않는다 — 부작용 없는 곁가지라 붙여도 에이전트의 행동은 그대로다. 그리고 update_plan·read_file·run_bash·search_docs·거부 — 모든 도구 결정이 위 (A)/(B) 중 하나를 지나므로 전부 자동 기록된다. 이건 M3에서 루프를 제대로 만들어 둔 덕이다: M4 메모리(llm/__main__ 무변경), M5 게이트(memory 무변경), M6 RAG(agent.py 무변경), 그리고 M7 로깅 — 루프는 계속 그대로였다. 이 문장으로 과정 전체를 닫는다: "잘 만든 agent loop는 능력을 붙여도(도구), 안전을 붙여도(게이트), 관찰을 붙여도(로깅) 흔들리지 않는다."

여기서 멈추고, 이렇게 이어간다 — 다음 단계

이 과정은 여기서 끝난다. 우리는 손으로 agent loop·메모리·계획·게이트·RAG·관찰·측정을 다 만들어 봤다. 그래서 이제 실무 도구를 써도 블랙박스가 아니다 — 각각이 "우리가 손으로 만든 골격의 어디를 대체하는지" 보인다. 코스 밖에서 이어 배울 것을 "우리가 만든 것 → 그 실무판"으로 가리키며 마친다.

다음 단계 포인터 (실제 존재하는 것만):
  • Claude Agent SDK / 자동 tool_runner — 우리가 손으로 짠 while 루프(M3)의 실무판. SDK의 client.beta.messages.tool_runner(+@beta_tool)가 tool_use↔tool_result 왕복을 자동화한다. 루프의 메커니즘을 손으로 이해했으니 이제 SDK를 써도 블랙박스가 아니다.
  • MCP (Model Context Protocol) — 우리 tools.py의 하드코딩 도구를 표준 프로토콜로 노출해 재사용·공유. read_file·search_docs를 MCP 서버로 빼면 다른 에이전트도 그대로 쓴다.
  • 진짜 embedding + vector DB — M6에서 못 박은 embed() seam 한 곳의 교체: TF-IDF(어휘) → 신경망 임베딩(의미, 예: sentence-transformers), 색인 → pgvector·Chroma·FAISS. 파이프라인은 그대로, 유사도만 어휘→의미.
  • 진짜 observability / eval 플랫폼 — 우리 logs/trace.jsonl / eval.py의 실무판: LangSmith 같은 tracing 플랫폼, 그리고 정답셋 + LLM-as-judge 기반 eval(위 문자열 매칭의 취약함을 넘는 judge 교체).
  • 프롬프트 캐싱 · 비용 최적화 (+ 멀티에이전트) — M4의 토큰 비용 감각의 연장: 반복되는 system/도구 정의를 prompt caching으로 캐시해 비용↓. 그리고 멀티에이전트(오케스트레이터-워커)로 확장 — 이 학습 자료를 만든 하네스 자체가 그 예다.

한눈 정리

  • "통합"은 새 코드가 아니다. M2~M6에서 새 능력 = 새 도구였고 루프는 고정이라, 다섯 도구는 이미 한 agent.py 루프에 통합돼 있다. 통합의 증명은 코드 합치기가 아니라 다섯 도구를 다 요구하는 복합 데모 한 번(계획→읽기→검색→쓰기)을 돌려 보이는 것.
  • observability = "무슨 일을 왜 했나"를 남기기. M6의 print(흘려보내고 사라짐)를 log_event로 logs/trace.jsonl에 영속·구조화한다. 왜? 에이전트는 비결정적(M1 stateless)이라 "그때 그 실행"의 경로는 기록해야만 남는다.
  • trace = 한 실행이 남긴 도구 호출들의 시간순 기록. event 6키(ts·step·tool·input·result_preview·approved, 거부도 기록). 훅은 모든 도구가 지나는 단 한 길목(=M5 게이트 자리)인 agent.py for-loop에 건다 — run_tool이 아니라(설계①).
  • eval = 기대대로 했는지 자동 채점(단위 테스트/CI 어서션의 에이전트판). 두 체크 — ① 옳은 도구를 불렀나(= trace를 읽어 확인) + ② 답에 정답 문자열. ★ 기록이 없으면 채점도 없다(설계② — trace가 eval의 증거). 단 문자열 매칭은 취약하다(버그 아니라 골격 — 진짜는 정답셋+LLM-as-judge로 check 판정부만 교체).
  • ★ 루프는 이번에도 그대로 — 과정 완주. 로깅은 관찰 지점 추가일 뿐 agent.py while 구조는 M3 이후 무변경(M4·M5·M6 무변경 계보). "잘 만든 루프는 능력·안전·관찰을 붙여도 안 흔들린다." 다음 단계(Agent SDK·MCP·진짜 vector DB·진짜 observability/eval·캐싱)는 전부 "우리가 만든 골격 → 그 실무판"이다.

M6까지 Hermes는 도구 호출을 print(f" ↳ step ...")로 화면에 흘려보내기만 했다 — 끝나면 사라진다. log_event는 그걸 구조화된 로그로 영속시킨다: 각 도구 호출을 {ts, step, tool, input, result_preview, approved} 한 줄(jsonl)로 logs/trace.jsonl에 append. 여기선 에이전트를 돌리지 않고 복합 데모가 남길 법한 trace를 손으로 몇 줄 남긴 뒤, 그 파일을 다시 읽어 "어떤 도구가 몇 번 불렸나"를 재구성한다.

# step1.py — M7 실습 부품 ①: 미니 log_event 로 실행 trace 를 남기고, 그 파일을 다시 읽어 집계한다.
#            API 호출이 없다 → 키가 없어도 실행된다. 표준 라이브러리(json/os/datetime/collections)만.
import json
import os
import datetime
from collections import Counter

LOG_DIR = "logs"
LOG_FILE = "logs/trace.jsonl"


def log_event(step, tool, tool_input, result, approved=True):
    """한 번의 도구 호출을 JSON 한 줄(jsonl)로 LOG_FILE 에 append 한다.
    클론 hermes/trace.py 의 log_event 와 '같은 함수'다 — 실습은 이 부품만 손에 익힌다.
    result 는 앞부분만 잘라 저장한다 — trace 는 '무슨 일이 있었나'의 요약이지 전체 덤프가 아니다."""
    os.makedirs(LOG_DIR, exist_ok=True)                       # logs/ 없으면 만든다 (없으면 FileNotFoundError)
    event = {
        "ts": datetime.datetime.now().isoformat(timespec="seconds"),
        "step": step,
        "tool": tool,
        "input": tool_input,
        "result_preview": str(result)[:200],                  # 결과는 앞부분만(전체 덤프 금지)
        "approved": approved,                                 # 거부(게이트)도 기록 — '무엇을 막았나'도 관찰
    }
    with open(LOG_FILE, "a", encoding="utf-8") as f:
        f.write(json.dumps(event, ensure_ascii=False) + "\n")  # 한글 보존(ensure_ascii=False)


# ── 이 실습은 에이전트를 '돌리지 않는다'. 대신 복합 데모가 남길 법한 trace 를 손으로 남겨 본다:
#    계획(update_plan) → 코드 읽기(read_file) → 문서 검색(search_docs) → 파일 쓰기(write_file, 거부 후 재승인).
os.makedirs(LOG_DIR, exist_ok=True)     # logs/ 준비
open(LOG_FILE, "w").close()             # 이전 실행의 trace 를 비우고 시작(여러 번 돌려도 깨끗하게)

log_event(1, "update_plan",
          {"steps": ["hermes/ 도구 목록 파악", "Nimbus 배포 명령·max_parallel 검색", "DEPLOY_NOTES.md 작성"]},
          "계획 저장됨: 3단계")
log_event(2, "read_file", {"path": "hermes/tools.py"},
          "# hermes/tools.py — TOOLS=[read_file, write_file, run_bash, update_plan, search_docs] ...")
log_event(3, "search_docs", {"query": "Nimbus 프로덕션 배포 명령 max_parallel 기본값"},
          "nimbus.toml 의 max_parallel 키는 한 번에 동시에 배포하는 서버 수를 정한다. max_parallel 기본값은 4다.")
log_event(4, "write_file", {"path": "DEPLOY_NOTES.md", "content": "..."},
          "사용자가 이 도구 실행을 거부했습니다.", approved=False)   # 첫 시도: 승인 게이트에서 거부됨(M5)
log_event(5, "write_file", {"path": "DEPLOY_NOTES.md", "content": "..."},
          "241 bytes를 DEPLOY_NOTES.md에 저장했다.")                  # 재시도: 승인되어 실행됨

# ── 이제 '무슨 일이 있었나'를 재구성한다: 파일을 한 줄씩 읽어(json.loads) 도구별로 집계한다.
events = [json.loads(line) for line in open(LOG_FILE, encoding="utf-8")]
counts = Counter(e["tool"] for e in events)
denied = [e for e in events if not e["approved"]]

print(f"trace 파일: {LOG_FILE} — event {len(events)}개\n")
for e in events:
    flag = "" if e["approved"] else "   ← 거부됨(실행 안 함)"
    print(f"  [step {e['step']}] {e['tool']:<12} {e['input']}{flag}")
print(f"\n도구별 호출 횟수: {dict(counts)}")
print(f"거부된 호출: {len(denied)}개")

여기서 볼 것: print는 사라지지만 trace는 남아 재구성된다. 5줄을 시간순으로 읽으면 그 실행이 밟은 경로 전체가 되살아난다 — 계획 → 코드 읽기 → 문서 검색 → 파일 쓰기. 이게 observability다: 각 event에 시각·도구·입력·결과 요약·승인 여부가 박혀 있어, 프로그램이 끝난 뒤에도 "무슨 도구를 왜 불렀나"를 사후에 답할 수 있다. 에이전트는 비결정적(M1 — 같은 질문에 다른 경로)이라, 바로 이 기록이 있어야 "이번엔 뭘 했지?"에 답한다.
세 가지 설계 포인트.
  • ensure_ascii=False — 없으면 한글이 \uXXXX로 이스케이프돼 로그가 안 읽힌다. 위 result_preview의 한글이 그대로 보이는 이유다.
  • os.makedirs(LOG_DIR, exist_ok=True) — logs/가 없으면 open(...,"a")가 FileNotFoundError다. 첫 호출에서 폴더를 만든다.
  • approved=False도 남긴다 — step 4의 거부(승인 게이트가 막은 write_file)가 trace에 "approved": false로 박혔다. observability는 "무엇을 했나"뿐 아니라 "무엇을 막았나"도 포함한다(M5 게이트와 맞물림).

2) 채점 로직만 짜 보기 (API 없이)

이제 eval의 실체를 만든다 — 단, 에이전트를 돌리지 않고 채점 규칙(판정부)만 짠다. 한 케이스의 기대 동작은 두 가지: ① 옳은 도구를 불렀나(want_tool in tools_used — trace가 증거) + ② 답에 정답 문자열이 있나(want_substring in answer). 이 둘이 모두 참이면 PASS. 가짜 trace(도구 리스트) + 가짜 answer를 하드코딩해 이 규칙만 손에 익힌다 — 실제 실행에서 이 두 값을 어떻게 얻는지는 step3에서 본다.

# step2.py — M7 실습 부품 ②: eval 의 '채점 로직(판정부)'만 떼어 짜 본다.
#            에이전트를 '돌리지 않는다' → 하드코딩한 '가짜 trace + 가짜 answer'로 PASS/FAIL 규칙만 익힌다.
#            API 호출 없음 → 키가 없어도 실행된다(표준 라이브러리조차 안 쓴다 — 순수 파이썬).

# 한 케이스 = (질문, 이번 실행이 부른 도구들[=가짜 trace], 최종 답[=가짜 answer],
#             반드시 불렀어야 할 도구, 답에 있어야 할 문자열)
# ★ 같은 질문의 '두 가지 가능한 실행' — 에이전트는 비결정적이라(M1) 매번 같은 경로를 밟지 않는다.
CASES = [
    ("Nimbus 동시 배포 서버 수 기본값? (검색한 실행)",
     ["update_plan", "search_docs"],              # trace: 검색을 했다
     "문서에 따르면 max_parallel 기본값은 4다.",    # answer: '4'가 근거와 함께 있다
     "search_docs", "4"),
    ("Nimbus 동시 배포 서버 수 기본값? (검색 건너뛴 실행)",
     ["update_plan"],                             # trace: search_docs 를 '건너뛰었다'
     "글쎄, 한 4대쯤 아닐까?",                      # answer: '4'는 우연히 들어갔다(지어냄)
     "search_docs", "4"),
]


def check(question, tools_used, answer, want_tool, want_substring):
    """한 케이스를 채점한다 — 클론 eval.py::check 의 '판정부' 그대로.
    두 조건이 모두 참이어야 PASS: (1) 옳은 도구를 불렀나(trace로 확인) + (2) 답에 정답 문자열이 있나."""
    tool_ok = want_tool in tools_used          # ← trace(도구 리스트)가 증거다
    ans_ok = want_substring in answer
    passed = tool_ok and ans_ok
    print(f"[{'PASS' if passed else 'FAIL'}] {question}")
    print(f"    {want_tool} 호출? {tool_ok} · 답에 '{want_substring}' 포함? {ans_ok}")
    return passed


results = [check(*c) for c in CASES]
print(f"\n{sum(results)}/{len(results)} 통과")

실제 eval.py와의 차이는 딱 하나 — tools_used·answer를 어디서 얻나. step2는 그 둘을 손으로 하드코딩했다. 클론 eval.py는 같은 check 판정부를 쓰되, 그 둘을 진짜 실행에서 얻는다: Hermes().run(question)이 answer를, 그 실행이 남긴 logs/trace.jsonl이 tools_used를 준다. 그 연결을 다음 step3에서 직접 본다.

# ★ 전제: '아래 Hermes 만들기(클론)' 섹션에서 hermes/trace.py 를 만들고 agent.py 에 log_event 훅을

클론으로 이어진다. 방금 만든 두 부품 — log_event(step1)과 check의 판정부(step2) — 는 이름·시그니처 그대로 Hermes에 들어간다. log_event는 hermes/trace.py가 되고(클론에선 agent.py의 도구 실행 for-loop — M5 승인 게이트가 선 바로 그 길목 — 에 호출 두 줄을 끼워 모든 도구 결정이 자동 기록된다), check는 eval.py가 된다(EVAL_CASES + trace 격리 + Hermes().run() + exit code). step3에서 손으로 이은 "실행 → trace → 채점"을, 클론에선 eval.py 한 파일이 두 케이스에 대해 자동으로 돈다. 실습에서 만든 부품이, 클론에선 통합 Hermes의 관찰·측정 장치가 된다 — 그리고 그걸 붙이는 데 agent.py의 agent loop는 한 줄도 재구성하지 않는다(관찰은 로직을 안 바꾼다).

이번 단계: M6가 남긴 세 예고를 회수하며 과정을 닫는다 — ② 검색이 맞는 chunk를 물어왔는지 측정 못 한다(→ eval), ③ 무슨 도구를 언제·왜 불렀는지 print로 흘려볼 뿐 남지 않는다(→ trace), ④ 이제 Hermes는 코딩(M2~M4)·자율(M5)·RAG(M6) 세 성격을 다 가졌다(→ 한 데모로 통합). ★ 그런데 결정적으로 — 세 flavor 통합은 이미 코드 레벨에서 끝나 있다. M3에서 agent loop를 완성한 뒤로 새 능력은 늘 루프 수정이 아니라 도구 추가였다 (read_file→write_file/run_bash→update_plan→search_docs). 그래서 다섯 도구가 한 agent.py 루프에 이미 다 꽂혀 있다. # hermes/trace.py  (신규 파일)
"""실행 trace 로깅 — agent loop가 부른 도구를 logs/trace.jsonl에 한 줄씩 남긴다(observability).
M6까지의 print(흘려보내고 사라짐)를 '구조화된 영속 로그'로 승격한 것. 로직은 안 바꾼다 — 관찰만 한다."""
import json
import os
import datetime
from .config import LOG_DIR, LOG_FILE


def log_event(step, tool, tool_input, result, approved=True):
    """한 번의 도구 호출을 JSON 한 줄(jsonl)로 LOG_FILE에 append한다.
    result는 앞부분만 잘라 저장한다 — trace는 '무슨 일이 있었나'의 요약이지 전체 덤프가 아니다."""
    os.makedirs(LOG_DIR, exist_ok=True)                       # logs/ 없으면 생성
    event = {
        "ts": datetime.datetime.now().isoformat(timespec="seconds"),
        "step": step,
        "tool": tool,
        "input": tool_input,
        "result_preview": str(result)[:200],                  # 길면 자른다(search_docs/read_file 대비)
        "approved": approved,                                 # 거부(게이트)도 기록 — '무엇을 막았나'도 관찰
    }
    with open(LOG_FILE, "a", encoding="utf-8") as f:
        f.write(json.dumps(event, ensure_ascii=False) + "\n")  # 한글 보존(ensure_ascii=False)
event 6키 — trace의 스키마(한 줄 = 한 도구 호출): ts(실행 시각) · step(agent loop 몇 번째 스텝) · tool(도구 이름) · input(도구 입력 dict) · result_preview(결과 앞 200자 — search_docs·read_file은 결과가 길어 요약만) · approved(True=실행됨 / False=게이트에서 거부됨). 두 디테일: ① ensure_ascii=False — 없으면 한글이 \uXXXX로 깨진다. ② str(result)[:200] — 전체 덤프 금지(로그가 순식간에 비대해진다).

# eval.py  (clone-project 루트에서: uv run python eval.py)
"""아주 작은 eval — 정해둔 질문에 Hermes가 '기대대로' 동작하는지 자동 채점한다.
기대 동작: (1) 옳은 도구를 불렀나(= trace를 읽어 확인) + (2) 답에 정답 문자열이 들어갔나.
★ 질문은 전부 읽기 전용(search_docs)이라 승인 게이트를 건드리지 않아 비대화형으로 안전하다."""
import json
import os
import sys
from hermes.agent import Hermes
from hermes.config import LOG_FILE

# (질문, 반드시 불러야 할 도구, 최종 답에 있어야 할 문자열) — 전부 kb/의 Nimbus 문서 근거
EVAL_CASES = [
    ("Nimbus에서 동시에 배포하는 서버 수 기본값이 몇이야?", "search_docs", "4"),
    ("Nimbus로 프로덕션 배포하는 명령이 뭐야?",              "search_docs", "nimbus ship"),
]


def check(question, want_tool, want_substring):
    """한 케이스를 채점한다. trace를 비워 이 실행만 격리 → run → trace로 도구 확인 + 답 문자열 확인."""
    os.makedirs(os.path.dirname(LOG_FILE) or ".", exist_ok=True)  # 데모 전에 eval을 돌려도 logs/가 없어 안 터지게
    open(LOG_FILE, "w").close()                              # 이 케이스의 trace만 남게 비운다
    answer = Hermes().run(question)                          # fresh 메모리로 실행
    events = [json.loads(line) for line in open(LOG_FILE, encoding="utf-8")]
    tools_used = {e["tool"] for e in events}                # 이번 실행이 부른 도구들(← trace가 증거)
    tool_ok = want_tool in tools_used
    ans_ok = want_substring in answer
    passed = tool_ok and ans_ok
    print(f"[{'PASS' if passed else 'FAIL'}] {question}")
    print(f"    {want_tool} 호출? {tool_ok} · 답에 '{want_substring}' 포함? {ans_ok}")
    return passed


def main():
    results = [check(q, t, s) for q, t, s in EVAL_CASES]
    passed = sum(results)
    print(f"\n{passed}/{len(results)} 통과")
    sys.exit(0 if passed == len(results) else 1)             # CI처럼 exit code로 성패


if __name__ == "__main__":
    main()

★ 질문은 왜 전부 읽기 전용(search_docs)인가: eval은 비대화형(파이프/CI)으로 돌린다 → write_file/run_bash가 끼면 M5 confirm()의 input()이 EOFError로 fail-closed 거부돼 결과가 뒤틀린다. 그래서 eval 질문은 search_docs만으로 답할 수 있는 사실 질문으로 골라 게이트를 안 건드린다(M5의 fail-closed 지식을 실전에 적용).
