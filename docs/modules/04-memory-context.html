Memory & Context

개념

M3에서 우리는 class Hermes가 stop_reason이 end_turn이 될 때까지 도는 agent loop를 만들었다. 그 루프는 매 스텝 self.messages(평범한 list)에 assistant 응답과 tool_result를 .append하고, 그 커진 list를 messages=self.messages로 통째로 다시 보낸다. 그래서 루프가 돌수록 history가 무한정 자란다 — M3 클론의 마지막에서 "이 self.messages가 커진다 → M4에서 다룬다"고 예고했고, agent.py엔 "이 self.messages가 M4에서 Memory로 교체될 자리"라는 주석이 이미 달려 있다. 이번 모듈이 그 예고와 주석을 회수한다.

왜 history가 계속 자라야 하는가? M1의 stateless 때문이다. Claude API는 상태를 갖지 않는다 — 서버는 지난 대화를 기억하지 않는다. 모델이 방금 전 내 말을 "기억하는" 것처럼 보이는 유일한 이유는, 우리가 매 호출마다 전체 messages history를 처음부터 다시 실어 보내기 때문이다. 즉 대화를 이어가려면 우리 쪽이 history를 누적해야 하고, 그 누적분을 매번 통째로 전송해야 한다. 여기서 두 가지 압박이 생긴다 — (1) 한 번의 호출에 실을 수 있는 토큰에는 상한(context window)이 있고, (2) 과금은 토큰 기준이라 history가 길수록 매 스텝이 더 비싸진다. 길어진 대화를 줄여야 하는 이유다.

M4의 해법은 self.messages를 class Memory로 승격하는 것이다. 이 객체는 자기 크기를 문자 수로 추정(token_estimate)하고, 그 추정치가 임계를 넘으면 최근 대화 몇 개만 남기고 그 이전 오래된 대화를 요약 1개로 대체한다(compaction). running example은 세 섹션이 공유한다 — 순수 텍스트로 길게 주고받은 멀티턴 대화를 임계까지 키운 뒤, 압축 전/후의 토큰 추정치와 메시지 개수를 눈으로 비교한다. Hermes에 작업 기억(working memory) 관리를 붙이는 모듈이다.

표기 규약(★ 세 섹션 공통): 개념·패턴은 공백/원어로 — memory/"메모리", context window(공백), compaction/"압축", persona, "토큰 추정". 코드·식별자·API 값은 코드 표기로 — class Memory, self.memory, .append(), .to_messages(), .token_estimate(), .compact(), 그리고 system=·messages=·tool_use·tool_result. 특히 헷갈리기 쉬운 쌍을 구분한다 — 개념 "토큰 추정" vs 메서드 token_estimate() / 개념 "압축"·"compaction" vs 메서드 compact() / 개념 "메모리" vs 클래스 Memory.

대화 메모리란 — history가 곧 기억

정의 — memory(메모리): 에이전트가 지난 대화를 이어가려고 누적·관리하는 대화 history. 그 자체가 서버에 저장된 상태가 아니라, 우리가 매 호출 통째로 재전송하기에 "기억"으로 작동한다. 익숙한 비유로는 프로세스의 작업 메모리 / 세션 상태다 — 요청과 요청 사이에 우리가 손으로 들고 있는 대화 맥락.

그래서 "메모리 관리"란 결국 무엇을 history에 남기고, 무엇을 줄일지의 문제다. 저장소를 새로 붙이는 게 아니라, 이미 들고 있는 messages 리스트를 얼마나·어떻게 유지할지를 정하는 것이다.

흔한 혼동 — 이 "memory"는 RAG가 아니다: 여기서 말하는 메모리는 "방금까지 무슨 대화를 했나"를 이어가는 working memory, 즉 대화 history 관리다. "내가 모르는 외부 지식을 검색해 프롬프트에 넣는" RAG(벡터 검색·임베딩·유사도)와는 다른 문제다. M4는 대화를 저장하고 요약할 뿐, 무엇도 검색하지 않는다. RAG는 M6에서 따로 다룬다.

context window와 비용 — 길수록 부딪히고, 길수록 비싸다

정의 — context window: 모델이 한 번의 호출에서 다룰 수 있는 토큰 총량의 상한. 프롬프트 입력(우리가 보낸 messages)과 생성 출력이 이 한도 안에 함께 들어가야 한다. 넘으면 못 넣는다. 비유하면 함수의 입력 버퍼 한도 — 버퍼에 안 들어가는 데이터는 실을 수 없다.

agent loop는 M1의 stateless 원리대로 매 스텝 커진 history를 통째로 재전송한다. 그래서 문제가 두 겹이다.

  • 한도(context window): history가 계속 자라면 언젠가 한 호출에 실을 수 있는 토큰 상한을 넘는다 — 그 너머는 못 보낸다.
  • 비용: 과금은 input/output 토큰 기준이다. history가 10K tokens까지 자랐다면, 그 뒤로는 매 스텝마다 그 10K를 input으로 다시 실어 보낸다 — 같은 대화를 스텝마다 반복 과금하는 셈이다.
왜 "한도보다 비용"이 실질 동기인가: 코스 기본 모델 claude-sonnet-4-6의 context window는 1M tokens로 매우 크다 — 웬만한 대화로는 한도에 잘 안 부딪힌다. 하지만 과금은 $3 / $15 per 1M tokens(input/output)라, 긴 history를 매 스텝 재전송하는 비용은 한도에 닿기 훨씬 전부터 꾸준히 쌓인다. 그래서 실무의 압축 동기는 대개 "터져서"가 아니라 "비싸져서"다. (그래서 클론에서는 압축을 눈으로 보려고 임계를 일부러 낮게 잡는다 — 1M을 채울 순 없으니까.)
비유의 한계: "입력 버퍼"는 넘치면 조용히 잘리기도 하지만, context window는 넘기면 API가 거부(에러)한다. 또 버퍼와 달리 입력과 출력이 같은 한도를 나눠 쓴다 — 프롬프트를 한도까지 채우면 답할 자리가 없어진다.

토큰을 대충 재기 — token_estimate

정의 — token_estimate(토큰 추정): 정확한 토크나이저를 부르지 않고 문자 수 등으로 토큰 수를 근사하는 것. "지금 history가 대략 몇 토큰인가"를 즉시 가늠하는 빠른 가늠자다. 비유하면 정확한 프로파일링 대신 len()으로 대충 크기를 재는 것 — 정밀하진 않아도 "임계를 넘었나?"를 판단하는 데는 충분하다.

구현은 한 줄이면 된다 — 모든 메시지의 문자 수를 더해 4로 나눈다(영어·코드 기준 대략 4자 ≈ 1토큰).

def token_estimate(messages) -> int:
    # 문자 수 // 4 ≈ 토큰 수. 정확한 토크나이저 대신 싼 근사.
    return sum(len(_text_of(m)) for m in messages) // 4

def _text_of(msg):
    # content 가 문자열이 아니라 블록 리스트/dict 여도 안전하게 문자열로.
    c = msg["content"]
    return c if isinstance(c, str) else str(c)
왜 정확히 안 재는가: Claude에는 정확한 측정 API(client.messages.count_tokens)가 있지만, 이건 네트워크 왕복이 드는 또 하나의 호출이다. 압축을 발동할지 말지를 정하는 가드에는 "정확히 8,213토큰"이 필요 없다 — "임계를 넘겼나 아닌가"만 알면 된다. 그 판단엔 문자 수 나눗셈이면 충분히 빠르고 싸다. (정밀 측정·prompt caching은 범위 밖 — 여기선 일부러 싼 추정치를 쓴다.)

compaction — 최근은 보존, 오래된 건 요약 1개로

정의 — compaction(압축): context window·비용을 아끼려고 오래된 대화 메시지들을 요약 1개로 대체해 history 토큰을 줄이는 것. 비유하면 로그 compaction/rotation, 또는 슬라이딩 윈도우에 접힌 요약 헤더를 붙이는 것 — 최근 항목은 원본 그대로 두고, 오래된 항목은 한 덩어리 요약으로 접는다.

정책은 두 부분이다 — 최근 keep_recent개는 원본 보존(대화를 매끄럽게 이어가야 하니까), 그 이전 오래된 것들은 하나의 요약으로 접기. 요약을 만드는 일은 마법이 아니라 또 한 번의 LLM 호출이다 — "이 로그를 요약해줘"라고 모델에게 부탁한다.

def compact(messages, keep_recent):
    recent = messages[-keep_recent:]     # 최근 대화는 그대로 이어간다
    old    = messages[:-keep_recent]     # 그 이전 오래된 대화는
    summary = _summarize(old)            # 별도 LLM 호출로 요약 1개로 접는다
    # 요약을 '맨 앞 user 메시지'로 넣고, 최근 대화를 뒤에 붙인다.
    return [{"role": "user", "content": f"[이전 대화 요약]\n{summary}"}] + recent

def _summarize(old) -> str:
    log = "\n".join(f"{m['role']}: {_text_of(m)}" for m in old)
    resp = client.messages.create(       # ← 요약도 결국 한 번의 create 호출
        model=MODEL, max_tokens=512,
        system="다음 대화 로그를 이후 대화에 필요한 사실 위주로 3~5문장으로 요약해줘.",
        messages=[{"role": "user", "content": log}],   # tools 없음, Hermes persona 아님
    )
    return "".join(b.text for b in resp.content if b.type == "text")

요약을 맨 앞 user 메시지로 넣는 데는 이유가 있다 — history는 항상 user로 시작해야 하므로(M1), 이렇게 하면 압축 후에도 첫 메시지가 언제나 user라 안전하다. 클론에서는 이 정책을 class Memory의 .compact()·._summarize() 메서드로 감싸고, .token_estimate()가 임계를 넘는 순간 .to_messages() 안에서 자동으로 .compact()가 돌게 한다.

running example로 돌려보면 압축의 효과가 수치로 보인다 — 순수 텍스트 멀티턴 대화를 임계까지 키운 뒤 압축하면, 이런 모양이 관찰된다.

압축 전:  messages 여러 개,   token_estimate = (임계 초과)
   ↓  compact()  — 최근 몇 개는 보존, 그 이전은 요약 1개로 접기
압축 후:  messages = 요약 1개 + 최근 몇 개,   token_estimate = (임계 아래로 ↓)

메시지 개수와 토큰 추정치가 둘 다 줄어든다. 그리고 압축된 history로도 "최근 맥락"이 살아 있어 대화를 한 턴 더 이어갈 수 있다. (실습에서 압축 전/후의 token_estimate와 메시지 개수를 직접 print해 실제 숫자로 확인한다.)

비유의 한계: 로그 rotation은 오래된 로그를 버리거나 그대로 아카이브하지만(원본 복구 가능), compaction은 요약이라 디테일이 영구적으로 유실되는 손실 압축이다. 게다가 요약 자체가 또 한 번의 유료 LLM 호출이라 공짜가 아니다 — 그래서 가끔만 발동하도록 임계를 잡는다.

압축의 함정 — 쌍을 쪼개지 마라

순수 텍스트 대화라면 아무 데서나 잘라 요약해도 된다. 하지만 진짜 Hermes의 history에는 M2에서 배운 tool_use(assistant) ↔ tool_result(user) 쌍이 섞여 있다. 여기서 함정이 생긴다.

함정 — 요약 경계가 쌍을 쪼개면 400: 오래된 앞부분을 요약으로 접을 때, 경계가 하필 tool_use와 그 짝 tool_result 사이를 지나면 어떻게 될까? tool_use는 요약에 먹혀 사라지고 짝 없는 tool_result만 남거나, 그 반대가 된다. 그러면 다음 create 호출이 400을 낸다 — M2에서 배운 바로 그 "짝이 안 맞는 tool 블록" 에러다. 해법(개념): 보존 경계가 tool_result에서 시작하면, 경계를 한 칸씩 앞으로 물려 tool_use와 tool_result가 같은 쪽(요약되거나, 보존되거나)에 오게 한다. (실제 경계 가드 코드 _is_tool_result_turn은 "Hermes 만들기"에서 다룬다 — 여기선 "쌍을 깨지 마라"만 기억하면 된다.)

기억할 원칙은 M2의 교훈 그대로다 — 400은 값보다 먼저 쌍·id 매칭을 의심하라. 압축은 그 쌍을 자기도 모르게 깰 수 있는 새 위험이다.

persona는 메모리 밖에 있다

정의 — persona: system prompt로 부여하는 에이전트의 고정 정체성·항구 규칙(M1의 SYSTEM). messages(history) 밖 별도 슬롯(system=)에 있어, compaction의 영향을 받지 않고 매 호출 항상 함께 전송된다. 비유하면 프로세스의 환경설정 / 불변 규칙 — 런타임 로그(대화)와 분리되어, 로그를 접어도 규칙은 그대로다.

이 구분이 메모리 설계의 한 축이다. compaction은 messages(소모성 대화)만 접는다 — system=SYSTEM에 있는 persona는 history가 아니므로 압축이 건드리지 않는다. 덕분에 오래된 대화를 아무리 접어도 에이전트의 정체성·규칙은 사라지지 않고, 매 호출 싸게(항상 같은 짧은 텍스트로) 함께 간다. "무엇이 항구 규칙(system)이고 무엇이 소모성 대화(messages)인가"를 나누는 것 자체가 메모리 설계의 핵심이다.

한눈 정리

  • 메모리 = 대화 history 관리다. 모델이 "기억"하는 건 M1의 stateless 때문에 우리가 매 호출 history를 통째로 재전송하기 때문 — 그래서 history가 길수록 context window에 부딪히고 매 스텝이 비싸진다. (이 메모리는 RAG가 아니다 — 검색이 아니라 대화 저장·요약. RAG는 M6.)
  • token_estimate = 문자 수 // 4 근사. 정확한 count_tokens는 네트워크 왕복이라, "임계를 넘었나"만 보는 가드엔 싼 추정이면 충분하다.
  • compaction = 추정치가 임계를 넘으면 최근 keep_recent개는 보존하고 그 이전 오래된 대화를 요약 1개로 대체(요약은 별도 LLM 호출). 요약은 맨 앞 user 메시지로 넣는다. 메시지 수·토큰이 함께 줄되 최근 맥락은 살아 있다.
  • 함정 = 쌍을 쪼개지 마라. 요약 경계가 tool_use/tool_result(M2) 사이를 지나면 400 — 경계를 쌍 밖으로 물린다.
  • persona는 메모리 밖. system= 슬롯의 항구 규칙이라 compaction에 안 사라지고 매 호출 싸게 함께 간다.
  • 범위 = 여기까지가 대화 메모리 관리 + context window 인식 + 요약 압축. 목표 분해(planning)와 위험 도구 승인 게이트는 M5, 외부 지식 검색(RAG)은 M6에서 다룬다.

API는 stateless라 지난 대화를 스스로 기억하지 못하기 때문이다(M1). 모델의 "기억"은 곧 우리가 매 호출 history 전체를 다시 보내는 것이고, 그래서 대화가 길수록 매 호출이 더 비싸지고(입력 토큰이 늘어난다) 언젠가 context window 한도에 부딪힌다. 그러니 오래된 대화를 줄여야 한다. 이번 실습은 그 줄이기 = compaction을 순수 텍스트 대화로 손에 익힌다: (1) 문자 수로 토큰을 추정하고, (2) 임계를 넘으면 최근 몇 개만 남기고 오래된 대화를 요약 1개로 대체한 뒤, (3) 압축 전/후의 토큰 수·메시지 수를 눈으로 비교한다.

이 실습은 도구 없는 순수 텍스트 대화다. user/assistant 텍스트만 주고받으므로 tool_use/tool_result 쌍이 없다 → 요약 경계가 그 쌍을 쪼개 400을 내는 함정이 아예 생기지 않는다. 덕분에 "추정 → 임계 → 최근 보존 → 요약 1개로 대체 → 축소"라는 압축 절차 자체에만 집중한다. (쌍이 섞인 실제 Hermes history의 경계 함정은 클론(Hermes 만들기)에서 실물로 만난다 — 같은 압축 골격에 경계 가드만 더한다.)

def _text_of(msg):
    c = msg["content"]
    return c if isinstance(c, str) else str(c)

def token_estimate(messages):
    return sum(len(_text_of(m)) for m in messages) // 4

# 오래된 메시지들을 '별도 LLM 호출' 하나로 요약한다 — tools 없음, 짧은 max_tokens.
def summarize(old):
    log = "\n".join(f"{m['role']}: {_text_of(m)}" for m in old)
    resp = client.messages.create(
        model=MODEL, max_tokens=512,
        system="다음 대화 로그를 이후 대화에 필요한 사실 위주로 3~5문장으로 간결히 요약해줘.",
        messages=[{"role": "user", "content": log}],   # 요약도 그냥 한 번의 messages.create
    )
    return "".join(b.text for b in resp.content if b.type == "text")

# 최근 keep_recent개는 그대로 두고, 그 이전(old)을 요약 1개로 대체한다.
def compact(messages):
    old = messages[:-keep_recent]      # 오래된 앞부분
    recent = messages[-keep_recent:]   # 최근 keep_recent개(그대로 보존)
    summary = summarize(old)
    # 요약을 '첫 user 메시지'로 prepend -> history는 항상 user로 시작(첫 메시지 user 규칙)
    return [{"role": "user", "content": f"[이전 대화 요약]\n{summary}"}] + recent

# --- 압축 전: 토큰·메시지 수 ---
print(f"[압축 전] tokens~{token_estimate(messages)}  msgs={len(messages)}")

# 임계를 넘으면 compaction (이 조건이 클론 Memory.to_messages 의 자동 발동과 같다)
if token_estimate(messages) > threshold:
    messages = compact(messages)
    print("  -> 임계 초과 -> compaction 실행 (오래된 대화 = 요약 1개)")

# --- 압축 후: 토큰·메시지 수 ---
print(f"[압축 후] tokens~{token_estimate(messages)}  msgs={len(messages)}")

# --- 압축된 history 로 한 턴 더: '최근 맥락'이 살아있는지 확인 ---
messages.append({"role": "user",
                 "content": "방금 알려준 3일차 노을 명소 두 곳 이름만 다시 정리해줘."})
resp = client.messages.create(model=MODEL, max_tokens=512, messages=messages)
answer = "".join(b.text for b in resp.content if b.type == "text")
print(f"[이어가기] {answer}")
요약은 "그냥 또 한 번의 messages.create"다. 특별한 API가 아니다 — 오래된 대화를 로그 문자열로 이어붙여 system="...요약해줘"로 한 번 부르면 된다. 단 두 가지가 중요하다: (1) tools를 넘기지 않는다(순수 텍스트 요약이라 도구가 필요 없다), (2) max_tokens를 작게(여기선 512) 잡아 요약이 짧고 싸게 나오게 한다. 이 요약 1개가 오래된 여러 메시지를 대신한다.

3) 돌려보기 — 압축 전/후 토큰·메시지 수를 눈으로 비교

실행하면 압축 전 → 압축 후로 토큰 추정치와 메시지 수가 함께 줄어드는 것을 볼 수 있다. 마지막 [이어가기]는 압축된 history로 한 턴 더 물어본 것이다 — 오래된 앞부분은 요약으로 접혔지만 최근 4개는 그대로 남아 노을 명소를 정확히 답한다.

무엇이 정확하고 무엇이 모델마다 다른가.
  • 정확(결정적): 압축 전 tokens~326·msgs=14와, 압축 후 msgs=5. 메시지 수는 항상 14 → 5다 (오래된 10개가 요약 1개로 접히고 + 보존한 최근 4개 = 5). token_estimate가 문자수 // 4라는 결정적 식이라 326은 손으로도 같은 값이 나온다.

왜 이게 "메모리 관리"인가. 요약된 옛 대화(일정·렌터카·음식·숙소·준비물)에는 노을 명소 이름이 없다 — 그건 보존된 최근 4개(우도·노을 Q&A) 안에 있다. 그래서 압축 뒤에도 "방금 얘기한 것"을 정확히 이어간다. 오래된 건 요약으로 접고 최근은 원문으로 남긴다 — 이게 compaction의 정책이고, 매 호출 통째로 재전송되는 history를 context window 안에서 싸게 유지하는 방법이다.
실험해 보기.
  • threshold를 150처럼 더 낮추면 → 더 짧은 대화에도 압축이 더 자주 발동한다.
  • keep_recent를 4 → 10으로 키우면 → 보존 구간이 커져 덜 접힌다(요약으로 줄어드는 양이 작아진다). 전체 메시지 수(14)에 가까워질수록 접을 옛 메시지가 거의 없어 압축 효과가 사라진다.
  • (예고) 클론에서는 이 절차를 class Memory로 감싸 to_messages()가 알아서 압축하고, 실제 tool_result가 섞인 history라 쌍을 안 쪼개는 경계 가드가 더해진다. 여기 함수(token_estimate/summarize/compact)가 그대로 Memory의 메서드가 된다.
막히면:
  • 압축이 아예 안 일어난다(-> 임계 초과 줄이 안 뜸) → 두 경우다. (a) token_estimate가 threshold 이하 → 대화를 더 길게 하거나 threshold를 낮춘다. (b) keep_recent가 전체 메시지 수 이상 → messages[:-keep_recent](old)가 비어 요약할 게 없다. keep_recent는 전체보다 작게.
  • 요약 호출에 실수로 tools=를 넘김 → 요약이 엉뚱하게 도구를 부르려 하거나 응답에 tool_use 블록이 섞여 "".join(...text...)이 비게 된다. summarize의 create에는 tools를 넘기지 않는다(순수 텍스트 요약).
  • BadRequestError(400) "first message must use role 'user'" → 압축 후 첫 메시지가 user가 아니다. 이 실습은 요약을 첫 user 메시지로 prepend하므로 안전하다 — recent가 assistant로 시작해도 그 앞의 요약(user)이 첫 메시지가 된다. 요약을 assistant로 넣지 말 것.
  • 요약이 부실해 이어지는 답이 헛돈다(맥락 유실) → system 프롬프트에 "이후 대화에 필요한 사실 위주"를 지시한다. 요약은 손실 압축이라 디테일 일부는 사라진다 — 그래서 최근 keep_recent개는 원문으로 보존한다.
  • token_estimate가 TypeError → content가 문자열이 아니라 블록 리스트/dict일 때 len(content)를 직접 부르면 깨진다. _text_of로 str()을 감싼다(이 실습은 순수 텍스트라 안 나지만, 도구가 섞이는 클론을 위한 습관).
  • 토큰이 딱 맞지 않는다 → token_estimate는 문자수 // 4 추정이다. 정확값(count_tokens)과 다르다 — 가드용이라 그래도 된다. "정확히 몇 토큰"을 기대하지 말 것.
  • AuthenticationError(401) → ANTHROPIC_API_KEY 미설정/오타. echo $ANTHROPIC_API_KEY로 확인(step1은 API를 안 부르니 키 없이도 됨).

M3 __init__에 달아 둔 주석 이 self.messages가 M4에서 Memory 객체로 교체될 자리다를 회수하는 모듈이다. 개념↔코드 매핑 한 줄: 개념의 대화 메모리 = class Memory, 토큰 추정 = token_estimate(), context window가 차기 전에 줄인다 = to_messages()의 if … > threshold: compact(), 최근은 남기고 오래된 건 요약 = compact()의 recent 보존 + _summarize(old).

전제: M3까지 만든 clone-project/hermes/(config.py, llm.py, tools.py, agent.py의 class Hermes, REPL __main__.py) 위에 더한다. 이번엔 새 파일 memory.py를 만들고, config.py에 상수 둘을 추가, agent.py에서 self.messages를 self.memory로 교체한다. llm.py·__main__.py·tools.py는 한 글자도 안 건드린다(캡슐화의 증거 — 뒤에서 확인). 참조 해답: clone-project/_solution/04-memory-context/hermes/ (막히면 diff로 대조).
실습과의 관계: 직접 사용해보기에서 순수 텍스트 대화로 눈으로 본 추정 → 임계 초과 → 최근 보존 → 오래된 것 요약 1개로 → 축소가 여기서도 똑같은 골격이다. 차이는 둘뿐: ① 실습은 한 스크립트에 token_estimate()/compact()를 함수로 절차적으로 펼쳤지만, Hermes는 같은 절차를 memory.py의 class Memory 메서드로 캡슐화하고 agent.py는 그걸 쓰기만 한다. ② 클론 history엔 실제 tool_use/tool_result 쌍이 섞여 있어, 실습엔 없던 경계 가드(쌍을 안 쪼개기)를 하나 더한다.
⚠ 이 메모리는 RAG가 아니다: 여기서 만드는 Memory는 방금까지 무슨 대화를 했나를 이어가는 working memory(대화 history 관리·요약)다. 내가 모르는 외부 지식을 검색해 넣는 RAG(임베딩·유사도 검색)는 M6이고, 저장·요약이지 벡터 검색이 아니다. 헷갈리지 말 것.

M3 → M4: self.messages(list)를 self.memory(Memory)로 (before / after)

지금 무엇을/왜: 이번 모듈에서 agent.py가 바뀌는 건 딱 다섯 곳, 그중 의미가 바뀌는 건 한 줄뿐이다. Memory.append를 list.append과 똑같은 사용감으로 만들었기 때문에, .append 3곳은 이름만(self.messages→self.memory) 바뀌고 로직은 그대로다. 먼저 두 그림을 나란히 보자 (개념용 축약 — 실제 타이핑은 아래 1)~3)에서 한다).

교체 포인트는 다섯이다:

  1. self.messages = [] → self.memory = Memory() + from .memory import Memory. history 소유 형태가 list → 자기 크기를 알고 스스로 줄이는 객체로.
  2. .append 3곳(①②③)은 이름만 self.messages→self.memory. 규칙(assistant를 통째로 append / tool_result는 user 턴)은 M2~M3 그대로다.
  3. messages=self.messages → messages=self.memory.to_messages() (유일한 의미 변경): 평소엔 내부 리스트를 그대로 돌려주지만, 토큰 추정이 임계를 넘으면 그 자리에서 compact()가 돈다. agent loop 코드는 압축을 몰라도 된다(캡슐화).
  4. tool_results 수집·종료 분기·MAX_STEPS 가드는 M3와 100% 동일 — 손대지 않는다.
  5. llm.py·__main__.py·tools.py는 무변경. 진입점을 안 건드리고 메모리를 붙인 것 자체가 캡슐화의 증거.
왜 압축이 to_messages() 안에서만 도는가: agent loop에서 create()가 불리는 시점은 항상 직전 스텝의 tool_result까지 history에 다 넣은 뒤다(맨 처음은 user 직후). 즉 to_messages()가 불리는 순간 history의 꼬리는 언제나 쌍이 완결돼 있어, 압축은 앞쪽만 안전하게 접으면 된다. 그래서 압축 훅 지점을 오직 to_messages() 하나로 둔다(append 도중, 쌍이 미완인 순간엔 안 건드린다).

# hermes/config.py  (맨 아래에 이어서 추가)

# M4 — Memory & Context: compaction(대화 요약 압축)용 상수

2) hermes/memory.py 신설 — class Memory (★ 이 모듈의 핵심)

지금 무엇을/왜: 이 파일이 이번 모듈의 심장이다. M3까지 agent.py가 직접 들던 self.messages(list)를 여기 class Memory로 승격한다 — list처럼 .append로 쌓되, API로 넘기기 직전에 스스로 토큰을 재고(token_estimate) 넘치면 접는다(compact). 조각으로 하나씩 쌓아 가자.

지금 무엇을/왜: 먼저 파일 머리 — 모듈 설명, import, 그리고 __init__. 요약도 같은 Claude 클라이언트로 부르므로 llm.py의 client와 config.py의 상수를 재사용(import)한다. 새 파일 hermes/memory.py를 만들고 아래를 그대로 친다.

# hermes/memory.py
"""Hermes의 대화 메모리 — 누적된 history를 소유하고, 너무 길어지면 스스로 압축한다.

M3까지 agent.py가 직접 들던 self.messages(평범한 list)를 이 class Memory로 승격한다.
list처럼 .append로 쌓되, API로 넘기기 직전(to_messages)에 토큰을 추정해 임계를 넘으면
오래된 메시지들을 '요약 1개'로 접는다(compaction). append 사용감은 list 그대로라
agent.py 변경은 최소가 된다."""
from .llm import client                      # 요약도 같은 Claude 클라이언트로 (재사용)
from .config import MODEL, COMPACT_THRESHOLD, KEEP_RECENT


class Memory:
    def __init__(self, threshold=COMPACT_THRESHOLD, keep_recent=KEEP_RECENT):
        self.messages = []              # append-only 로그 — M3의 self.messages가 이 안으로 들어왔다
        self.threshold = threshold      # 이 추정 토큰 수를 넘으면 compaction
        self.keep_recent = keep_recent  # 압축해도 최근 이만큼은 원문 그대로 보존
SYSTEM(persona)을 import하지 않는 이유: 요약은 요약 전용 system으로 부른다(뒤 _summarize). Hermes의 persona SYSTEM은 llm.py의 messages= 밖 별도 슬롯에 그대로 살아 있어 compaction과 무관하게 안 사라진다 — 그래서 Memory는 SYSTEM을 알 필요가 없다.

지금 무엇을/왜: append(list처럼 쌓기)와 token_estimate(문자 수로 토큰 대충 재기). class Memory 안에, __init__ 아래에 이어서 작성한다.

# hermes/memory.py  (class Memory 안에 이어서 — append · token_estimate)

    def append(self, msg):
        """list.append과 똑같은 사용감 — agent.py는 self.memory.append처럼 쓴다."""
        self.messages.append(msg)

    def token_estimate(self) -> int:
        """정확한 토크나이저(count_tokens, 네트워크 왕복) 대신 문자 수 // 4로 근사.
        가드(임계 판단)에는 이 싼 추정으로 충분하다."""
        return sum(len(_text_of(m)) for m in self.messages) // 4
정의 — token_estimate: 정확한 토크나이저(client.messages.count_tokens, 네트워크 왕복)를 매번 부르는 대신 문자 수 // 4로 지금 대략 몇 토큰인가를 즉시 가늠한다(정확한 프로파일링 대신 len()으로 크기 재기). 가드(임계 판단)엔 이 정도면 충분하다. _text_of로 감싸는 이유는 content가 문자열이 아니라 블록 리스트/dict일 수도 있어서다(뒤에서 정의).

지금 무엇을/왜: to_messages() — API 전송용 history를 돌려주는 창구이자 압축이 자동 발동하는 유일한 지점이다(before/after의 그 의미 있는 한 줄이 이걸 부른다). 이어서 작성한다.

# hermes/memory.py  (class Memory 안에 이어서 — to_messages: ★ 압축 자동 훅)

    def to_messages(self) -> list:
        """API 전송용 history를 반환한다. ★ 여기서 압축이 자동 발동한다:
        추정 토큰이 임계를 넘으면 compact()로 오래된 대화를 접은 뒤 반환한다.
        agent loop는 이 사실을 몰라도 된다(캡슐화)."""
        if self.token_estimate() > self.threshold:
            self.compact()
        return self.messages
개념↔코드: context window가 차기 전에 줄인다가 정확히 이 if self.token_estimate() > self.threshold: self.compact() 한 줄이다. agent.py는 messages=self.memory.to_messages()라고만 쓰면 되고, 압축이 필요한지/언제 도는지는 Memory가 알아서 판단한다.

지금 무엇을/왜: compact() — 이 모듈의 클라이맥스다. 최근 keep_recent개는 원문 보존, 그 이전 오래된 메시지들을 요약 1개로 대체한다. 그리고 ★ 경계 가드 — 보존 경계가 tool_use/tool_result 쌍을 쪼개지 않게 한 칸씩 물린다. 이어서 작성한다.

# hermes/memory.py  (class Memory 안에 이어서 — compact: 최근 보존 + 요약 1개 + 경계 가드)

    def compact(self):
        """최근 keep_recent개는 원문 보존, 그 이전 오래된 메시지들을 요약 1개로 대체한다."""
        cut = len(self.messages) - self.keep_recent
        if cut <= 0:
            return
        # ★ 경계 가드: 보존 구간이 tool_result로 시작하면 그 짝 tool_use가 요약에 먹혀
        # 다음 호출이 400(orphan tool_result)이 난다. 경계를 앞으로 물려 쌍을 안 쪼갠다.
        while cut > 0 and _is_tool_result_turn(self.messages[cut]):
            cut -= 1
        if cut <= 0:
            return
        old, recent = self.messages[:cut], self.messages[cut:]
        summary = self._summarize(old)
        # 요약은 '첫 user 메시지'로 prepend — history는 늘 user로 시작해야 하니 안전하다.
        self.messages = [{"role": "user", "content": f"[이전 대화 요약]\n{summary}"}] + recent
        print(f"  [memory] compaction: {len(old) + len(recent)} msgs → {len(recent) + 1} msgs")
★ 이 모듈의 대표 함정 — 압축이 쌍을 쪼개면 400: Hermes history엔 tool_use(assistant) ↔ tool_result(user) 쌍이 들어 있다(M2). 경계를 아무 데나 잘라 tool_result만 recent에 남고 그 짝 tool_use가 old로 넘어가 요약돼 버리면, 다음 create가 400 (orphan tool_result / 짝 없는 tool_use)이다 — M2에서 배운 바로 그 400. 그래서 while cut > 0 and _is_tool_result_turn(self.messages[cut]): cut -= 1로 경계를 쌍 밖으로 물린다. SDK 400은 값보다 필드·id 매칭·쌍부터 본다는 M2 교훈 그대로.
첫 메시지는 왜 user로 prepend? API 규칙상 history는 첫 메시지가 user여야 한다 (assistant로 시작하면 400). 압축 후 recent가 assistant부터 시작하더라도, 요약을 항상 첫 user 메시지 {"role":"user", "content":"[이전 대화 요약]\n…"}로 맨 앞에 붙이므로 언제나 안전하다. persona는 이 자리가 아니라 system= 슬롯이다.

지금 무엇을/왜: _summarize — 별도 LLM 호출로 오래된 로그를 요약한다. 핵심 셋: tools 없음, Hermes persona가 아닌 요약 전용 system, 짧은 max_tokens. 이어서 작성한다.

# hermes/memory.py  (class Memory 안에 이어서 — _summarize: 별도 LLM 호출)

    def _summarize(self, old) -> str:
        """오래된 메시지들을 별도 LLM 호출로 요약한다.
        tools 없음, Hermes persona(SYSTEM)도 아님 — 요약 전용 system을 따로 준다."""
        log = "\n".join(f"{m['role']}: {_text_of(m)}" for m in old)
        resp = client.messages.create(
            model=MODEL,
            max_tokens=512,
            system="다음 대화 로그를 이후 대화에 필요한 사실 위주로 3~5문장으로 간결히 요약해줘.",
            messages=[{"role": "user", "content": log}],
        )
        return "".join(b.text for b in resp.content if b.type == "text")

지금 무엇을/왜: 마지막으로 클래스 밖 헬퍼 둘. _text_of는 content를 안전하게 문자열로(추정·요약용), _is_tool_result_turn은 경계 가드가 쓰는 이 메시지가 tool_result 턴인가 판별기다. 파일 맨 아래, class Memory 바깥에 작성한다.

# hermes/memory.py  (파일 맨 아래, class Memory 바깥에 — 헬퍼 둘)


def _text_of(msg) -> str:
    """content를 문자열로 — 블록 리스트/dict여도 str()로 안전 직렬화(추정·요약용)."""
    c = msg["content"]
    return c if isinstance(c, str) else str(c)


def _is_tool_result_turn(msg) -> bool:
    """이 메시지가 tool_result 턴인가(경계 가드용).
    content가 블록 리스트이고 그 안에 type == 'tool_result' 블록이 있으면 True.
    우리가 만든 dict·SDK 객체 둘 다 대응한다."""
    c = msg["content"]
    if not isinstance(c, list):
        return False
    for b in c:
        t = b.get("type") if isinstance(b, dict) else getattr(b, "type", None)
        if t == "tool_result":
            return True
    return False
왜 _text_of로 감싸나(token_estimate TypeError 예방): assistant 턴의 content는 SDK 블록 리스트, tool_result 턴의 content는 dict 리스트다 — 여기에 len()을 바로 걸면 문자열이 아니라 깨지거나 엉뚱한 값이 나온다. str()로 직렬화하면 리스트/dict든 문자열이든 안전하게 길이를 잰다. _is_tool_result_turn이 b.get(...)(dict)과 getattr(...)(SDK 객체)를 둘 다 보는 이유도 같다 — history엔 두 형태가 섞여 있다.

3) hermes/agent.py 교체 — self.messages → self.memory

지금 무엇을/왜: 위 before/after에서 짚은 다섯 곳만 고친다. run()의 도구 왕복·종료 분기·가드는 M3와 한 글자도 다르지 않다. 아래가 교체를 반영한 agent.py 전체다 — 새로 짜는 게 아니라 그 다섯 곳만 고친다는 눈으로 보라(주석의 M4/self.memory 표시가 바뀐 지점).

# hermes/agent.py
"""Hermes 본체 — agent loop(ReAct)를 담은 class Hermes.

M2 llm.chat_with_tools 의 도구 1-step 왕복(if)을 while 루프로 '승격'한 것.
도구 왕복 4단계·tool_use_id 매칭은 M2와 완전히 동일하고, 그 왕복을
'stop_reason 이 tool_use 가 아닐 때까지 반복'으로 감쌌을 뿐이다.

M4: history 소유 형태를 평범한 list(self.messages)에서 self.memory(class Memory)로
교체했다. 로직이 바뀌는 건 딱 한 줄 — messages=self.memory.to_messages() — 이고,
거기서 토큰 추정이 임계를 넘으면 오래된 대화가 요약 1개로 압축(compaction)된다."""
from .llm import client, SYSTEM
from .config import MODEL, MAX_TOKENS, MAX_STEPS
from .tools import TOOLS, run_tool
from .memory import Memory


class Hermes:
    def __init__(self):
        # M3까진 self.messages = [] (평범한 list)였다. M4에서 그 자리를 Memory로 교체 —
        # 자기 크기를 알고(token_estimate) 스스로 줄이는(compact) 객체가 history를 소유한다.
        self.memory = Memory()

    def run(self, user_msg: str) -> str:
        """user_msg를 받아, stop_reason이 tool_use가 아닐 때까지 도구를 반복 실행한다.
        while 한 바퀴 = ReAct 한 사이클(추론→행동→관찰). MAX_STEPS로 무한 루프를 막는다."""
        self.memory.append({"role": "user", "content": user_msg})

        step = 0
        while step < MAX_STEPS:                 # ← M2의 if를 감싼 while + 무한 루프 가드
            step += 1
            # 매 스텝: history를 통째로 재전송(M1 stateless). 단, to_messages()가 그 순간
            # 토큰을 추정해 임계를 넘으면 오래된 대화를 요약 1개로 접어(compact) 돌려준다.
            resp = client.messages.create(
                model=MODEL,
                max_tokens=MAX_TOKENS,
                system=SYSTEM,
                tools=TOOLS,
                messages=self.memory.to_messages(),
            )
            # assistant 응답을 '통째로' append (tool_use 블록 보존).
            # M2에선 두 분기에 각각 있던 걸, 여기선 루프 상단 1회로 합쳤다.
            self.memory.append({"role": "assistant", "content": resp.content})

            # 종료 분기 — M2 chat_with_tools의 '그 테스트' 그대로.
            # tool_use가 아니면(end_turn/max_tokens/refusal) 최종 답으로 종료.
            if resp.stop_reason != "tool_use":
                return "".join(b.text for b in resp.content if b.type == "text")

            # 여기부터는 M2와 '완전히 동일' — tool_use 블록마다 실행해 tool_result 수집.
            tool_results = []
            for block in resp.content:
                if block.type == "tool_use":
                    print(f"  ↳ step {step}: {block.name}({block.input})")  # 루프가 도는 걸 눈으로
                    result = run_tool(block.name, block.input)   # 우리가 실행
                    tool_results.append({
                        "type": "tool_result",
                        "tool_use_id": block.id,   # tool_use 의 id와 반드시 매칭
                        "content": result,          # 반드시 문자열
                    })
            # 결과를 user 턴으로 회신하고 루프 top으로 → M2의 '2차 호출'을 루프가 대체.
            self.memory.append({"role": "user", "content": tool_results})

        # MAX_STEPS까지 돌아도 안 끝났다 → 강제 종료(가드 탈출).
        return "[max_steps 도달 — 루프를 강제 종료했어요]"
M3와의 diff 주의(딱 이만큼): ① from .memory import Memory 한 줄 추가. ② __init__의 self.messages = [] → self.memory = Memory()(주석도 갱신). ③ run()의 self.messages.append(…) 3곳을 self.memory.append(…)로. ④ messages=self.messages → messages=self.memory.to_messages()(유일한 의미 변경). 그 밖엔 한 글자도 안 바뀐다.
